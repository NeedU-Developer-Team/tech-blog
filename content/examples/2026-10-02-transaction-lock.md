선착순 쿠폰 기능을 처음 만들었을 때 테스트 환경에서는 아무 문제가 없었습니다. 하지만 요청이 동시에 들어오자 재고보다 많은 쿠폰이 발급됐습니다. 이 글은 그 문제를 발견하고, 세 가지 잠금 전략을 비교해 운영 환경에 적용한 기록입니다.

## 문제는 어디에서 시작됐나

쿠폰 수량을 읽고 차감하는 두 동작 사이에 다른 요청이 끼어들 수 있었습니다. 각 요청은 동일한 재고 값을 읽었고, 모두 자신이 마지막 쿠폰을 가져갈 수 있다고 판단했습니다.

```java
@Transactional
public Coupon issue(Long couponId, Long memberId) {
    Coupon coupon = couponRepository.findById(couponId)
        .orElseThrow(CouponNotFoundException::new);

    coupon.decreaseQuantity();
    return issuedCouponRepository.save(new Coupon(coupon, memberId));
}
```

단일 요청만 보면 자연스러운 코드지만, `읽기 → 판단 → 쓰기`가 하나의 원자적 연산은 아니었습니다.

## 세 가지 선택지를 같은 조건에서 비교했다

100개의 쿠폰에 1,000개 요청을 동시에 보내고 성공 건수, 평균 응답 시간, 데이터베이스 부하를 측정했습니다.

| 방식 | 정합성 | 평균 응답 | 운영 복잡도 |
| --- | --- | --- | --- |
| 낙관적 락 | 보장 | 빠름 | 재시도 정책 필요 |
| 비관적 락 | 보장 | 보통 | DB 연결 점유 |
| Redis 분산 락 | 보장 | 빠름 | 락 수명 관리 필요 |

낙관적 락은 충돌이 적을 때 가장 단순하고 빨랐지만, 선착순 이벤트처럼 충돌이 많은 상황에서는 재시도가 급격히 늘었습니다. 비관적 락은 구현이 명확한 대신 DB 커넥션을 오래 점유했습니다.

## 우리가 선택한 방식

최종적으로 Redis의 원자 연산으로 입구에서 재고를 선점하고, 메시지 큐를 통해 실제 발급을 비동기로 처리했습니다. 실패한 이벤트는 보상 작업으로 재고를 되돌렸습니다.

> 락 하나로 문제를 덮기보다, 사용자가 기다려야 하는 구간과 정합성이 필요한 구간을 분리하는 것이 더 중요했습니다.

## 운영에서 반드시 확인할 것

- 락 획득 실패를 장애가 아닌 정상적인 경쟁 결과로 다루기
- 락 만료 시간보다 비즈니스 로직이 길어질 가능성 확인하기
- 재시도 횟수와 간격에 상한 두기
- 발급 수, 실패 수, 보상 수를 한 화면에서 관측하기

동시성 제어는 정답을 고르는 문제가 아니었습니다. 충돌 빈도, 응답 시간, 운영 복잡도 사이에서 현재 서비스에 맞는 균형을 찾는 일이었습니다.
