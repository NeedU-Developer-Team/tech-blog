로그는 충분히 쌓이고 있었습니다. 문제는 고객 한 명의 요청이 API 게이트웨이에서 결제 서버까지 어떻게 흘렀는지 연결해서 볼 수 없다는 점이었습니다.

## 양보다 맥락

모든 요청에 같은 `trace_id`를 넣고 로그, 메트릭, 트레이스에서 공통으로 검색할 수 있게 했습니다. 장애 알림에도 해당 시간대의 트레이스 링크를 포함했습니다.

```json
{
  "level": "ERROR",
  "trace_id": "d14f8c5a",
  "service": "payment-api",
  "event": "payment_authorization_failed",
  "order_id": "ORD-4218"
}
```

## 알림은 행동으로 이어져야 한다

CPU 사용률처럼 원인에 가까운 지표 대신, 결제 성공률과 응답 지연처럼 고객 경험에 가까운 지표를 먼저 알리도록 바꿨습니다.

- 알림마다 담당 팀과 대응 문서를 연결했습니다.
- 같은 원인의 알림은 하나로 묶었습니다.
- 확인만 하고 끝나는 알림은 삭제했습니다.
- 배포 버전과 오류율을 같은 차트에 표시했습니다.

그 결과 평균 장애 복구 시간은 42분에서 14분으로 줄었습니다. 도구를 더 많이 도입해서가 아니라, 발견부터 원인 확인까지의 이동 거리를 줄였기 때문입니다.

## 다음 단계

현재는 주요 사용자 흐름에 SLO를 정의하고 있습니다. 시스템이 살아 있는지가 아니라, 사용자가 약속한 경험을 얻고 있는지를 기준으로 신뢰성을 운영하려 합니다.
