주문 테이블에 새로운 식별 체계를 추가해야 했습니다. 테이블은 이미 2억 건을 넘었고, 서비스 중단은 선택지가 아니었습니다.

## 한 번에 바꾸지 않는다

변경을 다섯 단계로 나눴습니다.

1. nullable 컬럼을 먼저 추가한다.
2. 애플리케이션에서 기존 컬럼과 새 컬럼에 이중으로 쓴다.
3. 작은 배치로 과거 데이터를 채운다.
4. 읽기 트래픽을 새 컬럼으로 점진적으로 전환한다.
5. 검증이 끝난 뒤 제약 조건을 적용한다.

각 단계는 독립적으로 되돌릴 수 있어야 했습니다. 배포와 데이터 변경을 한 번에 묶지 않은 이유입니다.

## 백필은 속도보다 서비스 안정성이 먼저다

백필 워커는 한 번에 1,000건만 처리했고, 복제 지연이 기준을 넘으면 자동으로 쉬었습니다.

```sql
UPDATE orders
SET new_order_key = CONCAT('ORD-', id)
WHERE id > :cursor
  AND id <= :cursor + 1000
  AND new_order_key IS NULL;
```

작업 속도는 예상보다 느렸지만, 운영 쿼리의 p99 지연 시간은 변하지 않았습니다. 무중단 마이그레이션의 성공 기준은 빨리 끝내는 것이 아니라 고객이 변화를 느끼지 못하게 하는 것입니다.

## 검증을 코드로 남겼다

전환 전후 값을 비교하는 검증 쿼리와 대시보드를 만들었습니다. 불일치 비율이 0.001%를 넘으면 읽기 전환이 자동 중단되도록 했습니다.

이번 작업 이후 우리는 스키마 변경 템플릿을 만들었습니다. 같은 위험을 매번 새롭게 고민하지 않도록, 체크리스트와 관측 지표까지 배포 과정의 일부로 만들었습니다.
