니쥬(NeedU)는 AI와 대화를 나누면 그 대화에서 취향과 관심사를 정리하고, 친구가 선물을 고를 때 참고할 수 있는 상품리스트를 만들어 주는 서비스입니다. 사용자에게 "좋아하는 카테고리를 골라 주세요"라고 묻는 대신 일상적인 대화를 하다 자연스럽게 드러나는 단서를 모으는 것이 AI 파트의 역할입니다. 이 글은 9월 22일 첫 버전부터 10월 2일 현재 버전까지, 대화 시스템 프롬프트와 취향 추출 구조를 네 번 크게 바꾼 과정을 정리한 기록입니다. 각 단계에서 어떤 문제를 봤고, 그 문제를 프롬프트로 풀었는지 구조로 풀었는지를 중심으로 썼습니다.

먼저 전체 흐름을 표로 요약하면 다음과 같습니다. 프롬프트 길이는 공백과 줄바꿈을 포함한 글자 수입니다.

| 버전 | 날짜 | 대화 프롬프트 | 추출 방식 | 해결하려던 문제 |
| --- | --- | --- | --- | --- |
| v1 목표 기반 질문 | 9/22 | 535자, 12줄 | 단일 모델이 칸까지 결정 | 첫 구현 |
| v2 수다형 | 9/29 | 2,257자, 65줄 | 최근 4턴 문맥, 항목 단위 검증 | 설문 같은 대화, 짧은 답 추출 실패 |
| v3 관심사와 취향 분리 | 9/29 | 2,569자, 72줄 | 취향에 측면(aspect)과 대상(target) 부여 | 관심사만 쌓이고 취향은 안 나옴 |
| v4 판단 모델 도입 | 10/1 | 2,486자, 70줄 | 후보 추출 + 판단 모델 + 코드 | 싫다는 대상이 관심사로 저장됨 |
| v5 companion | 10/2 | 776자, 24줄 | v4 유지 | 모든 턴이 질문으로 끝나는 대화 |

## 문제 상황: 질문지를 채우는 대화

첫 버전은 대화를 목표(goal) 단위로 나눴습니다. 관심사 찾기(INTEREST), 싫어하는 것 확인(DISLIKE), 자주 쓰는 물건(GEAR), 한 주제 깊게 듣기(DEEPEN) 같은 목표가 있고, 코드가 이번 턴의 목표를 고르면 그 목표에 맞는 지시문을 시스템 메시지로 붙였습니다.

```python
GOAL_INSTRUCTIONS = {
    ConversationGoal.INTEREST: (
        "최근 주말이나 저녁에 실제로 한 일을 물어 즐기는 대상이나 직접 하는 활동을 알아본다.",
        "최근에 시간 가는 줄 모르고 했던 일이나 새로 시작한 일을 물어본다.",
        ...
    ),
    ConversationGoal.GEAR: (
        "이미 나온 활동과 연결해 자주 쓰는 물건에서 중요하게 보는 속성 하나를 묻는다.",
        ...
    ),
}

messages.append({"role": "system", "content": f"이번 응답 목표는 {goal.value}이다. {instruction}"})
```

추출도 같은 목표를 기준으로 동작했습니다. 추출 모델은 사용자의 마지막 발화 한 줄과 직전 AI 발화만 보고, "현재 목표의 허용 field" 안에서 항목을 뽑은 뒤 `goalAssessment`로 목표를 달성했는지까지 스스로 판정했습니다.

구조는 깔끔했지만 유저 테스트와 대화 로그에서 세 가지 문제가 드러났습니다.

1. 대화가 설문처럼 느껴졌습니다. 시스템 프롬프트에 "설문처럼 들리는 질문은 피한다"고 적어 두었지만, 매 턴 목표가 "속성 하나를 묻는다"였기 때문에 결국 "주로 어떤 기준으로 고르세요?" 같은 질문이 나왔습니다.
2. 짧은 답에서 취향이 추출되지 않았습니다. "산책이요"처럼 답하면 직전 질문과 합쳐야 의미가 생기는데, 추출 모델은 마지막 발화만 근거(evidence)로 쓸 수 있었습니다. 앞 턴에서 이어지는 답도 마찬가지였습니다.
3. 추출 결과 중 항목 하나만 형식이 틀려도 그 턴 전체가 버려졌습니다. JSON 스키마 검증을 응답 단위로 했기 때문입니다.

〔수치 필요: 유저 테스트 인원, 테스트 방식, 대표 피드백 문장 1~2개〕

## 해결 과정

## 1단계: 목표를 참고 방향으로 낮추고 수다형으로 다시 쓰기

v2에서는 시스템 프롬프트를 처음부터 다시 썼습니다. 역할 정의를 "취향 발견을 돕는 대화 상대"에서 "편하게 수다를 떠는 대화 상대"로 바꾸고, 규칙을 대화 방식, 피하는 것, 말투, 안전으로 나눴습니다. 가장 효과가 컸던 것은 나쁜 응답과 좋은 응답을 짝지어 넣은 예시였습니다. 규칙만 있을 때 모델은 "~하셨군요"로 사용자의 말을 되풀이하고 일반론으로 정리한 뒤 다음 주제로 넘어가는 패턴을 반복했는데, 이 패턴을 그대로 나쁜 예로 보여 주는 방식을 택했습니다. 〔확인 필요: 예시 추가 후 되풀이 패턴이 실제로 줄었는지, 줄었다면 대략 어느 정도인지〕

```text
[예시] 분위기 참고용이며 예시 문장을 그대로 쓰지 않는다.
사용자: 요즘 자기 전에 게임 한 판씩 해요
나쁜 응답: 게임을 즐기시는군요. 주로 어떤 장르의 게임을 선호하세요?
좋은 응답: 한 판만 하고 자는 게 제일 어렵다고들 하던데, 그게 잘 지켜져요?
사용자: 주말에 부모님 댁 다녀왔어요
나쁜 응답: 가족들 만나고 오셨군요. 오랜만에 뵈면 반갑지만 몸은 좀 피곤하기도 하죠.
좋은 응답: 부모님 댁 가면 꼭 하고 오는 게 있어요?
```

목표 지시문은 "이번 응답 목표는 X이다"에서 "이번 응답의 참고 방향"으로 바꾸고, 사용자가 새 이야기를 꺼냈으면 그 이야기를 우선하라고 명시했습니다. 같은 목표가 여러 번 돌아올 때 같은 문구만 반복되지 않도록 지시문 후보를 순환시켰고, 첫인사가 매번 "요즘 어떻게 지내세요?"로 굳지 않도록 세션마다 소재 하나를 무작위로 골라 현재 요일과 시간대와 함께 넘겼습니다.

추출 쪽은 세 가지를 바꿨습니다.

- 최근 대화 8개 메시지(사용자 발화 기준 4턴)를 함께 넘기고, 그 안의 사용자 발화를 근거로 쓸 수 있게 했습니다. AI 메시지는 해석용 문맥으로만 쓰고 근거로는 쓰지 못하게 막았습니다.
- 모델이 목표 달성 여부를 판정하던 `goalAssessment`를 없애고, "딱히 없어요"처럼 해당하는 게 없다고 답했는지만 `noneAnswer`로 받았습니다. 목표 달성 판정은 코드로 옮겼습니다.
- 응답 전체가 아니라 항목 단위로 검증해서 틀린 항목만 버렸습니다.

프롬프트에는 "행동과 생각에서 읽히는 신호"라는 절을 새로 넣었습니다. 사용자가 취향을 직접 말하는 경우는 드물어서, 행동에 만족이나 반복이나 일부러 한 선택이 붙어 있을 때만 추론으로 추출하도록 기준을 세웠습니다.

| 발화 | 추출 결과 | 이유 |
| --- | --- | --- |
| 어제 친구랑 카페 갔어요 | 없음 | 행동만 있고 선호 표현이 없음 |
| 구석 자리가 조용해서 두 시간이나 있었어요 | 카페, inferred | 일부러 머문 선택 |
| 주말엔 보통 동네 한 바퀴 뛰어요 | 러닝(hobbies), explicit | 반복 행동을 직접 말함 |
| 하루 비면 한강 가서 자전거 타고 싶어요 | 한강 자전거, confidence 0.5 | 희망은 낮은 신뢰도로만 |

이 단계에서 대화 프롬프트는 535자에서 2,257자로, 추출 프롬프트는 1,253자에서 2,735자로 늘었습니다. 대화 히스토리도 12개에서 18개 메시지로 늘렸습니다.

## 2단계: 관심사와 취향을 나누기

v2로 대화는 부드러워졌지만 쌓이는 데이터를 보니 "캠핑", "커피", "등산" 같은 관심사 이름만 늘어나고 있었습니다. 선물을 고르는 친구에게 필요한 것은 캠핑을 좋아한다는 사실보다 혼자 조용한 곳으로 가는 캠핑을 좋아하는지, 장비는 무채색을 고르는지 같은 정보입니다.

그래서 관심사(interests, hobbies)와 취향(preferences)의 정의를 프롬프트에서 분리했습니다. 관심사는 "무엇에 관심이 있는가"이고 명사나 행위로 씁니다. 취향은 "그 안에서 어떤 것을 더 좋아하는가"이고 대상과 합친 구로 씁니다.

```text
- 음악 → 잔잔한 음악
- 커피 → 산미 적고 고소한 커피
- 여행 → 사람 적고 자연 많은 곳
- 전자기기 → 가볍고 단순한 디자인
```

취향 항목에는 측면(aspect) 하나와 그 취향이 붙은 관심사(target)를 함께 남기게 했습니다. aspect는 attribute(모양, 스타일), sensory(맛, 향, 소리), situation(때와 장소), criterion(고르는 기준), motive(이유) 다섯 가지입니다. 이 구분은 추천 쪽에서 바로 쓰였습니다. situation 취향은 사용 공간을 찾는 보조 쿼리로, attribute와 sensory와 criterion 취향은 상품 설명과의 유사도 가산으로 들어갑니다.

같은 날 대화 쪽도 하나 손봤습니다. v2 프롬프트에 "사용자가 신나서 이야기하는 주제에 오래 머문다"고 적어 두었더니, 등산 이야기가 나오면 산 이름, 코스, 장비, 같이 간 사람을 차례로 묻다가 대화가 끝나 버렸습니다. 새 관심사가 나오지 않은 연속 턴 수를 세션에 저장하고, 2턴을 넘기면 방금 이야기를 연결 고리로 삼아 다른 생활 영역으로 건너가라는 지시로 바꿨습니다.

```python
def record_interest_progress(state, known_values, accepted):
    # 취향(preferences)은 기존 관심사를 더 자세히 들은 것이라 새 관심사로 치지 않는다.
    found_new = any(
        signal.link_role == LinkRole.QUERY and normalize_text(signal.value) not in known_values
        for signal in accepted
    )
    state.turns_since_new_interest = 0 if found_new else state.turns_since_new_interest + 1
```

## 3단계: 칸을 고르는 일을 추출 모델에서 떼어 내기

v3까지는 추출 모델 하나가 발화에서 대상을 찾고, 그 대상이 좋은지 싫은지 판단하고, 어느 칸(field)에 넣을지까지 한 번에 정했습니다. 그러다 보니 "러닝은 숨차서 싫어요"의 러닝이 관심사로 들어가는 오류가 나왔습니다. 같은 대상이 좋아하는 칸과 싫어하는 칸에 동시에 남는 경우도 있었습니다. 추천에서 싫어하는 것은 상품을 빼는 안전 정보로 쓰이기 때문에 이 오류는 비용이 큽니다.

프롬프트 규칙을 더 넣는 방법도 검토했지만, 추출 프롬프트는 이미 3,900자를 넘은 상태였습니다. 대상 찾기, 태도 판단, 칸 고르기를 한 번의 생성에 맡기는 한 규칙을 늘려도 같은 오류가 다시 나올 수 있다고 보고 역할을 셋으로 나눴습니다.

```text
사용자 발화
 ├─ 응답 모델: 니쥬의 답장 생성 (아래 과정과 동시에 실행)
 └─ 추출 모델: 발화에 나온 대상을 후보로 최대 8개 추출 (좋고 싫음은 판단하지 않음)
     └─ 판단 모델(Jev): 후보마다 태도, 취향·관심사 여부, 분류, 구체성을 확률로 응답
         └─ 코드: 태도와 대상 종류로 저장할 칸을 결정, 기준 미달은 버림
```

추출 모델의 프롬프트(CANDIDATE_SYSTEM)는 "놓치지 않는 것이 중요하다. 애매한 표현도 후보로 넣으면 다음 단계가 거른다"로 시작합니다. 정밀도는 판단 모델과 코드가 책임지고, 추출 모델은 재현율만 책임지게 한 것입니다.

판단 모델로는 TypeSafe의 Jev를 썼습니다. 생성 모델이 아니라 선택지 중 하나를 확률로 고르는 판단 전용 모델이라 출력 형식이 깨질 일이 없고, 도입 전 한국어 태도 판정 테스트에서 17문항 중 15문항을 맞혔습니다. 평균 응답 시간은 0.3초, 호출당 비용은 약 0.00003달러였습니다. Jev는 영어 위주로 학습돼 있고 선택지를 글자 그대로 읽기 때문에 선택지 설명은 영어로 조건을 분명하게 적었습니다.

```python
_STANCE_CRITERIA = {
    Stance.LIKE: "The user personally likes, enjoys, is into, or regularly chooses to do it now",
    Stance.DISLIKE: "The user personally dislikes it, finds it unpleasant or bothersome, or wants to avoid it",
    Stance.NOT_A_SUBJECT: (
        "It is a reason, feeling, or bodily reaction the user mentioned, such as being out of "
        "breath or finding something tedious, not a thing or activity"
    ),
    ...
}
```

칸은 코드가 정합니다. 태도가 dislike면 대상 종류와 관계없이 싫어하는 것으로 가고, like인 활동은 습관으로 하는지에 대한 판단이 0.5 이상일 때만 취미(hobbies)로, 아니면 관심사로 갑니다. 태도 확신이 0.6보다 낮으면 저장하지 않습니다. 다만 취향은 "보통 혼자 봐요"처럼 습관으로 드러나 확신이 낮게 나오는 경향이 있어서, 취향 축까지 분류된 후보는 0.5를 기준으로 받았습니다.

```python
def _field_for(candidate, stance, material, answers, index, *, has_taste_axis=False):
    if stance == Stance.CANNOT_USE:
        return TasteField.CONSTRAINTS, None
    if material == Material.NOT_MATERIAL:
        return None, None
    if stance == Stance.DISLIKE:
        return TasteField.DISLIKES, None
    ...
```

이 구조로 바꾸면서 관심사 분야 22개와 취향 축(시각, 감각, 상황, 소비 기준, 동기)을 분류표(taxonomy)로 정의하고, 추출 프롬프트와 판단 질문과 추천 쿼리가 같은 분류표를 보게 했습니다. 프로필 병합에서는 한 턴에 같은 대상이 선호와 비선호로 함께 나오면 비선호를 우선하고, 이전에 싫다고 한 대상은 이번 발화에서 명시적으로 좋다고 할 때만 선호로 바꾸도록 했습니다. 판단 모델 설정이 없으면 v3의 추출 방식으로 그대로 동작하게 남겨 두었습니다.

〔수치 필요: 같은 대화 로그 N개에서 비선호가 관심사로 잘못 저장된 건수, v3 대비 v4〕

## 4단계: 규칙 목록을 지우고 성격 소개글로 바꾸기

v4까지 오면서 대화는 덜 딱딱해졌지만 다른 문제가 보였습니다. 모든 턴이 "짧은 반응 + 질문 하나"로 끝났습니다. v2에서 대화가 멈추지 않도록 "응답은 항상 질문 하나로 끝낸다"고 적었고, 응답 가드도 물음표 뒤에 붙은 문장을 잘라 냈기 때문에 구조적으로 모든 턴이 질문이었습니다. 질문이 아무리 자연스러워도 열 턴 연속으로 질문을 받으면 사용자는 인터뷰를 받는 느낌을 받습니다.

또 하나는 응답 모델이 2,500자 가까운 규칙을 지키느라 대화 흐름을 놓치는 경우였습니다. 응답 모델로 작고 빠른 모델(Gemini 3.5 Flash-Lite)을 쓰고 있어서, 지시가 많을수록 방금 사용자가 한 말보다 규칙을 맞추는 쪽으로 응답이 기울었습니다.

v5(companion)에서는 접근을 바꿨습니다. 시스템 프롬프트에서 규칙 목록을 지우고 니쥬가 어떤 친구인지를 풀어 쓴 소개글로 바꿨습니다. 금지 규칙은 꼭 필요한 것만 말투 안에 녹였고, 안전 규칙만 별도 블록으로 남겼습니다. 길이는 2,486자에서 776자로 줄었습니다.

```text
당신은 "니쥬"예요. 사용자랑 편하게 수다 떠는 친구 같은 존재예요.

니쥬는 이 사람이 어떤 사람인지가 제일 궁금해요.
대단한 인생관보다는 평소 사는 모습이요. 아침은 챙겨 먹는지, 퇴근하고 뭘 하면 하루가 풀리는지,
쉬는 날엔 나가는 쪽인지 집에 있는 쪽인지, 사소한 데서 뭘 꼭 챙기는 사람인지 같은 것들이요.
...
매번 질문으로 끝낼 필요는 없고, 물을 땐 친구한테 묻듯 하나만 가볍게 물어요.
```

대신 매 턴 "무엇을 알아낼지(goal)"를 정하던 자리에 "어떻게 반응할지(move)"를 정하는 짧은 메모를 붙였습니다. move는 여섯 가지입니다.

| move | 하는 일 | 고르는 조건 |
| --- | --- | --- |
| follow | 반응하고 궁금한 것 하나 묻기 | 기본값, 사용자가 되물었을 때 |
| add | 묻지 않고 반응과 니쥬 생각만 말하기 | 질문으로 끝난 응답이 2번 이어졌을 때 |
| reflect_back | 들은 단서로 인상을 짐작하고 맞는지 묻기 | 단서가 충분하고 에너지가 괜찮을 때 |
| bridge | 방금 이야기에서 다른 일상으로 건너가기 | 새 관심사 없이 3턴, 에너지 하락 |
| play | 둘 중 하나 고르기 놀이 | 에너지 낮은 턴 2연속 |
| return | 가장 신나 보였던 화제로 돌아가기 | 에너지 낮은 턴 2연속, 돌아갈 화제가 있을 때 |

move를 고르는 기준은 사용자 에너지입니다. 답 길이를 그 사용자의 평균 대비 비율로 보고, 웃음과 감탄 표현, 니쥬에게 되묻는지, "딱히", "글쎄" 같은 회피 표현을 더해 0~1 점수를 만듭니다. 판단 모델이 답의 깊이(대충 넘김, 사실만 답함, 이유와 감정을 말함)를 매긴 값도 30% 비중으로 섞습니다. 원래 짧게 쓰는 사람을 이탈로 오해하지 않도록 절대 길이 대신 평균 대비 비율을 쓴 것이 핵심이었습니다.

```python
def turn_energy(state, utterance, *, answer_depth=None):
    text = utterance.strip()
    score = 0.3 + 0.5 * _length_score(state, text)   # 이 사용자 평균 대비 길이
    if _LAUGHTER.search(text):
        score += 0.15
    if asks_back(text):                               # 되묻기는 대화가 재밌다는 강한 신호
        score += 0.2
    if _SHORT_AVOIDANCE.match(text) or _AVOIDANCE.search(text):
        score -= 0.35
    score = max(0.0, min(score, 1.0))
    if answer_depth is not None:
        score = 0.7 * score + 0.3 * max(0.0, min(answer_depth / 2, 1.0))
    return score
```

정보가 비어 있는 영역(아직 취향 축이 안 나왔다거나 싫어하는 것을 모른다거나)은 move를 정하는 데 쓰지 않고, bridge와 play에서 어느 화제로 갈지 고를 때 가중치로만 씁니다. 가중치는 대화 초반 0에서 후반 1로 올라갑니다. 초반에는 사용자가 하고 싶은 이야기를 따라가고, 후반으로 갈수록 빈 칸을 채우는 쪽으로 기울게 한 것입니다.

종료 조건도 바꿨습니다. 이전에는 추천에 필요한 정보가 모이면 바로 대화를 끝냈는데, 즐겁게 이야기하는 중에 끊기는 경험이 어색했습니다. 지금은 정보가 충분해도 14턴을 넘겼거나 에너지가 최고점 대비 0.2 이상 떨어졌을 때, 또는 "그만할게요" 같은 종료 의사가 있을 때만 마무리합니다. 응답 길이도 사용자 발화 길이에 맞춰 60~110자 사이에서 예산을 줍니다.

첫인사 소재도 손봤습니다. v2의 소재 10개는 대부분 "요즘 하는 것"에 몰려 있어서 첫 질문에 따라 대화 방향이 크게 갈렸습니다. 소재를 14개 생활 영역(쉬는 날, 오가는 길, 폰 속 일상, 물건과 소비, 계절 등) 38개로 늘리고, 영역을 먼저 고른 뒤 그 안에서 소재를 고르게 해서 소재가 많은 영역으로 쏠리지 않게 했습니다.

- 프롬프트 규칙으로 막을 수 있는 문제와 구조로 막아야 하는 문제를 구분하는 데 시간이 가장 많이 들었습니다. "설문처럼 묻지 말라"는 규칙은 매 턴 목표가 정보 수집인 구조에서는 지켜지지 않았고, "싫다는 대상을 관심사에 넣지 말라"는 규칙만으로는 취향과 관심사를 추출하는 구조에서는 지켜지지 않았습니다. 두 경우 모두 결정을 다른 단계로 옮기고 나서야 해결됐습니다.
- 나쁜 응답과 좋은 응답을 짝지은 예시는 규칙 문장보다 효과가 컸습니다. 반대로 작은 응답 모델에 규칙을 계속 쌓는 방식은 한계가 있었고, 이번 턴에 어떻게 반응할지는 코드가 정하고 프롬프트는 성격만 설명하는 쪽이 관리하기 쉬웠습니다. 〔확인 필요: companion 전환 후 체감이나 측정 결과 한 줄〕
- 추출을 후보 찾기와 판단으로 나누면서 각 모델에 다른 목표를 줄 수 있었습니다. 추출 모델은 재현율, 판단 모델과 코드는 정밀도를 맡고, 판단 기준값(0.6, 0.5)은 실제 대화 로그를 보며 조정할 수 있는 숫자로 코드에 남겼습니다.
- 각 단계는 설정값으로 이전 방식과 나란히 실행할 수 있게 남겨 두었습니다(`CONVERSATION_STYLE=explore | reflective | companion`). 다음 단계에서는 이 세 방식을 같은 사용자 시나리오로 비교하는 평가셋을 만들고, 추천 결과에 대한 친구의 반응을 다시 취향 신호로 넣는 피드백 루프를 붙일 계획입니다.
