안녕하세요, NeedU 프론트엔드 개발자 김주희입니다.

1편에서는 카테고리나 예산을 바꿀 때 목록이 통째로 사라지던 문제를 고쳤습니다. 새 목록이 올 때까지 이전 목록을 붙잡아 두는 방식이었습니다.

그런데 그 과정에서 숙제가 하나 남았습니다. 이전 목록을 보여 주는 동안, 화면에 그대로 남아 있는 카드들이 계속 다시 그려지고 있었습니다. 2편에서는 이 숙제를 어떻게 풀었는지 이야기해 보겠습니다.

## 화면은 그대로인데, 카드는 계속 다시 그려지고 있었습니다

1편의 개선으로 조건을 바꿔도 목록이 사라지지 않게 됐습니다. 사용자 눈에는 이전 목록이 잠깐 흐려졌다가 새 목록으로 바뀌는 것이 전부입니다.

그런데 React Profiler로 들여다보니 이야기가 달랐습니다. 조건을 바꿀 때마다 화면에 남아 있는 카드들이 하나도 빠짐없이 다시 그려지고 있었습니다. 카드에 보이는 이미지, 이름, 가격은 그대로인데도 말입니다.

![개선 전 React Profiler Flamegraph. 카테고리를 바꾼 뒤 목록 아래의 상품 카드들이 회색 빗금 없이 모두 색칠되어 있어, 화면에 남아 있는 카드가 전부 다시 그려졌음을 보여 줌](/images/2026-11-11-product-list-performance-2-card-rerender/before-cards-rendered.png "개선 전: 카테고리 1번 변경 후 다시 그려진 상품 카드들")

위 Flamegraph에서 색칠된 칸은 이번 변경에서 다시 그려진 컴포넌트입니다. 목록(`PersonalRecommendationsListContent`) 아래에 나란히 있는 상품 카드들이 모두 색칠되어 있습니다.

### 얼마나 다시 그리는지부터 셌습니다

느낌만으로는 이게 정말 문제인지 판단하기 어려웠습니다. 그래서 1편에서 만든 측정 도구(`window.__perf`)로 카드가 다시 그려지는 횟수를 직접 셌습니다.

렌더링 횟수는 React의 `<Profiler>`로 잴 수 있습니다. 다만 기본 프로덕션 빌드에서는 Profiler가 꺼져 있어서, 프로파일링 빌드(`next build --profile`)를 따로 만들어 측정했습니다. 상품 카드를 `<Profiler>`로 감싸 두면, 카드가 다시 그려질 때마다 `render:product-card:update`라는 이름으로 기록이 남습니다.

측정 시나리오는 다음과 같습니다.

1. 상품 목록에 들어가 기록을 초기화합니다.
2. 카테고리와 예산을 섞어서 다섯 번 바꿉니다.
3. 결과를 확인합니다.

내 추천 목록과 공개 상품 목록 두 화면에서 모두 쟀습니다.

| 항목 | 공개 상품 목록 | 내 추천 목록 |
|---|---|---|
| 카드 다시 그리기 (`product-card:update`) | 195회 / 13.7ms | 195회 / 13.6ms |
| 목록 다시 그리기 합계 | 19.2ms | 19.4ms |

조건을 다섯 번 바꿨을 뿐인데, 카드는 195번 다시 그려졌습니다.

시간으로 보면 13ms 남짓이라 당장 느껴질 정도는 아닙니다. 하지만 바뀐 것이 없는 카드를 다시 그리는 일은, 카드 수가 늘거나 기기가 느려지면 그대로 비용이 됩니다. 하지 않아도 되는 일이라면 하지 않는 편이 맞다고 판단했습니다.

## 목록이 그려질 때마다 카드 20개가 따라 그려졌습니다

195라는 숫자는 생각보다 단순하게 나왔습니다.

조건을 한 번 바꾸면 목록은 **두 번** 다시 그려집니다.

- ① 이전 목록을 흐리게 만들 때
- ② 새 목록이 도착해 바꿔 끼울 때

그리고 React는 기본적으로 부모가 다시 그려지면 자식도 함께 다시 그립니다. 한 페이지에 카드가 약 20개 있으니 계산은 이렇습니다.

> 카드 약 20개 × 2번 = 조건 1번에 약 39번 → 조건 5번에 195번

![개선 전 ProductCard 하나를 선택한 React Profiler. Why did this render?에 The parent component rendered가 표시되고, Rendered at에 2.9s와 3.7s 두 번이 기록됨](/images/2026-11-11-product-list-performance-2-card-rerender/before-card-why-rendered.png "개선 전: 카드가 다시 그려진 이유와 횟수")

카드 하나를 골라 보면 이유가 분명하게 나옵니다. "Why did this render?"에는 **부모 컴포넌트가 다시 그려졌기 때문**이라고 나오고, "Rendered at"에는 카테고리를 한 번 바꿨는데 2.9초와 3.7초, 두 번 다시 그려진 기록이 남아 있습니다.

![조건을 1번 바꿀 때 카드가 다시 그려지는 횟수. 개선 전에는 흐림 시작과 새 목록 도착 때 목록이 두 번 렌더링되며 그때마다 카드 약 20개를 다시 그려 1번에 약 39회, 5번에 195회가 된다. 개선 후에는 두 번 모두 카드에 보이는 값이 같아 건너뛰고, 새 상품만 처음 그린다](/images/2026-11-11-product-list-performance-2-card-rerender/card-rerender-flow.png "조건을 1번 바꿀 때 카드가 다시 그려지는 횟수")

그렇다면 카드를 `React.memo`로 감싸면 될까요? `memo`는 넘겨받은 값(props)이 이전과 같으면 다시 그리기를 건너뛰는 기능입니다. 하지만 코드를 살펴보니 `memo`만으로는 부족한 이유가 두 가지 있었고, 측정 방식에도 고칠 점이 하나 있었습니다.

### 목록이 그려질 때마다 상품 객체를 새로 만들어 넘기고 있었습니다

공개 상품 목록은 카드에 상품 정보를 이렇게 넘기고 있었습니다.

```tsx
<ProductCard
  product={{ name: product.name, price: product.price /* ...나머지 필드 */ }}
/>
```

`{{ ... }}`는 목록이 그려질 때마다 **새 객체**를 만듭니다. 안에 든 값은 같아도 객체 자체는 매번 다릅니다. `memo`는 기본적으로 props를 `===`로 비교하기 때문에, 이렇게 넘기면 항상 "바뀌었다"고 판단해 다시 그리게 됩니다.

### 예산만 바꿔도, 같은 상품이 새 객체로 도착했습니다

두 번째 원인은 조금 더 숨어 있었습니다. 공개 상품 목록처럼 새 객체를 만들지 않고 받은 상품을 그대로 넘기는 내 추천 목록에서도, 새 목록이 도착할 때마다 카드가 다시 그려졌습니다.

예산을 10만 원에서 9만 원으로 줄이는 상황을 예로 들어 보겠습니다. 5만 원짜리 "향수 A"는 두 조건에 모두 해당하니, 줄이기 전 목록에도 줄인 뒤 목록에도 들어 있습니다. 화면에서도 같은 자리에 그대로 남아 있습니다.

```js
// 예산 10만 원 목록에 있던 향수 A
const before = { name: "향수 A", price: 50000 };

// 예산 9만 원 목록에 새로 도착한 향수 A
const after = { name: "향수 A", price: 50000 };

before === after; // false: 내용은 같지만 서로 다른 객체
```

이름도 가격도 같지만, 서버에서 새 응답을 받아 만든 **다른 객체**입니다. `memo`는 `===`로 비교하니 "바뀌었다"고 판단하고 카드를 다시 그립니다.

사실 TanStack Query에는 이런 낭비를 막아 주는 **structural sharing**이라는 기능이 있습니다. 새 응답을 받으면 이전 데이터와 하나씩 비교해서, 바뀌지 않은 부분은 이전 객체를 그대로 다시 씁니다. 이 기능이 동작하면 위의 `before === after`가 `true`가 됩니다.

문제는 이 비교가 **같은 쿼리 키 안에서만** 일어난다는 점이었습니다. 1편에서 조건을 쿼리 키에 넣었기 때문에, 예산을 바꾸면 쿼리 키도 달라집니다.

```ts
["personal-recommendations", { category, maxPrice: 100000 }] // 이전 목록
["personal-recommendations", { category, maxPrice: 90000 }]  // 새 목록
```

TanStack Query 입장에서 둘은 서로 다른 데이터입니다. 그래서 비교하지 않고 따로 저장하고, 향수 A처럼 두 목록에 모두 있는 상품도 새 객체로 넘어옵니다. 조건별로 결과를 나눠 저장하려던 1편의 설계가, 여기서는 객체 재사용을 막은 셈입니다.

정리하면, 목록이 다시 그려지는 두 순간에 카드가 받는 객체가 달랐습니다.

| 목록이 다시 그려지는 순간 | 카드가 받는 상품 객체 | 기본 `memo`로 막을 수 있나 |
|---|---|---|
| ① 이전 목록을 흐리게 만들 때 | 이전 목록의 객체 그대로 | 막을 수 있음 |
| ② 새 목록이 도착했을 때 | 같은 상품도 새 객체 | 막을 수 없음 |

`memo`만 붙이면 ①만 막고 ②는 그대로 남습니다. 새 목록이 도착하는 순간까지 막으려면, 객체가 같은지가 아니라 **카드에 보이는 값이 같은지**를 비교해야 했습니다.

### 측정 위치에도 함정이 있었습니다

하나 더 걸리는 부분이 있었습니다. 지금은 측정용 `<Profiler>`가 카드 **바깥**에서 카드를 감싸고 있었습니다.

```tsx
<PerfProfiler id="product-card">
  <ProductCard product={product} />
</PerfProfiler>
```

이 구조에서는 카드에 `memo`를 붙여도, 바깥의 Profiler는 목록과 함께 다시 그려집니다. 그러면 카드는 실제로 건너뛰었는데 update로 기록될 수 있습니다.

고친 효과를 숫자로 확인하려면 Profiler를 `memo` **안쪽**으로 옮겨야 했습니다.

## 바로 memo만 붙이지는 않았습니다

원인을 정리하고 나니, 고치는 방법도 여러 가지가 보였습니다. 방법을 고르는 기준은 하나였습니다.

> ① 흐림 시작과 ② 새 목록 도착, 두 번의 렌더링을 모두 막을 수 있는가

### memo만 붙이기: 절반만 막습니다

가장 먼저 떠오르는 방법은 카드를 `memo`로 감싸고, 매번 새 객체를 만들던 코드를 받은 상품을 그대로 넘기도록 고치는 것입니다. 가장 단순하고 고칠 곳도 적습니다.

하지만 앞의 표에서 봤듯이, 이 방법으로는 ①만 막을 수 있습니다. 새 목록이 도착하면 같은 상품도 새 객체로 오기 때문에 ②는 그대로 남습니다.

### React Compiler: 범위는 크고, 새 객체 문제는 그대로입니다

React Compiler는 빌드할 때 컴포넌트와 값을 자동으로 기억하도록 코드를 바꿔 주는 도구입니다. `memo`를 일일이 붙이지 않아도 된다는 점이 끌렸습니다.

하지만 카드 하나를 고치려고 프로젝트 전체의 빌드 설정을 바꾸는 것은 범위가 너무 컸습니다. 무엇보다 컴파일러도 결국 "같은 객체인지"로 판단합니다. 쿼리 키가 바뀌어 새로 만들어진 객체는 컴파일러에게도 다른 값이라, ②를 막지 못합니다.

### 보이는 값으로 비교하기: 두 가지 방법이 남았습니다

②까지 막으려면 "객체가 같은지"가 아니라 **"카드에 보이는 값이 같은지"**로 판단해야 합니다. 그렇게 만드는 방법은 두 가지였습니다.

**첫 번째는 비교 함수를 직접 만드는 방법입니다.** `memo`는 두 번째 인자로 비교 함수를 받을 수 있습니다. 여기에 이름, 가격처럼 카드에 보이는 값만 하나씩 비교하는 함수를 넘깁니다. 카드를 쓰는 쪽은 지금처럼 `product` 객체 하나만 넘기면 됩니다.

```tsx
<ProductCard product={product} detailHref={detailHref} />
```

**두 번째는 값을 하나씩 나눠 넘기는 방법입니다.** `product` 객체 대신 이름, 가격 등을 각각 props로 넘깁니다. 문자열과 숫자는 값이 같으면 `===`로도 같다고 나오니, 기본 `memo`만으로 충분합니다.

```tsx
<ProductCard
  name={product.name}
  category={product.category}
  price={product.price}
  /* ...3개 더 */
/>
```

두 방법은 효과가 같습니다. 차이는 코드를 고치는 범위와, 나중에 카드를 고칠 때의 안전함에 있었습니다.

| 비교 | 비교 함수를 직접 만들기 | 값을 하나씩 나눠 넘기기 |
|---|---|---|
| 고치는 곳 | 대부분 카드 컴포넌트 안 | 카드와, 카드를 쓰는 두 목록 모두 |
| 카드를 쓰는 코드 | `product={product}` 그대로 | props 6개를 나열해 길어짐 |
| 카드에 보여 줄 값을 추가할 때 | 비교 함수에도 직접 추가해야 함. 빠뜨려도 오류가 나지 않음 | props 타입에만 추가하면 됨. 빠뜨리면 타입 오류로 바로 드러남 |

### 비교 함수를 직접 만들기로 했습니다

이번 작업의 목표는 "다시 그리지 않아도 되는 카드를 다시 그리지 않기"였습니다. 카드를 쓰는 쪽 코드는 최대한 건드리고 싶지 않았습니다. 그래서 변경이 카드 안에서 끝나는 **비교 함수를 직접 만드는 방법**을 골랐습니다.

값을 추가할 때 비교 함수에서 빠뜨릴 수 있다는 부담은, 비교 함수 바로 위에 주의 문구를 남겨 두는 것으로 보완했습니다.

## 보이는 값이 같으면 건너뛰도록 바꿨습니다

바꾼 곳은 세 군데입니다.

### 1. 카드에 보이는 값만 비교하기

카드에 보이는 값만 골라 비교하는 함수를 만들고, `memo`에 함께 넘겼습니다.

```tsx
// 카드에 표시하는 상품 필드를 추가하면 이 비교에도 함께 추가해야 함
function areProductCardPropsEqual(prev, next) {
  return (
    prev.detailHref === next.detailHref &&
    prev.product.name === next.product.name &&
    prev.product.price === next.product.price
    // ...category, productImageUrl, purchaseUrl도 같은 방식으로 비교
  );
}

export default memo(ProfiledProductCard, areProductCardPropsEqual);
```

이제 상품 객체가 새로 만들어져도, 이름·카테고리·가격·이미지·구매 링크·상세 링크가 모두 같으면 카드는 다시 그리지 않습니다.

### 2. 측정용 Profiler를 memo 안쪽으로 옮기기

카드가 다시 그리기를 건너뛰면 Profiler도 함께 건너뛰어서, 실제로 다시 그린 경우만 기록됩니다.

```tsx
// 렌더링을 건너뛴 카드는 update로 기록되지 않도록 Profiler를 memo 안쪽에 둠
function ProfiledProductCard(props) {
  return (
    <PerfProfiler id="product-card">
      <ProductCardContent {...props} />
    </PerfProfiler>
  );
}
```

### 3. 목록에서 새 객체 만들지 않기

공개 상품 목록에서 매번 새 객체를 만들던 코드를 지우고, 받은 상품을 그대로 넘기도록 정리했습니다.

```tsx
<ProductCard key={product.recommendationId} product={product} detailHref={detailHref} />
```

개선 전 Flamegraph와 같은 장면입니다. 목록은 여전히 다시 그려지지만, 그 아래 `ProfiledProductCard (Memo)` 카드들은 모두 회색 빗금으로 바뀌었습니다. 회색 빗금은 다시 그리지 않고 건너뛰었다는 뜻입니다.

숫자를 보며 생길 수 있는 궁금증 두 가지도 짚고 넘어가겠습니다.

**새로 들어온 상품도 있는데, 왜 0회일까요?** 새로 들어온 상품의 카드는 "다시 그리기(update)"가 아니라 "처음 그리기(mount)"로 기록됩니다. 이번에 줄인 것은 이미 화면에 있던 카드를 다시 그리는 일입니다. 새 카드를 처음 그리는 일은 원래 해야 하는 일이라 그대로 남아 있습니다.

**조건 변경 전체 시간은 왜 1~2ms밖에 줄지 않았을까요?** 측정용 목업 데이터는 실제 서버처럼 보이도록 응답을 일부러 150ms 늦게 돌려줍니다. 약 160ms 중 150ms가 응답을 기다리는 시간이고, 이번 작업은 그 뒤의 렌더링만 줄였습니다. 그래서 이번 작업의 효과는 전체 시간보다 렌더링 횟수와 렌더링 시간으로 보는 것이 맞다고 판단했습니다.

### 공짜는 아니었습니다

이번에도 대가는 있었습니다. 비교 함수는 "카드에 보이는 값이 무엇인지"를 사람이 직접 적어 둔 목록입니다.

나중에 카드에 할인율을 새로 표시하게 됐는데, 비교 함수에 추가하는 것을 잊으면 어떻게 될까요? 타입 오류는 나지 않습니다. 대신 할인율만 바뀐 경우에는 카드가 다시 그려지지 않아, 화면에 이전 할인율이 그대로 남습니다.

그래서 비교 함수 바로 위에 "필드를 추가하면 여기도 함께 고쳐야 한다"는 주석을 남겼습니다. 이후 상품 목록 작업에서도 카드를 건드릴 때마다 이 부분을 따로 확인하고 있습니다. 값을 하나씩 나눠 넘기는 방법이었다면 타입 오류로 막을 수 있었던 문제라, 이번 선택의 대가로 안고 가기로 했습니다.
