안녕하세요, 주라 팀 NeedU 프론트엔드 Juno 입니다!

1편에서는 카테고리나 예산을 바꿀 때 목록이 통째로 사라지던 문제를, 새 목록이 올 때까지 이전 목록을 붙잡아 두는 방식으로 고쳤습니다. 그런데 그 과정에서 숙제가 하나 남았습니다. 이전 목록을 보여 주는 동안, 화면에 그대로 남아 있는 카드들이 계속 다시 그려지고 있었습니다. 2편에서는 이 숙제를 어떻게 풀었는지 이야기해 보겠습니다.

## 화면은 그대로인데, 카드는 계속 다시 그려지고 있었습니다

1편의 개선으로 조건을 바꿔도 목록이 사라지지 않게 됐습니다. 사용자 눈에는 이전 목록이 잠깐 흐려졌다가 새 목록으로 바뀌는 것이 전부입니다.

그런데 React Profiler로 들여다보니 이야기가 달랐습니다. 조건을 바꿀 때마다 화면에 남아 있는 카드들이 하나도 빠짐없이 다시 그려지고 있었습니다. 카드에 보이는 이미지, 이름, 가격은 그대로인데도 말입니다.

![개선 전 React Profiler Flamegraph. 카테고리를 바꾼 뒤 목록 아래의 상품 카드들이 회색 빗금 없이 모두 색칠되어 있어, 화면에 남아 있는 카드가 전부 다시 그려졌음을 보여 줌](/images/2026-11-11-product-list-performance-2-card-rerender/before-cards-rendered.png "개선 전: 카테고리 1번 변경 후 다시 그려진 상품 카드들")

위 Flamegraph에서 색칠된 칸은 이번 변경에서 다시 그려진 컴포넌트입니다. 목록(`PersonalRecommendationsListContent`) 아래에 나란히 있는 상품 카드들이 하나도 빠짐없이 색칠되어 있습니다.

### 얼마나 다시 그리는지부터 셌습니다

느낌만으로는 이게 정말 문제인지 판단하기 어려웠습니다. 그래서 1편에서 만든 측정 도구(`window.__perf`)로 카드가 다시 그려지는 횟수를 직접 셌습니다.

렌더링 횟수를 재려면 React의 `<Profiler>`가 프로덕션 빌드에서도 동작해야 합니다. 기본 프로덕션 빌드에서는 Profiler가 꺼져 있기 때문에, 프로파일링 빌드(`next build --profile`)를 따로 만들어 측정했습니다. 상품 카드를 `<Profiler>`로 감싸 두면, 카드가 다시 그려질 때마다 `render:product-card:update`라는 이름으로 기록이 남습니다.

측정 시나리오는 간단합니다. 상품 목록에 들어가 기록을 초기화하고, 카테고리와 예산을 섞어서 다섯 번 바꾼 뒤 결과를 확인했습니다. 내 추천 목록과 공개 상품 목록 두 화면에서 모두 쟀습니다.

| 항목 | 공개 상품 목록 | 내 추천 목록 |
|---|---|---|
| 카드 다시 그리기 (`product-card:update`) | 195회 / 13.7ms | 195회 / 13.6ms |
| 목록 다시 그리기 합계 | 19.2ms | 19.4ms |

조건을 다섯 번 바꿨을 뿐인데, 카드는 195번 다시 그려졌습니다. 시간으로 보면 13ms 남짓이라 당장 느껴질 정도는 아닙니다. 하지만 바뀐 것이 없는 카드를 다시 그리는 일은, 카드 수가 늘거나 기기가 느려지면 그대로 비용이 됩니다. 하지 않아도 되는 일이라면 하지 않는 편이 맞다고 판단했습니다.

## 목록이 그려질 때마다 카드 20개가 따라 그려졌습니다

195라는 숫자는 생각보다 단순하게 나왔습니다.

조건을 한 번 바꾸면 목록은 **두 번** 다시 그려집니다. 한 번은 이전 목록을 흐리게 만들 때, 또 한 번은 새 목록이 도착해 바꿔 끼울 때입니다. 그리고 React는 기본적으로 부모가 다시 그려지면 자식도 함께 다시 그립니다. 한 페이지에 카드가 약 20개 있으니, 조건 한 번에 20개 × 2번으로 약 39번, 다섯 번이면 195번이 됩니다.

![개선 전 ProductCard 하나를 선택한 React Profiler. Why did this render?에 The parent component rendered가 표시되고, Rendered at에 2.9s와 3.7s 두 번이 기록됨](/images/2026-11-11-product-list-performance-2-card-rerender/before-card-why-rendered.png "개선 전: 카드가 다시 그려진 이유와 횟수")

카드 하나를 골라 보면 이유가 분명하게 나옵니다. "Why did this render?"에는 **부모 컴포넌트가 다시 그려졌기 때문**이라고 나오고, "Rendered at"에는 카테고리를 한 번 바꿨는데 2.9초와 3.7초, 두 번 다시 그려진 기록이 남아 있습니다.

![조건을 1번 바꿀 때 카드가 다시 그려지는 횟수. 개선 전에는 흐림 시작과 새 목록 도착 때 목록이 두 번 렌더링되며 그때마다 카드 약 20개를 다시 그려 1번에 약 39회, 5번에 195회가 된다. 개선 후에는 두 번 모두 카드에 보이는 값이 같아 건너뛰고, 새 상품만 처음 그린다](/images/2026-11-11-product-list-performance-2-card-rerender/card-rerender-flow.png "조건을 1번 바꿀 때 카드가 다시 그려지는 횟수")

그렇다면 카드를 `React.memo`로 감싸면 될까요? `memo`는 넘겨받은 값(props)이 이전과 같으면 다시 그리기를 건너뛰는 기능입니다. 하지만 코드를 살펴보니 `memo`만으로는 부족한 이유가 두 가지 있었습니다.

### 이유 1. 매번 새 객체를 만들어 넘기고 있었습니다

공개 상품 목록은 카드에 상품 정보를 이렇게 넘기고 있었습니다.

```tsx
<ProductCard
  product={{ name: product.name, price: product.price /* ...나머지 필드 */ }}
/>
```

`{{ ... }}`는 목록이 그려질 때마다 **새 객체**를 만듭니다. 안에 든 값은 같아도 객체 자체는 매번 다릅니다. `memo`는 기본적으로 props를 `===`로 비교하기 때문에, 이렇게 넘기면 항상 "바뀌었다"고 판단해 다시 그리게 됩니다.

### 이유 2. 조건이 바뀌면 같은 상품도 새 객체로 옵니다

두 번째 이유는 조금 더 숨어 있었습니다.

1편에서 TanStack Query를 도입하면서 조건(카테고리, 예산)을 쿼리 키로 삼았습니다. TanStack Query에는 같은 쿼리 키로 다시 요청했을 때 바뀌지 않은 데이터는 이전 객체를 그대로 재사용하는 기능(structural sharing)이 있습니다. 그런데 조건이 바뀌면 쿼리 키도 바뀝니다. 서로 다른 쿼리의 결과이니, 예산을 조금 줄여서 같은 상품이 그대로 남아 있더라도 상품 객체는 모두 새로 만들어집니다.

즉, 이전 목록을 흐리게 만들 때의 렌더링은 `memo`로 막을 수 있어도, 새 목록이 도착했을 때의 렌더링은 기본 `memo`로는 막을 수 없었습니다.

### 측정 위치에도 함정이 있었습니다

하나 더 걸리는 부분이 있었습니다. 지금은 측정용 `<Profiler>`가 카드 **바깥**에서 카드를 감싸고 있었습니다.

```tsx
<PerfProfiler id="product-card">
  <ProductCard product={product} />
</PerfProfiler>
```

이 구조에서는 카드에 `memo`를 붙여 다시 그리기를 건너뛰어도, 바깥의 Profiler 자체는 목록과 함께 다시 그려집니다. 그러면 카드가 실제로는 건너뛰었는데도 update로 기록될 수 있습니다. 고친 효과를 숫자로 확인하려면 Profiler를 `memo` 경계 **안쪽**으로 옮겨야 했습니다.

## 바로 memo만 붙이지는 않았습니다

원인을 정리하고 나니, 고치는 방법도 여러 가지가 보였습니다.

| 방법 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. `memo` + 원본 객체 전달 | 카드를 `memo`로 감싸고, 새 객체 대신 받은 상품을 그대로 넘김 | 가장 단순함 | 새 목록이 도착하면 같은 상품도 다시 그려짐 |
| B. `memo` + 값 비교 함수 | 카드에 보이는 값만 하나씩 비교하는 함수를 `memo`에 넘김 | 두 번의 렌더링을 모두 막음, 기존 props 구조 유지 | 카드에 필드를 추가할 때 비교 함수도 고쳐야 함 |
| C. 값을 하나씩 props로 넘기기 | `product` 객체 대신 이름, 가격 등을 따로 넘기고 기본 `memo` 사용 | B와 효과가 같음, 필드를 빠뜨리면 타입 오류로 드러남 | 카드와 두 목록의 호출 코드가 모두 바뀌고 길어짐 |
| D. React Compiler 도입 | 컴파일러가 자동으로 memo를 적용 | 프로젝트 전체에 효과 | 빌드 설정까지 바꿔야 함, 새 객체 문제는 그대로 |

**A**는 가장 먼저 떠오르는 방법입니다. 하지만 이유 2 때문에 새 목록이 도착할 때의 렌더링은 그대로 남습니다. 문제의 절반만 푸는 셈이었습니다.

**D**의 React Compiler는 컴포넌트와 값을 자동으로 기억해 주는 도구입니다. 편해 보였지만, 카드 하나를 고치려고 프로젝트 전체의 빌드 설정을 바꾸는 것은 범위가 너무 컸습니다. 무엇보다 컴파일러도 결국 "같은 객체인지"를 기준으로 판단하기 때문에, 쿼리 키가 바뀌어 새로 만들어진 객체 문제는 풀어 주지 못합니다.

남은 것은 **B**와 **C**였습니다. 둘 다 "객체가 같은지"가 아니라 "카드에 보이는 값이 같은지"를 기준으로 판단하므로 효과는 같습니다. 차이는 어디를 고치느냐였습니다.

C는 필드를 빠뜨리면 타입 오류로 바로 드러난다는 장점이 있습니다. 대신 카드의 props 구조가 바뀌어서, 카드를 쓰는 두 목록의 호출 코드가 모두 바뀌고 props 6개를 나열하느라 길어집니다. B는 변경이 대부분 카드 컴포넌트 안에서 끝나고, 호출하는 쪽은 `product={product}` 그대로입니다.

이번 작업의 목표는 "다시 그리지 않아도 되는 카드를 다시 그리지 않기"였고, 기존 구조는 최대한 건드리지 않고 싶었습니다. 그래서 **B**를 골랐습니다. 비교 함수를 함께 고쳐야 하는 부담은, 비교 함수 바로 옆에 주의 문구를 남겨 두는 것으로 보완하기로 했습니다.

## 보이는 값이 같으면 건너뛰도록 바꿨습니다

먼저 카드에 보이는 값만 골라 비교하는 함수를 만들고, `memo`에 함께 넘겼습니다.

```tsx
// 카드에 표시하는 상품 필드를 추가하면 이 비교에도 함께 추가해야 함
function areProductCardPropsEqual(prev, next) {
  return (
    prev.detailHref === next.detailHref &&
    prev.product.name === next.product.name &&
    prev.product.price === next.product.price
    // ...category, productImageUrl, purchaseUrl도 같은 방식으로 비교
  );
}

export default memo(ProfiledProductCard, areProductCardPropsEqual);
```

이제 상품 객체가 새로 만들어져도, 이름·카테고리·가격·이미지·구매 링크·상세 링크가 모두 같으면 카드는 다시 그리지 않습니다.

다음으로 측정용 Profiler를 `memo` 안쪽으로 옮겼습니다. 카드가 다시 그리기를 건너뛰면 Profiler도 함께 건너뛰어서, 실제로 다시 그린 경우만 기록됩니다.

```tsx
// 렌더링을 건너뛴 카드는 update로 기록되지 않도록 Profiler를 memo 안쪽에 둠
function ProfiledProductCard(props) {
  return (
    <PerfProfiler id="product-card">
      <ProductCardContent {...props} />
    </PerfProfiler>
  );
}
```

마지막으로 목록 쪽에서는 매번 새 객체를 만들던 코드를 지우고, 받은 상품을 그대로 넘기도록 정리했습니다.

```tsx
<ProductCard key={product.recommendationId} product={product} detailHref={detailHref} />
```

## 195번이 0번이 됐습니다

같은 시나리오로 다시 쟀습니다.

| 항목 | 공개 상품 목록 | 내 추천 목록 |
|---|---|---|
| 카드 다시 그리기 | 195회 / 13.7ms → **0회** | 195회 / 13.6ms → **0회** |
| 목록 다시 그리기 합계 | 19.2ms → **6.6ms** | 19.4ms → **5.7ms** |
| 목록 다시 그리기 1번 (중앙값) | 1.9ms → **0.6ms** | 2.0ms → **0.6ms** |
| 조건 변경 전체 시간 (중앙값) | 160.9ms → 159.4ms | 160.4ms → 159.1ms |

카드 다시 그리기는 두 화면 모두 0회가 됐습니다. 카드를 다시 그리지 않으니 목록 한 번을 그리는 시간도 약 3분의 1로 줄었습니다.

![개선 후 React Profiler Flamegraph. 목록(PersonalRecommendationsListContent)은 다시 그려졌지만, 그 아래 ProfiledProductCard (Memo) 카드들은 모두 회색 빗금으로 표시되어 다시 그리지 않았음을 보여 줌](/images/2026-11-11-product-list-performance-2-card-rerender/after-cards-skipped.png "개선 후: 카테고리 1번 변경 후 다시 그리기를 건너뛴 상품 카드들")

개선 전 Flamegraph와 같은 장면입니다. 목록은 여전히 다시 그려지지만, 그 아래 `ProfiledProductCard (Memo)` 카드들은 모두 회색 빗금으로 바뀌었습니다. 회색 빗금은 이번 변경에서 다시 그리지 않고 건너뛰었다는 뜻입니다. 카드 바깥에 있던 측정용 Profiler도 카드 안쪽으로 들어가, 카드와 함께 건너뛰었습니다.

0회라는 숫자가 조금 이상하게 느껴질 수도 있습니다. 조건을 바꾸면 새로 들어오는 상품도 있는데, 그 카드는 어떻게 된 걸까요? 새로 들어온 상품의 카드는 "다시 그리기(update)"가 아니라 "처음 그리기(mount)"로 기록됩니다. 이번에 줄인 것은 이미 화면에 있던 카드를 다시 그리는 일이고, 새 카드를 처음 그리는 일은 원래 해야 하는 일이라 그대로 남아 있습니다.

조건 변경 전체 시간이 1~2ms 정도밖에 줄지 않은 것도 같은 맥락입니다. 측정용 목업 데이터는 실제 서버처럼 보이도록 응답을 일부러 150ms 늦게 돌려줍니다. 약 160ms 중 150ms가 응답을 기다리는 시간이고, 이번 작업은 그 뒤의 렌더링만 줄였기 때문에 전체 시간에는 거의 드러나지 않습니다. 그래서 이번 작업의 효과는 전체 시간보다 렌더링 횟수와 렌더링 시간으로 보는 것이 맞다고 판단했습니다.

### 공짜는 아니었습니다

이번에도 대가는 있었습니다. 비교 함수는 "카드에 보이는 값이 무엇인지"를 사람이 직접 적어 둔 목록입니다. 나중에 카드에 새 정보, 예를 들어 할인율을 표시하게 됐는데 비교 함수에 추가하는 것을 잊으면 어떻게 될까요? 타입 오류도 나지 않고, 할인율만 바뀐 경우에는 카드가 다시 그려지지 않아 화면이 갱신되지 않습니다.

그래서 비교 함수 바로 위에 "필드를 추가하면 여기도 함께 고쳐야 한다"는 주석을 남겼습니다. 실제로 이후 상품 목록 작업들에서도 카드를 건드릴 때마다 이 부분을 따로 확인하는 항목으로 챙기고 있습니다. C 방법을 골랐다면 타입 오류로 막을 수 있었던 부분이라, 선택의 대가로 안고 가는 부분입니다.
