안녕하세요. NeedU 백엔드팀입니다.

NeedU에는 친구 목록과 개인·친구 선물 추천 상품을 조회하는 API가 있습니다. V1 기능 구현을 마친 뒤 어느 정도의 부하를 견딜 수 있는지 확인하기 위해 테스트를 시작했는데, 첫 결과는 예상보다 좋지 않았습니다. 동시 사용자 20명에서 HikariCP 커넥션 10개가 모두 사용됐고, 처리량은 약 110 RPS에서 더 올라가지 않았습니다.

처음에는 커넥션 풀이 작은 것이 원인이라 생각했습니다. 하지만 풀 크기를 두 배로 늘려도 처리량은 개선되지 않았습니다. 문제는 커넥션의 개수가 아니라 각 커넥션이 느린 쿼리에 오래 붙잡혀 있었다는 점이었습니다.

원인을 따라가 보니 해당 테이블들에는 필요한 인덱스가 이미 존재했습니다. 다만 대량 시드 데이터 삽입 이후 MySQL 통계가 갱신되지 않아 옵티마이저가 인덱스를 활용하지 못하고 매 요청마다 약 4만 행을 풀스캔하고 있었습니다.

이 글을 통해 부하 테스트 결과에 따른 성능 개선 과정을 공유하고자 합니다.

1. 재현 가능한 부하 테스트와 관측 환경을 만든 과정
2. HikariCP 커넥션 풀을 늘렸지만 실패한 이유
3. 실행계획과 메트릭으로 진짜 병목을 찾은 과정
4. MySQL 통계 보정 후 최대 처리량이 약 130 RPS에서 2,483 RPS로 증가한 결과
5. 병목은 사라진 것이 아니라 다른 곳으로 이동한다.

## 문제 상황: 20 VU부터 멈춘 처리량

테스트 대상은 사용자가 자주 호출하는 조회 API 세 종류였습니다.

- 친구 목록 조회
- 개인 추천 상품 조회
- 친구 선물 추천 상품 조회

각 VU(Virtual User)는 세 API의 첫 페이지와 커서 페이지를 순차적으로 조회했습니다. 한 iteration은 총 6개의 HTTP 요청으로 구성했고, 완료 후 0.2초 동안 대기하도록 했습니다.

```
친구 목록 1페이지 → 친구 목록 2페이지
→ 개인 추천 1페이지 → 개인 추천 2페이지
→ 선물 추천 1페이지 → 선물 추천 2페이지
→ 0.2초 대기
```

테스트 환경은 다음과 같습니다.

| 항목 | 설정 |
| --- | --- |
| 호스트 | MacBook Pro, 10 CPU / 16 GiB |
| Docker VM | 10 CPU / 약 7.75 GiB |
| Spring Boot 애플리케이션 | 2 CPU / 1 GiB |
| MySQL | 2 CPU / 1 GiB |
| Tomcat 최대 스레드 | 200 |
| Hikari 최대 커넥션 | 10 |
| 부하 패턴 | Ramp-up 1분 / Hold 3분 / Ramp-down 30초 |
| 부하 도구 | k6 |
| 메트릭 수집·시각화 | Prometheus / Grafana |

이 결과는 동일한 로컬 환경에서 병목과 개선 효과를 비교하기 위한 수치입니다.

첫 테스트에서는 20 VU만으로도 문제가 분명하게 드러났습니다.

| 지표 | 측정 결과 |
| --- | --- |
| Spring 평균 처리량 | 110.8 RPS |
| Hikari Active 평균 / 최대 | 10 / 10 |
| Hikari Pending 평균 / 최대 | 6.6 / 10 |
| 평균 커넥션 점유시간 | 89.5ms |
| 평균 커넥션 획득 대기시간 | 51.8ms |
| App CPU 평균 | 8.5% |
| HTTP 실패율 | 0% |

애플리케이션 CPU는 8.5%로 여유가 있었지만 커넥션 풀은 테스트 내내 포화 상태였습니다. 평균 점유시간으로 단순 계산한 처리량도 실제 결과와 거의 같았습니다.

```
10 connections ÷ 0.0895초 ≈ 111.7 checkout/s
```

처리량은 실패율만으로 판단할 수 없습니다. 모든 요청이 200 응답을 받았지만, 이미 20 VU에서 커넥션 대기가 발생하고 있었습니다. VU가 늘어나면 완료되는 요청 수보다 대기열과 응답시간이 커질 가능성이 높은 상태였습니다.

![초기 20 VU 부하 테스트의 Hikari 커넥션과 애플리케이션 CPU 사용률](/assets/images/posts/load-test-improvement/02.png)

## 1단계: Hikari 커넥션을 두 배로 늘려보자

가장 먼저 떠올린 가설은 단순했습니다.

> “커넥션 10개가 모두 사용 중이라면 20개로 늘리면 되지 않을까?”
> 

당시 App CPU가 낮았기 때문에 커넥션을 더 제공하면 동시에 처리하는 요청이 늘고, 처리량도 증가할 것으로 예상했습니다.

```
Hikari Pending 감소
→ 동시 DB 작업 증가
→ App CPU 사용률 증가
→ 전체 처리량 증가
→ p95·p99 감소
```

하지만 결과는 예상과 달랐습니다. Pending 요청 수는 줄었지만 전체 처리량과 p95·p99는 개선되지 않았습니다. 오히려 SQL 처리시간과 커넥션 획득 대기시간이 증가했습니다.

문제는 요청의 대기 장소만 바뀐 것이었습니다. 기존에는 요청이 Hikari 앞에서 기다렸다면, 커넥션을 늘린 뒤에는 더 많은 쿼리가 MySQL 안으로 동시에 들어가 서로 경합이 발생했습니다. Spring 애플리케이션의 낮은 CPU만 보고 시스템 전체에 여유가 있다고 판단한 것이 오판이었습니다.

![Hikari 최대 커넥션을 20개로 늘린 부하 테스트 결과](/assets/images/posts/load-test-improvement/03.png)

여기서 Hikari 최대 커넥션을 다시 10으로 되돌렸습니다.

## 2단계: Slow Query가 없는데 DB가 느릴 수 있을까

부하 테스트 중 MySQL의 row lock wait와 slow query는 모두 0이었습니다. 이 수치만 보면 DB에는 특별한 문제가 없어 보입니다.

하지만 slow query가 없다는 결과가 쿼리가 효율적이라는 것까지 보장하는가? 라는 생각이 들었습니다. 개별 쿼리가 slow query 기준보다 빨라도, 비효율적인 쿼리가 높은 빈도로 반복되면 CPU를 소모하고 커넥션을 오래 점유할 수 있습니다.

API별 지연을 비교해보았습니다.

| API | 초기 20 VU p95 | 초기 20 VU p99 |
| --- | --- | --- |
| 친구 목록 | 110.9ms | 192.3ms |
| 개인 추천 상품 | 220.4ms | 344.1ms |
| 친구 선물 추천 상품 | 339.3ms | 373.0ms |

추천 API가 친구 목록보다 두세 배 느렸습니다. 개인 추천과 선물 추천 테이블은 각각 약 4만 건이었기 때문에 추천 조회의 실행계획을 직접 확인했습니다.

```
Limit: 21 rows
└─ Sort: score DESC, id DESC
   └─ Filter: user_id = ?
      └─ Table scan: 약 40,000 rows
```

두 추천 테이블에는 이미 `(user_id, score, id)` 복합 인덱스가 존재했습니다. 그런데 실제 실행계획은 인덱스가 아닌 테이블 풀스캔을 선택하고 있었습니다.

부하 중 수집한 SQL 지표도 같은 사실을 보여줬습니다.

| SQL | 평균 실행시간 | 실행당 검사 행 수 |
| --- | --- | --- |
| 선물 추천 목록 | 약 74ms | 약 40,000행 |
| 개인 추천 목록 | 약 42ms | 약 40,000행 |
| 선물 가격 범위 `MIN/MAX` | 약 29ms | 약 40,000행 |
| 개인 가격 범위 `MIN/MAX` | 약 30ms | 약 40,000행 |
| 친구 목록 | 약 2.5~3.3ms | 약 588행 |

## 진짜 원인: 인덱스가 아니라 통계였다

왜 인덱스가 있는데도 MySQL은 풀스캔을 선택했을까요?

확인 결과 옵티마이저가 예상한 테이블 크기는 약 1행이었고, 인덱스 cardinality는 0이었습니다. 실제로는 약 4만 건이 있었지만 MySQL은 거의 비어 있는 테이블로 판단하고 있었습니다.

테스트 데이터를 한 번에 대량 삽입한 뒤 InnoDB 통계가 갱신되지 않은 것이 원인이었습니다. 옵티마이저는 1행짜리 테이블을 위해 인덱스를 타는 것보다 전체를 읽는 편이 저렴하다고 판단했던 것이었습니다.

```
잘못된 InnoDB 통계
→ 기존 복합 인덱스 미사용
→ 추천 조회마다 약 40,000행 풀스캔
→ MySQL CPU와 커넥션 점유시간 증가
→ Hikari 10개 상시 포화
→ 약 130 RPS에서 처리량 고정
→ 추가 요청이 Pending으로 누적
→ p95·p99 증가
```

그래서 테이블 통계를 다시 수집했습니다.

```sql
ANALYZE TABLE
    users,
    friends,
    products,
    personal_recommendations,
    gift_recommendations;
```

변경은 이것이 전부였습니다. 애플리케이션 쿼리도, Hikari 풀 크기도, 인덱스 구성도 바꾸지 않았습니다.

## 3단계: 같은 조건으로 다시 측정하기

통계 보정 효과와 다음 병목을 확인하기 위해 Hikari 최대 커넥션을 10으로 유지한 채 20 → 50 → 100 → 150 → 200 VU 순서로 부하를 높였습니다.

### 테스트 1: 20 VU — 풀스캔이 사라지자 즉시 달라졌다

| 지표 | 통계 보정 전 | 통계 보정 후 |
| --- | --- | --- |
| Spring RPS | 129.9 | 504.0 |
| 친구 목록 p95 | 109.0ms | 7.0ms |
| 개인 추천 p95 | 200.2ms | 8.8ms |
| 선물 추천 p95 | 300.4ms | 7.0ms |
| 평균 커넥션 점유시간 | 76.1ms | 2.3ms |
| 평균 커넥션 획득 대기 | 40.7ms | 0.5ms |
| App CPU | 7.7% | 24.4% |

추천 목록 SQL은 약 42~74ms에서 0.55~0.57ms로 줄었습니다. 가격 범위 SQL도 약 29~30ms에서 1.44~1.50ms로 감소했습니다. 커넥션이 빠르게 반환되면서 Spring 처리량은 같은 20 VU에서 약 3.9배 증가했습니다.

App CPU가 7.7%에서 24.4%로 증가한 것도 중요한 변화였습니다. 애플리케이션이 더 비효율적으로 변한 것이 아니라, DB를 기다리던 요청이 실제 애플리케이션 로직을 더 많이 수행하게 된 결과입니다.

![MySQL 통계 보정 후 20 VU 부하 테스트 결과](/assets/images/posts/load-test-improvement/07.png)

![커넥션 점유시간이 76.1ms에서 2.3ms로 감소하며 처리량이 3.9배 증가했다.](/assets/images/posts/load-test-improvement/08.png)

### 테스트 2: 50 VU — 아직은 선형에 가까운 증가

| 지표 | 측정 결과 |
| --- | --- |
| Spring RPS | 1,355.8 |
| 친구 목록 p95 | 3.1ms |
| 개인 추천 p95 | 4.6ms |
| 선물 추천 p95 | 5.1ms |
| Hikari Active 평균 | 2.7 |
| Hikari Pending 평균 / 최대 | 0.8 / 17 |
| 평균 커넥션 획득 대기 | 0.2ms |
| App CPU | 45.8% |

20 VU보다 일부 응답시간이 더 낮았습니다. 이는 코드 변경의 효과라기보다 JVM JIT 컴파일과 MySQL 버퍼가 충분히 워밍업된 영향으로 판단했습니다. 처리량은 20 VU 대비 약 2.7배 증가했고, 지속적인 커넥션 대기도 나타나지 않았습니다.

![MySQL 통계 보정 후 50 VU 부하 테스트 결과](/assets/images/posts/load-test-improvement/09.png)

![50 VU에서도 p95는 10ms 이내를 유지했고 처리량은 약 1,356 RPS까지 증가했다.](/assets/images/posts/load-test-improvement/10.png)

### 테스트 3: 100 VU — 최대 처리량과 첫 번째 경고 신호

| 지표 | 측정 결과 |
| --- | --- |
| Spring RPS | **2,482.6** |
| 친구 목록 p95 / p99 | 23.6ms / 46.6ms |
| 개인 추천 p95 / p99 | 35.6ms / 48.7ms |
| 선물 추천 p95 / p99 | 38.9ms / 49.9ms |
| Hikari Active 평균 | 7.0 |
| Hikari Pending 평균 / 최대 | 2.8 / 24 |
| 평균 커넥션 획득 대기 | 1.5ms |
| App CPU | 75.8% |

100 VU에서는 최대 약 2,483 RPS를 기록했습니다. 하지만 App CPU가 약 80%까지 올라갔고, Hikari Pending과 tail latency도 함께 증가하기 시작했습니다.

처리량은 늘고 있었지만 시스템이 한계 구간에 가까워지고 있다는 신호였습니다.

## 완벽하지 않은 해결책: 병목은 사라지지 않고 이동한다

통계 재설정으로 추천 조회의 풀스캔은 사라졌고, 최대 처리량은 약 130 RPS에서 2,483 RPS로 증가했습니다. 하지만 시스템의 한계까지 사라진 것은 아니었습니다.

100 VU부터 App CPU와 tail latency가 상승했고, 150 VU에서는 Hikari Pending이 급격히 증가했습니다. 여기서 다시 커넥션 풀을 늘리면 앞선 실험과 같은 문제가 반복될 가능성이 컸습니다. 더 많은 요청을 MySQL로 보내기보다, 요청 하나를 처리할 때 반복되는 DB 작업과 불필요한 객체 생성을 줄이는 쪽으로 다음 개선 방향을 잡았습니다.

## 반복되는 가격 범위만 캐싱하기

통계 보정 후 추천 목록 SQL은 약 0.55ms까지 줄었지만, 가격 범위를 계산하는 `MIN/MAX` 쿼리는 약 1.44~1.50ms가 걸렸습니다. 이 쿼리는 같은 사용자의 첫 페이지와 커서 페이지를 조회할 때마다 반복됐습니다.

처음부터 추천 목록 전체를 캐싱하지는 않았습니다. 목록은 사용자, 가격 필터, 페이지 크기, cursor, score 정렬을 함께 고려해야 합니다. 캐시 키 조합이 많아지고 추천 결과가 갱신될 때 무효화할 범위도 커집니다.

반면 사용자별 가격 범위는 다음 특성이 있었습니다.

- 결과가 최솟값과 최댓값 두 개로 작습니다.
- 추천 목록보다 자주 바뀌지 않습니다.
- 첫 페이지와 커서 페이지에서 반복해서 사용됩니다.
- 추천 결과가 갱신되는 시점이 명확해 무효화하기 쉽습니다.

따라서 개인 추천과 선물 추천의 가격 범위만 Caffeine 로컬 캐시에 저장했습니다. TTL은 10분으로 설정하고, 추천 갱신 트랜잭션이 커밋된 뒤 해당 사용자의 개인·선물 가격 범위를 모두 무효화하도록 구성했습니다.

연속으로 실행한 다섯 번의 부하 테스트에서 가격 범위 캐시 hit ratio는 99.93~99.97%였습니다. 각 사이클에서 약 7.9만~54만 번 발생한 가격 범위 조회 가운데 DB까지 내려간 cache miss는 약 37~367회였습니다. 매 요청마다 실행되던 `MIN/MAX` 쿼리 대부분이 메모리 조회로 바뀐 것입니다.

![가격 범위 캐시 적용 후 전체 조회와 실제 DB 조회 횟수 비교](/assets/images/posts/load-test-improvement/17.png)

다만 이 수치는 VU를 단계적으로 높이며 연속 실행한 Warm Cache 중심의 결과입니다. Cold Start 성능이나 다중 인스턴스에서의 캐시 정합성까지 검증한 수치로 해석해서는 안 됩니다.

## 목록 조회에 필요한 값만 가져오기

추천 목록 Repository는 연관된 상품 Entity까지 조회한 뒤 응답 DTO로 변환하고 있었습니다. 응답에 사용하지 않는 컬럼도 함께 읽고, 조회된 Entity를 생성해 영속성 컨텍스트에서 관리해야 했습니다.

이를 응답에 필요한 필드만 선택하는 DTO Projection으로 변경했습니다.

```
[변경 전]
추천 Entity + 상품 Entity 전체 조회
→ Entity 생성 및 영속성 컨텍스트 관리
→ Response DTO 변환

[변경 후]
응답에 필요한 컬럼만 조회
→ Projection 생성
→ Response DTO 변환
```

조회 데이터와 객체 생성을 줄이면 DB에서 애플리케이션으로 전달되는 데이터, 매핑 비용, 메모리 할당을 함께 줄일 수 있습니다. 특히 목록처럼 같은 형태의 객체를 짧은 시간에 많이 만드는 API에서 효과를 기대했습니다.

Connector/J의 PreparedStatement 캐시도 활성화했습니다.

```
spring.datasource.hikari.data-source-properties.cachePrepStmts=true
spring.datasource.hikari.data-source-properties.prepStmtCacheSize=250
spring.datasource.hikari.data-source-properties.prepStmtCacheSqlLimit=2048
```

반복되는 SQL을 실행할 때 Connector/J가 PreparedStatement를 준비하며 발생하는 부가 비용을 재사용하기 위한 설정입니다. `useServerPrepStmts`는 활성화하지 않았으므로 서버 측 Prepared Statement를 사용하도록 바꾼 것은 아닙니다.

DTO Projection과 PreparedStatement 캐시는 각각을 분리한 A/B 테스트를 수행하지 않았습니다. 따라서 특정 설정이 처리량을 몇 배 높였다고 해석하지 않고, 요청당 조회·객체 생성 비용을 줄이기 위해 함께 적용한 개선으로만 평가했습니다.

## Serial GC에서 G1GC로 전환하기

기존 컨테이너에서는 Serial GC가 선택되고 있었습니다. Serial GC는 하나의 스레드로 GC 작업을 수행해 오버헤드가 작지만, 멀티코어 환경의 고부하 애플리케이션에서는 GC 작업을 병렬화할 수 없습니다. G1GC는 Heap을 여러 Region으로 나누고 일부 작업을 애플리케이션과 동시에, 여러 스레드로 수행해 정지 시간을 더 예측 가능하게 관리합니다.

런타임 옵션에 `-XX:+UseG1GC`를 명시한 뒤, 같은 20·50·100·150·200 VU 구간을 다시 측정했습니다.

| 지표 | Serial GC | G1GC |
| --- | --- | --- |
| 평균 Heap 사용률 범위 | 50~63% | 21~32% |
| 최대 Heap 사용률 범위 | 62~83% | 34~51% |
| 최대 관측 처리량 | 3,742 RPS | 3,571 RPS |

![가격 범위 캐시 적용 후 전체 조회와 실제 DB 조회 횟수 비교](/assets/images/posts/load-test-improvement/18.png)

Heap 사용률은 확실히 낮아졌지만 처리량까지 증가한 것은 아니었습니다. Serial GC 실행에서는 200 VU에서 약 3,742 RPS, G1GC 실행에서는 150 VU에서 약 3,571 RPS가 최대였습니다.

즉, G1GC 전환은 최고 처리량을 높이는 최적화가 아니라 메모리 여유를 확보하고 고부하에서 GC 부담을 낮추기 위한 선택이었습니다. GC 역시 항상 더 우수한 하나의 답이 있는 것이 아니라, 처리량과 지연, 메모리 사용량 중 어떤 목표를 우선할지에 따라 선택해야 했습니다.

---

## 후속 개선 결과: 한계 구간이 150 VU까지 이동했다

최종 테스트도 이전과 같은 로컬 Docker 자원과 Hikari 최대 커넥션 10 조건에서 진행했습니다. 아래 값은 Ramp-up과 Ramp-down을 제외한 각 3분 유지 구간의 평균입니다.

| VU | Spring RPS | App CPU | Heap 평균 | Hikari Pending 평균 | API p95 범위 |
| --- | --- | --- | --- | --- | --- |
| 20 | 515 | 24.2% | 24.4% | 0.2 | 4.0~6.9ms |
| 50 | 1,352 | 39.9% | 21.4% | 0.3 | 3.4~4.1ms |
| 100 | 2,538 | 72.5% | 21.1% | 2.7 | 4.8~5.2ms |
| 150 | **3,571** | 92.4% | 24.6% | 9.7 | 11.9~13.3ms |
| 200 | 3,353 | 98.4% | 31.7% | 32.5 | 62.6~70.6ms |

![후속 개선 후 VU별 처리량과 시스템 지표](/assets/images/posts/load-test-improvement/19.png)

통계 재설정 직후 최대 처리량은 100 VU에서 약 2,483 RPS였습니다. 후속 개선 뒤에는 150 VU에서 약 3,571 RPS를 기록해 최대 관측 처리량이 추가로 약 43.8% 증가했습니다. 같은 150 VU끼리 비교하면 약 2,243 RPS에서 3,571 RPS로 약 59.2% 증가했습니다.

낮은 부하에서는 차이가 크지 않았습니다. 20~100 VU 처리량은 통계 재설정 직후와 비슷한 수준이었습니다. 차이는 시스템이 포화 구간에 접근했을 때 나타났습니다. 반복 DB 조회와 객체 생성 부담을 줄이자 처리량이 증가하는 구간이 100 VU에서 150 VU까지 확장됐습니다.

하지만 200 VU에서는 다시 한계가 나타났습니다.

```
150 VU
→ 약 3,571 RPS
→ App CPU 92.4%
→ API p95 11.9~13.3ms

200 VU
→ 약 3,353 RPS로 감소
→ App CPU 98.4%
→ Hikari Pending 평균 32.5
→ API p95 62.6~70.6ms
```

추가된 부하는 처리량으로 전환되지 않고 CPU 사용률과 커넥션 대기, tail latency를 증가시켰습니다. 풀스캔을 제거했을 때는 DB 쿼리가 병목이었지만, 후속 개선 뒤에는 애플리케이션 CPU와 고부하 구간의 커넥션 대기가 새로운 한계로 드러났습니다.

최대 관측 처리량과 운영 가능한 처리량도 여전히 다릅니다. 150 VU에서 가장 높은 RPS를 기록했지만 CPU가 이미 90%를 넘었습니다. 실제 안정 구간은 운영 SLO와 오류 예산을 먼저 정한 뒤, 그보다 보수적으로 결정해야 합니다. 또한 이 결과는 동일한 로컬 환경에서 개선 전후를 비교한 값이며 운영 환경의 수용량을 의미하지 않습니다.

## 이번 테스트에서 배운 것

첫째, 캐시는 넓게 적용하는 것보다 반복 빈도가 높고 정합성 관리가 단순한 값부터 적용하는 편이 효과를 검증하기 쉽습니다. 추천 목록 전체가 아니라 가격 범위만 선택한 이유입니다.

둘째, 같은 결과를 반환하더라도 요청 하나가 수행하는 일은 다를 수 있습니다. 필요한 컬럼만 조회하고 반복 SQL의 준비 비용을 재사용하면 DB와 애플리케이션이 처리해야 할 작업을 함께 줄일 수 있습니다.

셋째, 개별 개선의 기대 효과와 전체 테스트 결과를 구분해야 합니다. 가격 범위 캐시는 hit/miss 지표로 DB 조회 감소를 확인했고, GC는 같은 VU 구간의 메모리 사용량을 비교했습니다. 

마지막으로, 성능 개선은 병목을 완전히 없애는 작업이 아니었습니다. 불필요한 작업을 하나씩 줄일수록 다음 한계가 더 선명하게 보였습니다.

## 마무리

처음에는 Hikari 커넥션이 부족하다고 생각했습니다. 하지만 풀 크기를 늘려도 처리량은 나아지지 않았고, 실행계획을 확인한 뒤에야 잘못된 통계로 기존 인덱스가 사용되지 않는다는 사실을 찾았습니다.

통계를 재설정해 풀스캔을 제거하자 최대 처리량은 약 130 RPS에서 2,483 RPS로 약 19배 증가했습니다. 이후 가격 범위 캐싱, DTO Projection, PreparedStatement 캐시를 적용해 요청당 작업을 줄였고, 최대 관측 처리량은 다시 3,571 RPS까지 증가했습니다. G1GC 전환으로 평균 Heap 사용률도 약 50~63%에서 21~32%로 낮아졌습니다.

```
통계 재설정: 약 130 RPS → 약 2,483 RPS
후속 개선: 약 2,483 RPS → 약 3,571 RPS
가격 범위 캐시 hit ratio: 99.93~99.97%
평균 Heap 사용률: 약 50~63% → 약 21~32%
새로운 한계: App CPU와 고부하 구간의 커넥션 대기
```

이번 테스트를 통해 얻은 결론은 “커넥션을 몇 개로 설정해야 하는가”보다 

> 같은 요청을 처리하기 위해 꼭 필요한 작업은 무엇이고, 매번 반복하지 않아도 되는 작업은 무엇인가?
> 

였습니다.

병목은 사라지지 않았습니다. 다만 근거 없이 자원을 늘리는 대신, 측정 가능한 작은 개선을 반복하면서 시스템이 더 많은 요청을 처리할 수 있는 지점까지 병목을 이동시킬 수 있었습니다.
