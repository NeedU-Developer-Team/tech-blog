안녕하세요, NeedU 프론트엔드 개발자 김주희입니다.

쇼핑몰에서 상품을 하나 눌러 봤다가 뒤로가기를 눌렀는데, 보던 목록이 사라지고 맨 위로 돌아가 있었던 경험 있으신가요? 저희 서비스에도 바로 그런 문제가 있었습니다.

[2편](https://needu-developer-team.github.io/tech-blog/posts/product-list-performance-2-card-rerender/)에서 조건을 바꿀 때 카드가 다시 그려지던 문제를 줄였다면, 이번 3편에서는 **상품을 보고 목록으로 돌아오는 순간**을 다뤄 보려고 해요. NeedU는 대화로 취향을 분석해 선물할 상품을 추천해 주는 서비스라, 사용자들은 상품을 눌러 보고 돌아오기를 여러 번 반복하며 선물을 고르거든요.

그런데 돌아올 때마다 목록이 처음 상태로 돌아가 있었습니다.

![개선 전 뒤로가기 모습. 리빙 카테고리를 고르고 예산을 13만 원으로 줄인 뒤 목록을 내려가 상품을 누르면, 상세 데이터가 없는 측정용 목업이라 페이지를 찾을 수 없다는 화면이 나온다. 뒤로가기를 하면 카테고리는 전체로, 예산은 20만 원으로 돌아가고 목록이 맨 위에서 시작함](/images/2026-11-25-product-list-performance-3-back-restore/before-back.gif "개선 전: 상품을 보고 뒤로가기로 돌아온 모습. 측정용 목업 데이터라 상세 대신 '페이지를 찾을 수 없어요'가 보입니다.")

골라 둔 카테고리는 "전체"로, 조절해 둔 예산은 처음 범위로 돌아갔고, 한참 내려가서 보던 목록은 맨 위에서 다시 시작했습니다. 세 번째 줄쯤에서 본 상품과 비교하고 싶어도 돌아올 때마다 **필터를 다시 고르고 스크롤을 다시 내려야** 했습니다. 내 추천, 공유 탭, 친구 추천 세 화면 모두 마찬가지였습니다.

실제 상품 상세에서 돌아오는 경우는 뒤에서 스테이징 환경으로 따로 확인했습니다.

## 왜 다 사라졌을까

원인부터 찾아봤습니다. 사라지는 것은 **필터**와 **스크롤 위치**, 두 가지였고 이유는 서로 달랐습니다.

### 필터는 컴포넌트와 함께 사라졌습니다

React로 만든 화면은 **컴포넌트** 단위로 이루어져 있습니다. 상품 목록도 하나의 컴포넌트이고, 이 컴포넌트가 `useState`로 카테고리와 예산을 기억하고 있었습니다. 문제는 이 값이 **컴포넌트 안에만** 있다는 점이었습니다.

![목록 컴포넌트와 상태의 관계. 목록 화면에 있을 때는 목록 컴포넌트가 카테고리와 예산을 기억한다. 상세로 이동하면 목록 컴포넌트가 사라지면서 기억하던 값도 사라지고, 돌아오면 새 목록 컴포넌트가 처음 값으로 시작한다](/images/2026-11-25-product-list-performance-3-back-restore/component-state-lost.svg "목록 컴포넌트가 사라지면, 그 안에 기억하던 값도 함께 사라집니다.")

상품을 누르면 상세 화면으로 바뀌면서 목록 컴포넌트가 사라지고, 컴포넌트가 기억하던 카테고리와 예산도 함께 사라집니다. 뒤로가기로 돌아오면 목록 컴포넌트가 새로 만들어지니 처음 값으로 시작할 수밖에 없었습니다.

반면 "내 추천"과 "공유 탭" 중 어느 탭을 보고 있었는지는 잘 유지되고 있었습니다. 탭은 주소(`?tab=shared`)에 들어 있었고, 주소는 뒤로가기를 하면 그대로 돌아오기 때문입니다. 결국 문제는 **주소에 없는 값**들이었습니다.

### 스크롤은 브라우저가 기억해 주지 않았습니다

브라우저에는 원래 뒤로가기를 하면 보던 위치로 되돌려 주는 기능이 있습니다. 하지만 이 기능은 **페이지 전체가 스크롤될 때**만 동작합니다.

![일반 페이지와 NeedU 화면 구조 비교. 일반 페이지는 페이지 전체가 스크롤되어 브라우저가 위치를 기억한다. NeedU는 헤더와 하단 메뉴가 고정되고 가운데 영역만 스크롤되어 브라우저가 위치를 기억하지 않는다](/images/2026-11-25-product-list-performance-3-back-restore/scroll-area-structure.svg "NeedU는 가운데 영역만 스크롤되어, 브라우저의 기본 복원이 닿지 않습니다.")

NeedU는 상단 헤더와 하단 메뉴를 고정하기 위해 페이지 전체가 아니라 **가운데 영역 하나만** 스크롤되는 구조입니다. 그래서 브라우저가 기억해 주는 범위 밖에 있었습니다.

## 그럼 떠날 때 저장해 두면 되지 않을까

원인을 알고 나니 해결 방법은 간단해 보였습니다.

> 떠날 때 필터와 위치를 어딘가에 적어 두고, 돌아오면 다시 꺼내 쓰면 된다.

방향은 맞았습니다. 하지만 하나씩 따져 보니 "어딘가에 적어 둔다"는 말 안에 질문이 네 개나 숨어 있었습니다.

1. **어디에** 적어 둘까?
2. 돌아온 건지, **새로 들어온 건지** 어떻게 알까?
3. **언제** 적고, 언제 멈출까?
4. 돌아왔을 때 **목록이 같다는 보장**이 있을까?

이번 글은 이 네 질문에 하나씩 답해 온 과정입니다.

## 어디에 적어 둘까: URL 대신 Zustand

가장 먼저 떠오른 곳은 주소, 즉 URL이었습니다. 탭이 이미 주소에 들어 있으니 카테고리와 예산도 넣으면 될 것 같았고, URL에 넣으면 뒤로가기는 물론 새로고침이나 링크 공유까지 됩니다.

하지만 이번에 필요한 것은 "보고 돌아왔을 때 그대로 있기"였고, 새로고침 후 유지나 링크 공유는 범위에서 뺐습니다. 그런데 URL로 가면 쓰지 않을 기능 때문에 고칠 곳이 가장 많았습니다. 탭마다 다른 예산을 주소로 표현해야 하고, 주소에 잘못된 값이 들어온 경우를 처리해야 하며, 서버에서 미리 받아 두는 첫 페이지의 조건까지 주소에 맞춰 바꿔야 했습니다.

브라우저의 `sessionStorage`도 살펴봤습니다. 새로고침해도 남는 저장 공간이지만, 서버에서 처음 그린 화면은 이 값을 모릅니다. 화면이 뜬 뒤에야 값을 읽기 때문에 **필터 없는 목록이 잠깐 보였다가 바뀌는** 깜빡임이 생길 수 있었습니다.

그래서 **Zustand**를 골랐습니다. Zustand는 컴포넌트 바깥에 두는 작은 상태 저장소입니다. 목록 컴포넌트가 사라져도 여기에 둔 값은 남아 있어서, 화면 전체가 함께 쓰는 메모장처럼 쓸 수 있습니다.

메모리에 두니 새로고침하면 사라지지만 이번 범위에서는 문제가 되지 않았습니다. 대신 화면을 **처음 그릴 때 바로 읽을 수 있어서** 깜빡임이 없고, NeedU는 이미 다른 화면에서 Zustand를 쓰고 있어 새 도구를 들일 필요도 없었습니다.

| | URL | `sessionStorage` | Zustand |
| --- | --- | --- | --- |
| 뒤로가기 복원 | 됨 | 됨 | 됨 |
| 새로고침 후 | 유지 | 유지 | 사라짐 |
| 첫 화면 깜빡임 | 없음 | 생길 수 있음 | 없음 |
| 고칠 범위 | 가장 큼 | 보통 | 작음 |

스크롤 위치도 같은 저장소에 **`scrollTop`**으로 적어 두기로 했습니다. "맨 위에서 몇 픽셀 내려왔는지"를 나타내는 숫자 하나입니다.

## 돌아온 건지 어떻게 알까: 방문 기록에 이름표 붙이기

그런데 그냥 "상품 목록의 필터"로 적어 두면 곤란한 상황이 생깁니다. 상세에서 **뒤로가기**로 돌아오면 복원해야 하지만, 하단 메뉴로 **새로 들어오면** 처음 상태여야 합니다. 두 경우 모두 주소는 `/products`로 똑같아서, 주소만 봐서는 구분할 수 없었습니다.

그래서 브라우저의 **방문 기록**을 이용했습니다. 브라우저는 뒤로가기를 위해 지나온 화면들을 한 칸씩 기억하고, 칸마다 `history.state`라는 작은 메모지를 붙일 수 있습니다. `history.state`는 방문 기록 칸마다 따로 보관되는 데이터로, 뒤로가기로 그 칸에 돌아오면 다시 읽을 수 있습니다.

이 메모지에 **고유한 이름표**를 적어 두고, Zustand에는 그 이름표를 기준으로 필터와 위치를 저장했습니다.

![방문 기록 이름표로 뒤로가기와 새 진입을 구분하는 흐름. 목록에 들어오면 방문 기록 칸의 메모지에 이름표 A를 붙이고, Zustand에 이름표 A의 필터와 위치를 저장한다. 뒤로가기로 돌아오면 이름표 A를 찾아 복원하고, 메뉴로 새로 들어오면 이름표가 없는 새 칸이라 처음 상태로 시작한다](/images/2026-11-25-product-list-performance-3-back-restore/history-entry-key.svg "같은 주소라도, 방문 기록의 이름표로 뒤로가기와 새 진입을 구분합니다.")

```ts
const ensureHistoryEntryKey = () => {
  const currentEntryKey = readHistoryEntryKey();
  if (currentEntryKey) return currentEntryKey;      // 이미 이름표가 있으면 그대로 사용

  const entryKey = crypto.randomUUID();              // 겹치지 않는 새 이름표
  window.history.replaceState({ ...window.history.state, [HISTORY_ENTRY_KEY]: entryKey }, "");
  return entryKey;
};
```

여기에 안전장치 두 가지를 더했습니다.

- **어느 목록의 값인지(`listId`)도 함께 적었습니다.** 내 추천의 값이 친구 추천에 섞이지 않도록 하고, 친구 추천은 친구마다(`friend:친구ID`) 따로 적습니다.
- **최근 20개만 남겼습니다.** 목록을 오갈 때마다 기록이 쌓이므로 오래된 것부터 지웁니다.

복원은 목록 컴포넌트가 처음 만들어질 때 합니다. 적어 둔 필터를 `useState`의 첫 값으로 넣어서, **처음 그리는 순간부터** 복원된 필터로 목록을 보여 줍니다.

```tsx
const [restoredFilter] = useState(() => readProductListFilter(PERSONAL_PRODUCT_LIST_ID));
```

### 그런데 탭이 바뀌지 않았습니다

필터 복원을 붙이고 나니 이상한 문제가 생겼습니다. 공유 탭을 눌러도 화면이 바뀌지 않았던 것입니다. 주소는 분명 `?tab=shared`로 바뀌었는데도 말이죠.

탭 전환은 방문 기록이 쌓이지 않도록 `history.replaceState(null, ...)`로 **주소만** 바꾸고 있었습니다. 그런데 메모지 자리에 `null`을 넘기면 방금 붙인 이름표까지 지워집니다. 그래서 이름표를 지키려고 **기존 메모지를 통째로** 넘기도록 바꿨는데, 이것이 문제였습니다.

![탭 전환 문제의 원인. 기존 메모지를 통째로 넘기면 Next.js 내부 표시 __NA가 함께 넘어가 Next.js가 주소 변경을 무시한다. 우리 이름표만 넘기면 Next.js가 주소 변경을 반영해 탭이 바뀐다](/images/2026-11-25-product-list-performance-3-back-restore/replace-state-na.svg "기존 메모지를 통째로 넘기면, Next.js가 주소 변경을 화면에 반영하지 않습니다.")

메모지에는 우리 이름표뿐 아니라 Next.js가 내부에서 쓰는 표시(`__NA`)도 들어 있었습니다. Next.js는 이 표시가 있으면 "내가 직접 처리한 이동"으로 여기고, 바뀐 주소를 화면에 반영하지 않습니다. 그래서 주소만 바뀌고 화면은 그대로였던 것입니다.

결국 주소를 바꿀 때는 **우리 이름표만** 넘기도록 고쳐서 해결했습니다.

```ts
export const replaceProductListUrl = (url: string) => {
  const entryKey = readHistoryEntryKey();
  window.history.replaceState(entryKey ? { [HISTORY_ENTRY_KEY]: entryKey } : null, "", url);
};
```

## 언제 적어 둘까: 떠나는 순간, 0이 적혀 있었습니다

이제 스크롤 위치를 적어 둘 차례입니다. 가장 쉬운 방법은 **스크롤할 때마다** 위치를 적는 것인데, 이렇게 하면 정말 떠날 때의 위치가 남을까요? 상품을 누르는 순간 스크롤 위치가 어떻게 바뀌는지 직접 기록해 봤습니다.

| 시점 | 스크롤 위치 | 목록 카드 |
| --- | --- | --- |
| 상품을 누를 때 | 3254 | 60개 |
| 상세 화면으로 바뀐 뒤 | **0** | 0개 |
| 뒤로가기 직후 | - | 60개 |

상세 화면은 목록보다 훨씬 짧아서, 화면이 바뀌면 내려갈 곳이 없어져 스크롤 위치가 0이 됩니다. 그리고 이때 **"위치가 바뀌었다"는 알림(`scroll` 이벤트)이 한 번 더** 옵니다.

![상세 화면으로 이동할 때의 순서. 3254에서 상품을 누르면 목록이 사라지고 상세 화면이 그려진 뒤, 위치 0을 알리는 scroll 이벤트가 도착한다. 이 알림을 그대로 적으면 3254가 0으로 덮어써진다](/images/2026-11-25-product-list-performance-3-back-restore/scroll-event-order.svg "목록이 사라진 뒤 도착한 위치 0의 알림이, 적어 둔 3254를 덮어씁니다.")

스크롤할 때마다 적도록 해 두면 이 마지막 알림이 **적어 둔 3254를 0으로 덮어쓰고**, 돌아오면 결국 또 맨 위입니다. 결국 중요한 것은 "어떻게 적을까"가 아니라 **"언제 적기를 멈출까"**였습니다. 알림이 오기 전, 목록이 사라지는 그 순간에 적기를 멈춰야 했습니다.

### 그리기 전에 처리하기: `useLayoutEffect`

React에는 화면이 바뀔 때 코드를 실행하는 방법이 두 가지 있고, 차이는 **실행 시점**입니다. `useEffect`는 브라우저가 화면을 **그린 뒤에** 실행되고, `useLayoutEffect`는 화면을 **그리기 직전에** 실행됩니다. 보통은 `useEffect`를 쓰지만, 이번에는 그 "뒤에"가 문제였습니다.

![useEffect와 useLayoutEffect의 실행 시점 비교. useEffect는 화면을 그린 뒤 실행되어, 떠날 때는 위치 0 알림을 적을 수 있고 돌아올 때는 맨 위가 먼저 보인 뒤 이동한다. useLayoutEffect는 그리기 전에 실행되어, 떠날 때 알림 받기를 먼저 멈추고 돌아올 때 이동한 상태로 처음 그린다](/images/2026-11-25-product-list-performance-3-back-restore/effect-timing.svg "그리기 전에 실행되는 useLayoutEffect는, 떠날 때 먼저 멈추고 돌아올 때 먼저 옮깁니다.")

`useEffect`라면 떠날 때 알림 받기를 **늦게** 멈춰서 0을 적을 수 있고, 돌아올 때는 **맨 위가 잠깐 보인 뒤** 이동합니다. 반면 `useLayoutEffect`는 둘 다 그리기 전에 처리합니다. 떠날 때는 목록이 사라지는 순간 알림 받기를 멈추고, 돌아올 때는 위치를 옮긴 상태로 처음 그립니다.

```ts
export function useProductListScrollRestore(listId: string) {
  useLayoutEffect(() => {
    const scrollArea = document.querySelector<HTMLElement>("[data-main-scroll-area]");
    if (!scrollArea) return;

    const savedScrollTop = readProductListScrollTop(listId);
    if (savedScrollTop !== null) scrollArea.scrollTop = savedScrollTop;   // 1. 그리기 전에 위치 복원

    const handleScroll = () => saveProductListScrollTop(listId, scrollArea.scrollTop);
    scrollArea.addEventListener("scroll", handleScroll, { passive: true }); // 2. 스크롤할 때마다 기록
    return () => scrollArea.removeEventListener("scroll", handleScroll);   // 3. 목록이 사라지는 순간 기록 중지
  }, [listId]);
}
```

가운데 스크롤 영역은 모든 화면이 함께 쓰는 레이아웃에 있습니다. 목록에서 이 영역을 찾을 수 있도록, 레이아웃 구조는 그대로 두고 `data-main-scroll-area`라는 표시 한 줄만 붙였습니다.

## 목록이 같다는 보장이 있을까: 5분 동안 붙잡아 두기

마지막 질문이 남았습니다. `scrollTop`은 "맨 위에서 3254픽셀"이라는 숫자일 뿐이라, 돌아왔을 때 목록이 떠날 때와 다르면 **같은 위치에 다른 상품**이 보입니다.

그리고 NeedU에서는 목록이 실제로 달라질 수 있었습니다. **취향 분석을 새로 확정할 때마다 추천 상품이 쌓이기 때문입니다.** 게다가 목록은 추천 점수 순서라서, 새 상품은 맨 뒤가 아니라 기존 상품들 사이에 끼어듭니다.

![새 상품이 끼어들 때의 스크롤 위치. 분석 확정 전에는 저장한 위치에 상품 C가 있다. 확정 후 위쪽에 새 상품이 끼어들면 같은 위치에 다른 상품이 보인다](/images/2026-11-25-product-list-performance-3-back-restore/accumulate-shift.svg "위쪽에 새 상품이 끼어들면, 같은 위치에 다른 상품이 보입니다.")

상품 목록은 TanStack Query가 관리합니다. 서버에서 받은 목록을 **보관함(캐시)**에 넣어 두고 다시 쓰게 해 주는 라이브러리로, 시간 설정이 두 가지 있습니다.

- `staleTime`: 받은 목록을 **최신으로 믿는 시간**입니다. 유통기한과 비슷합니다.
- `gcTime`: 쓰지 않는 목록을 **보관하는 시간**입니다. 기본 5분이 지나면 지웁니다.

내 추천은 유통기한이 이미 5분이었지만 공유 탭과 친구 추천은 0이었습니다. 받자마자 오래된 것으로 보고, 돌아올 때 다시 요청할 수 있는 상태였습니다. 그래서 두 가지를 함께 했습니다.

- **공유 탭과 친구 추천도 유통기한을 5분으로 맞췄습니다.** 5분 안에 돌아오면 받아 둔 목록을 그대로 씁니다.
- **취향 분석을 확정하는 순간 보관함을 비웠습니다.** 적어 둔 필터와 위치도 함께 지워, 새 목록을 맨 위부터 보여 줍니다.

```ts
// 분석 확정 응답을 받으면 이전 목록과 복원 값을 모두 지운 뒤 이동
clearPersonalRecommendationsCache(queryClient);
clearMyGiftRecommendationsCache(queryClient);
clearProductListRestoreState();
router.replace("/products");
```

받아 둔 목록은 "틀린 목록"이 아니라 "새 상품만 빠진 목록"이어서, 5분 동안 그대로 보여 줘도 부담이 크지 않다고 판단했습니다. 5분은 측정으로 정한 값은 아니고, 내 추천이 이미 쓰던 값에 맞춰 세 화면을 통일한 것입니다. 보관 시간 기본값(`gcTime`)과도 같습니다.

![뒤로가기로 돌아올 때의 세 가지 경우. 5분 안에 돌아오면 보관함에 목록이 있어 다시 요청하지 않고 위치를 정확히 복원한다. 5분이 지나 보관함이 비었으면 일부 페이지만 있어 위치가 앞쪽으로 당겨진다. 분석을 확정했으면 보관함과 복원값을 지워 새 목록을 맨 위부터 보여 준다](/images/2026-11-25-product-list-performance-3-back-restore/return-cache-flow.svg "돌아올 때 보관함의 상태에 따라 결과가 세 가지로 나뉩니다.")

## 복원 구조의 변화

지금까지의 과정을 정리하면, 뒤로가기 복원은 다음 세 단계를 거쳐 지금의 모습이 되었습니다.

![세 구조 비교. 개선 전에는 목록 컴포넌트와 함께 필터와 위치가 사라져 맨 위에서 시작한다. 스크롤할 때마다 위치만 적으면 떠나는 순간의 0이 덮어써져 여전히 맨 위에서 시작한다. 지금 구조는 방문 기록 이름표로 구분해 그리기 전에 복원하고, 5분 동안 목록을 붙잡아 떠날 때와 같은 위치로 돌아온다](/images/2026-11-25-product-list-performance-3-back-restore/before-after.svg "아무것도 적지 않던 구조에서, 이름표로 구분하고 그리기 전에 되돌리는 지금 구조까지")

**1. 아무것도 적어 두지 않던 구조.** 목록 컴포넌트가 사라지면서 필터와 위치도 함께 사라졌습니다. 돌아오면 카테고리는 "전체", 위치는 맨 위였습니다.

**2. 스크롤할 때마다 위치만 적는 구조.** 처음 떠올린 방법입니다. 하지만 떠나는 순간 도착하는 위치 0의 알림이 적어 둔 값을 덮어써서, 결국 맨 위로 돌아오게 됩니다. 주소만 보고 적으면 메뉴로 새로 들어올 때도 이전 값이 복원되는 문제도 남습니다.

**3. 이름표로 구분하고, 그리기 전에 처리하는 지금 구조.** 방문 기록의 이름표로 뒤로가기와 새 진입을 구분합니다. 목록이 사라지는 순간 적기를 멈추고, 돌아올 때는 그리기 전에 위치를 옮기며, 5분 동안은 목록도 그대로 붙잡아 둡니다.

| --- | --- | --- | --- |
| 카테고리·예산 | 사라짐 | 사라짐 | 유지 |
| 스크롤 위치 | 맨 위 | 0으로 덮어써져 맨 위 | 떠날 때와 같은 위치 |
| 메뉴로 새로 들어올 때 | 처음 상태 | 이전 값이 섞일 수 있음 | 처음 상태 |

## 아직 남아 있는 것들

모든 경우를 해결한 것은 아닙니다.

**5분이 지나면 위치를 잃습니다.** 상세에 5분 넘게 머물렀다 돌아오면, 5165.5에서 떠났는데 1202.5에 멈췄습니다. 보관함이 비워져 첫 페이지만 남았고, 그 높이까지만 내려갈 수 있었던 것으로 보입니다. 보관 시간을 늘리면 해결되지만 메모리를 더 쓰게 되고, 실제로 상세에 얼마나 머무는지 데이터가 없어 배포 후 체류 시간을 보고 판단하기로 했습니다.

**새로고침하면 사라집니다.** 메모리에 적어 두는 방식이라 새로고침이나 링크 공유는 지원하지 않습니다. 필요해지면 URL 방식으로 옮겨야 합니다.

**친구 추천은 잠깐 기다립니다.** 친구 정보를 받은 뒤에 목록을 그려서, 돌아올 때 0.3초 이내의 대기 화면을 거친 뒤 위치로 이동합니다.

**바뀌기 쉬운 부분에 기대고 있습니다.** Next.js 내부 표시(`__NA`)의 동작은 공개된 기능이 아니라 버전을 올릴 때 바뀔 수 있습니다. 그래서 코드에 이유를 주석으로 남기고, 버전을 올릴 때 탭 전환과 복원을 함께 확인하기로 했습니다.
