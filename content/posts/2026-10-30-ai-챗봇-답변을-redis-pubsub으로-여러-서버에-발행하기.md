안녕하세요. NeedU 백엔드 개발자 노주연입니다.

지난 [1편](https://needu-developer-team.github.io/tech-blog/posts/ai-챗봇-답변을-sse와-비동기로-실시간-전달하기/)에서는 AI 답변을 SSE로 한 문장씩 흘려보내고, 메시지 전송은 202로 접수만 하게 전환한 과정을 이야기하였습니다. 괜찮았습니다. 서버가 한 대라면 그걸로 충분합니다.

하지만 V2부터 NeedU BE는 다중 인스턴스 환경으로 바뀌게 됩니다. 따라서 1편 마지막에 남긴 질문, **`POST /messages`를 받은 서버와 SSE 연결이 붙어 있는 서버가 다르면 답변 조각은 어디로 가야 하는가**는 SSE를 운영에 올리기 전에 반드시 풀어야 하는 숙제였습니다.

이번 글은 그 질문에 대한 답, 그중에서도 **이벤트를 보내는 쪽의 이야기**입니다.

## 답변은 A에서 만들어지는데, 연결은 B에 있다

AI 챗봇 화면은 서버에 요청을 두 종류 보냅니다. 대화방에 들어올 때 여는 SSE 연결(`GET /stream`)과, 메시지를 보낼 때마다 보내는 `POST /messages`입니다. 로드밸런서는 이 둘을 각자 알아서 서버에 나눠 줍니다. 그러면 다음과 같은 상황이 발생할 수 있습니다.

![POST는 서버 A로, SSE 연결은 서버 B로 가서 A가 만든 답변 조각이 브라우저에 도착하지 못하는 모습](/images/2026-10-30-ai-chat-redis-pubsub-publish/lost-reply.svg "메시지를 받은 서버 A가 답변을 만들지만, 브라우저와 연결된 SSE는 서버 B의 메모리에 있습니다. A는 그 연결을 쓸 방법이 없습니다.")

SSE 연결은 `SseEmitter`라는 객체로 연결을 받은 서버 B의 메모리 안에 있습니다. 답변은 서버 A의 스레드가 만듭니다. A가 아무리 열심히 답을 만들어도 B의 메모리에 있는 연결에는 손을 댈 수가 없습니다.

사용자 화면에서는 점 세 개만 계속 깜빡이게 됩니다.

![사용자가 메시지를 보낸 뒤 니쥬의 말풍선에 점 세 개만 계속 깜빡이고 답변은 나타나지 않는 화면](/images/2026-10-30-ai-chat-redis-pubsub-publish/waiting-dots.svg "답변은 서버 A에서 잘 만들어지고 있지만, 화면에는 점 세 개만 깜빡입니다.")

또한 같은 대화방을 탭 두 개로 열면 연결이 B와 C에 하나씩 있을 수도 있습니다. 답변을 만드는 서버는 연결이 어디에 몇 개 있는지 알 길이 없습니다.

![같은 대화방을 탭 두 개로 열어 SSE 연결이 서버 B와 C에 하나씩 있고, 답변을 만드는 서버 A는 연결이 어디에 몇 개 있는지 모르는 모습](/images/2026-10-30-ai-chat-redis-pubsub-publish/scattered-connections.svg "같은 12번 대화방이라도 탭마다 연결이 다른 서버에 붙을 수 있습니다. 답변을 만드는 서버 A의 메모리에는 그 정보가 없습니다.")

## 찾아가지 말고, 다 들리게 외치자

그래서 방향을 바꿨습니다. 답변을 만든 서버가 연결을 찾아가는 게 아니라, 모든 서버에 들리게 외치고 연결을 가진 서버가 알아서 받아 가게 하는 겁니다. NeedU는 이미 캐싱 목적으로 Redis를 쓰고 있었으니 Redis Pub/Sub을 메시지 브로커로 활용하였습니다.

![서버 A가 Redis 채널에 발행하면 서버 A, B, C가 모두 받고, 대화방 연결을 가진 서버 B만 브라우저로 보내는 흐름](/images/2026-10-30-ai-chat-redis-pubsub-publish/pubsub-broadcast.svg "답변 조각은 Redis 채널 하나로 모든 서버에 퍼집니다. 그 대화방의 SSE 연결을 가진 서버 B만 브라우저로 보내고, 나머지는 버립니다.")

답변 스레드는 조각이 생길 때마다 Redis 채널에 발행(PUBLISH)만 하고 끝입니다. 모든 서버는 이 채널을 구독하고 있다가, 받은 이벤트의 대화방 연결이 자기한테 있으면 브라우저로 보내고 없으면 버립니다.

바리스타는 음료를 들고 테이블마다 돌아다니며 주문한 사람을 찾지 않습니다. "12번 고객님, 주문하신 음료 나왔습니다" 하고 부르면, 12번 번호표를 가진 사람만 일어나고 나머지는 하던 이야기를 이어 갑니다.

이렇게 구성하고 나니 좋았던 점은 답변을 만드는 쪽이 누가 듣고 있는지 전혀 신경 쓰지 않아도 된다는 것이었습니다. 연결이 어느 서버에 있든, 두 개든, 아예 없든 발행하는 코드는 똑같습니다. 1편에서 이야기한 "나갔다 와도 답이 온다"가 서버 여러 대에서 성립하는 것도 이 덕분입니다. 화면을 나가도 답변 스레드가 끝까지 일하는 건 202 비동기 덕분이지만, 다시 들어와 새로 연 연결이 다른 서버에 붙어도 이어지는 이벤트를 받을 수 있는 건 이벤트를 특정 연결이 아니라 대화방 앞으로 보내기 때문입니다.

다음은 Redis Pub/Sub을 사용하며, 이벤트를 발행하는 곳의 설계를 정한 규약들입니다.

## 채널은 딱 하나만

처음 정한 건 채널을 어떻게 나눌지였습니다. 대화방마다 채널을 따로 만들면 각 서버는 SSE 연결이 생기고 없어질 때마다 구독할 채널을 늘렸다 줄였다 해야 합니다.

그래서 AI 대화 이벤트용 채널은 하나만 두고, 대화방 ID를 메시지 안에 넣었습니다. 실제로 Redis를 지나가는 메시지는 이렇게 생겼습니다.

```json
{
  "conversationId": 12,
  "type": "DELTA",
  "data": { "userMessageId": 345, "index": 3, "text": "보통 언제 달리는 편이에요?" }
}
```

대가는 있습니다. 모든 서버가 모든 대화방 이벤트를 받고, 연결이 없는 서버는 받자마자 버리는 일을 반복합니다. 지금 규모에서는 그 낭비보다 구독 관리를 안 해도 되는 편함이 훨씬 크다 판단했습니다.

### 동일 서버여도 Redis를 거치도록

POST를 받은 서버에 마침 SSE 연결도 있다면, 굳이 Redis를 거치지 않고 바로 보내면 더 빠를 겁니다. 이 지름길은 일부러 만들지 않았습니다.

지름길이 생기면 이벤트가 브라우저까지 가는 길이 두 개가 됩니다. 같은 대화방을 탭 두 개로 열었는데 한 탭은 같은 서버, 한 탭은 다른 서버에 붙어 있다면 한쪽은 지름길로, 한쪽은 Redis로 받게 됩니다. 길마다 지연도 다르고 실패하는 방식도 다르기에, 동작에서 문제가 생겼을 때 원인을 찾기가 훨씬 어려워집니다. 길이 하나면 로컬에서 서버 한 대로 본 동작이 운영의 여러 대 환경에서도 동일하게 발생할 수 있고 결과적으로 문제 해결에도 도움이 될 것이라 생각했습니다.

## 한 턴의 이벤트는 한 곳에서 차례대로

답변 하나는 Redis 메시지 여러 개로 쪼개져서 나갑니다. 조각 순서가 바뀌면 문장이 깨지니, 한 턴의 이벤트는 반드시 한 스레드가 차례대로 발행하게 했습니다.

이 일을 턴마다 하나씩 만드는 `AiChatTurnEvents`라는 작은 객체가 맡습니다. AI 서버에서 조각이 올 때마다 `publishDelta`가 불리고, 조각마다 `index`가 0, 1, 2… 하고 올라갑니다. FE는 이 숫자로 빠지거나 겹친 조각이 없는지 봅니다.

Redis 공식 문서는 "구독자는 메시지를 발행된 순서대로 받는다"고 보장합니다. 따라서 한 스레드가 차례대로 보내기만 하면 각 서버까지는 순서가 지켜집니다. 

- 정확히는 "각 서버의 구독 연결까지"입니다. 그다음, 서버 안에서 브라우저로 내보내는 단계에 순서가 섞이는 문제가 발생할 수 있는데 이는 이어지는 3편에서 다루도록 하겠습니다.

### 한 번 실패하면 그 턴은 더 보내지 않는다

Redis 연결이 잠깐 끊기면 발행이 실패할 수 있습니다. 이때 `AiChatTurnEvents`는 경고 로그를 남기고, 그 턴에 남은 이벤트는 아예 보내지 않습니다.

```java
private void publish(AiChatEventType type, Object data) {
    if (publishFailed) {
        return;
    }
    try {
        publisher.publish(conversationId, type, data);
    } catch (RuntimeException e) {
        publishFailed = true;
        log.warn("AI chat event publish failed. conversationId={}, userMessageId={}, type={}",
                conversationId, userMessageId, type, e);
    }
}
```

중간 조각이 빠진 채로 뒤 조각을 계속 보내면 화면에는 앞뒤가 안 맞는 문장이 그려집니다. 그럴 바엔 멈추고, 화면 복구는 아래에서 이야기할 DB 쪽에 맡기는 게 낫다고 봤습니다. 

대신 발행이 실패해도 답변 생성은 멈추지 않습니다. 끝까지 만들어서 DB에 저장합니다.

## Pub/Sub은 메시지를 잃어버린다

Redis Pub/Sub을 쓰면서 가장 먼저 받아들여야 했던 사실은 이겁니다. 메시지를 보관하지 않습니다. 

발행하는 그 순간 구독 중인 곳에만 전달되고 끝입니다. Redis 문서도 Pub/Sub의 전달 보장을 **"최대 한 번(at-most-once)"**이라고 적어 둡니다. 그 순간 연결이 없던 브라우저는 그 이벤트를 다시 받을 방법이 없습니다.

여기서 1편에서 팀끼리 맞춰 둔 약속이 저희를 살려 줍니다. `delta`는 화면을 미리 채우는 용도일 뿐이고, 진짜 답은 `completed`와 DB에 있다는 약속입니다.

이 약속을 Pub/Sub 전체로 넓혀서, 설계 전체에 깔아 둔 전제가,

**"이벤트는 빨리 보여 주는 용도고, 정답은 DB에 있다"**입니다. 

사용자 메시지는 AI를 부르기 전에 DB에 저장하고, AI 답변도 DB에 저장한 다음에야 `completed`를 발행합니다. 이벤트를 놓친 화면은 다시 연결할 때 메시지 목록 API로 최종 답을 가져옵니다.

### 턴을 끝내는 순서의 중요성

앞선 전제를 지키려다 보니 답변 스레드가 일을 마무리하는 순서에 꽤 신경을 쓰게 됐습니다. 정리할 것은 답변 저장, 그리고 1편에서 만든 대화방 락과 202 전에 남겨 둔 생성 중 표시, 마지막으로 `completed`와 `done` 이벤트입니다.

![답변 DB 저장, 생성 중 표시 삭제, 대화방 락 해제, completed 발행, done 발행 순서로 진행되고, 그 사이 재연결한 화면이 무엇을 보는지 보여 주는 그림](/images/2026-10-30-ai-chat-redis-pubsub-publish/finish-order.svg "답변 스레드가 턴을 끝내는 순서. 어느 순간에 사용자가 다시 들어와도 답변을 놓치지 않도록 맞춘 순서입니다.")

순서 하나하나에 이유가 있습니다.

답변을 먼저 저장하고 생성 중 표시를 지웁니다. 거꾸로 하면 표시는 지워졌는데 답변은 아직 DB에 없는 틈이 생기고, 그 틈에 다시 들어온 화면은 `connected` 이벤트에서 "생성 중 아님"을 보고 목록을 조회했다가 답이 없다고 판단합니다.

생성 중 표시를 지우고 나서 락을 풉니다. 락이 먼저 풀리면, 그 틈에 같은 `clientMessageId`로 들어온 재전송 요청이 남아 있는 생성 중 표시를 보고 "아직 만드는 중"이라며 202를 받는데, 정작 이벤트는 다시 오지 않습니다.

락을 풀고 나서 `completed`를 보냅니다. `completed`가 먼저 가면, 답을 받자마자 다음 메시지를 보낸 사용자가 아직 안 풀린 락 때문에 429를 받습니다.

이렇게 맞춰 두면 사용자가 어느 순간에 다시 들어와도 답변을 놓치는 구간이 없습니다. 저장과 표시 삭제 사이에 들어오면 "생성 중"을 안내받고 곧 `completed`를 받고, 표시 삭제 뒤에 들어오면 목록에서 이미 저장된 답변을 받습니다.

### 실패도 같은 길로 끝낸다

답변 생성이 실패하면 `completed` 대신 `error`를 보내고, 똑같이 `done`으로 턴을 닫습니다. 

정리 순서도 같습니다. `error`에는 FE가 다음에 뭘 할지 고를 수 있게 두 가지 표시를 넣었습니다. 같은 메시지로 다시 보내면 될 수 있다는 `retryable`, AI 세션이 사라져서 이 대화는 이어 갈 수 없다는 `restartRequired`입니다. 앞의 경우 FE는 메시지 옆에 재전송 버튼을 달고, 뒤의 경우 새 대화를 시작하라고 안내합니다.

## 발행자 설계 마무리, 구독자에서의 문제점

돌아보면 발행자 쪽 설계는 결국 "잃어버릴 수 있다"는 걸 숨기지 않는 데서 시작했습니다. Pub/Sub이 이벤트를 잃을 수 있다고 인정하고 나니, 무엇을 꼭 DB에 남겨야 하는지, 어떤 순서로 정리해야 하는지가 자연스럽게 정해졌습니다.

하지만 구독자 측에서 예상 못 한 일이 기다리고 있었습니다. Redis는 분명 순서대로 보내 주는데, 브라우저에 도착한 답변이 이상하게 나타나는 것이었습니다.

자세한 이야기는 이어지는 3편에서 구독자 측 구조를 설계하는 과정에 담도록 하겠습니다. 감사합니다.
