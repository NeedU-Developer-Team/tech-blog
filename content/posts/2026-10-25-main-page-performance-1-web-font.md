안녕하세요, 주라 팀 NeedU 프론트엔드 Juno 입니다!

이 글은 메인페이지 성능 개선 시리즈의 1편입니다. 측정 기준을 세우고 원인을 분석한 과정과, 첫 번째 원인이었던 웹폰트를 개선한 과정을 다룹니다.

## 헤더 아래가 5.7초 동안 비어 있었습니다

NeedU 메인페이지는 로그인한 사용자에게 안내 문구와 추천 상품 3개를 보여 줍니다. 그런데 모바일 환경에서 헤더는 금방 보이는데, 그 아래 콘텐츠가 한참 비어 있다가 나타났습니다. 느린 4G 기준으로 안내 문구가 보이기까지 **5.72초**, 상품 사진까지는 **7.20초**가 걸렸습니다.

![개선 전 메인페이지 로딩 모습. 새로고침 후 헤더만 보이는 빈 화면이 이어지다가 안내 문구와 상품 사진이 나타남](/images/2026-10-25-main-page-performance-1-web-font/before-loading.gif "개선 전 메인페이지 로딩 모습 (느린 4G, CPU 4배 감속)")

### 감으로 고치지 않기 위해 측정 기준부터 정했습니다

처음에는 "폰트가 무거워서 그렇다", "API가 느리다" 같은 추측이 먼저 떠올랐습니다. 하지만 원인이 여러 개 겹쳐 있을 때 감으로 하나씩 고치면, 무엇이 효과가 있었는지 알 수 없습니다. 그래서 코드를 고치기 전에 측정 방법을 먼저 고정했습니다.

| 항목 | 설정 |
|---|---|
| 대상 | dev 서버의 메인페이지 (취향 분석을 마친 계정으로 로그인) |
| 네트워크 | Chrome DevTools `느린 4G` |
| CPU | `4배 감속` |
| 캐시 | `캐시 사용 중지` (첫 방문 조건) |
| 횟수 | 개선 전은 5회 측정 후 중앙값, 이후 단계는 1~2회 측정 |
| Lighthouse | 모바일, 시뮬레이션된 제한, 두 번째 시도부터 단계마다 3회 측정 후 중앙값 |

사용자의 대부분이 모바일이라, 데스크톱이 아니라 느린 회선과 느린 CPU를 기준으로 삼았습니다. 개선 단계는 측정 횟수가 적어, 0.1~0.2초 안팎의 차이는 측정 편차일 수 있다는 점을 감안하고 비교했습니다.

Lighthouse 점수만 보면 "무엇이 언제 보이는지"를 놓치기 쉽습니다. 그래서 사용자가 실제로 느끼는 순간을 기준으로 세 가지 시점을 정했습니다.

| 지표 | 의미 | 측정 방법 |
|---|---|---|
| ① 헤더 | 흰 화면이 끝나고 헤더가 처음 보이는 시점 | 필름스트립 |
| ② 안내 문구 | 헤더 아래 핵심 콘텐츠가 처음 보이는 시점 | 필름스트립 |
| ③ 상품 사진 | 추천 상품 사진 3장이 모두 보이는 시점 | HAR의 마지막 상품 이미지 응답 완료 시점 |

필름스트립은 "언제 보였는지"를, HAR은 요청 순서·우선순위·대기 시간을 통해 "왜 그때 보였는지"를 알려 줍니다. 여기에 Lighthouse(모바일, 시뮬레이션된 제한) 결과를 함께 남겼습니다.

| 지표 | 개선 전 |
|---|---|
| ① 헤더 | 1.86s |
| ② 안내 문구 | 5.72s |
| ③ 상품 사진 | 7.20s |
| Lighthouse 성능 점수 | 74 |
| Lighthouse LCP | 9.49s |

### HAR로 찾은 원인 다섯 가지

개선 전 HAR을 시간 순서대로 따라가 보니, 콘텐츠가 늦게 보이는 이유는 하나가 아니었습니다.

| 원인 | 내용 |
|---|---|
| 1. 웹폰트 | 두 굵기의 폰트 파일 약 **972kB**가 초기 JS와 같은 시간대에 받아짐 |
| 2. 분석 스크립트 | 초기 JS와 대역폭을 나눠 씀 |
| 3. 클라이언트 데이터 요청 | JS 실행이 끝난 뒤에야 API를 요청함 |
| 4. 순차 요청 | 안내 문구 응답 이후에야 추천 상품을 요청함 |
| 5. 상품 이미지 | CSS 배경 이미지라 브라우저가 늦게 발견함 |

그중 가장 먼저 눈에 띈 것은 웹폰트였습니다. 페이지를 여는 데 필요한 JS보다 폰트 파일이 훨씬 컸고, 폰트 다운로드가 끝나는 데만 약 9.7초가 걸렸습니다. 1편에서는 이 웹폰트 문제를 다루고, 나머지 원인은 2편에서 다룹니다.

![개선 전 HAR 폭포 차트. 폰트 2개의 다운로드가 초기 JS와 같은 시간대에 진행됨](/images/2026-10-25-main-page-performance-1-web-font/before-har.png "개선 전 폰트와 초기 JS 요청. 개발자 도구는 1kB를 1,000바이트로 표시해 합계가 본문 값보다 조금 크게 보입니다")

## 웹폰트를 줄이기까지의 다섯 번의 시도

웹폰트 문제를 해결하기 위해 다섯 번 시도했습니다. 효과가 없거나 오히려 느려진 시도도 있어, 순서대로 모두 정리했습니다.

### 첫 번째 시도. preload를 껐더니 오히려 느려졌습니다

처음 시도한 방법은 단순했습니다. Next.js의 `next/font`가 넣어 주는 폰트 `preload`가 초기 JS와 대역폭을 다툰다고 보고, preload를 꺼서 폰트를 나중에 받게 했습니다.

결과는 반대였습니다.

| 항목 | 개선 전 (preload 사용) | preload 끔 |
|---|---|---|
| 폰트 요청 시작 | 0.63s | 1.32s |
| 폰트 우선순위 | 높음 (High) | **가장 높음 (VeryHigh)** |
| 초기 JS 다운로드 완료 | 4.69s | **5.22s** |

preload를 끄더라도 폰트는 사라지지 않습니다. CSS를 해석하다가 폰트가 필요하다는 것을 알게 되면, 브라우저는 그 폰트를 **가장 높음** 우선순위로 요청합니다. 반면 Next.js의 초기 JS는 `async` 스크립트라 **낮음** 우선순위입니다. 폰트를 받는 시점이 조금 늦어졌을 뿐, 오히려 더 높은 우선순위로 회선을 차지해 JS가 약 0.5초 더 늦어졌습니다.

이 변경은 바로 되돌렸습니다. 대신 "언제 받느냐"보다 **"얼마나 받느냐"**를 먼저 줄여야 한다는 방향을 얻었습니다.

### 두 번째 시도. woff2로 바꿔 용량은 줄었지만, 화면은 그대로였습니다

먼저 폰트를 `next/font`에 맡기지 않고 직접 관리하도록 바꿨습니다. 원본 폰트를 압축 효율이 좋은 woff2로 바꾸고, `@font-face`를 직접 작성했습니다. 폰트 파일에는 1년 캐시(`immutable`) 헤더를 붙였습니다.

작업 중 함정도 하나 발견했습니다. 인증을 확인하는 proxy(미들웨어)가 `/fonts` 경로까지 가로채, 폰트 요청을 로그인 페이지로 돌려보내고 있었습니다. 정적 파일 경로를 proxy 대상에서 제외해 해결했습니다.

| 항목 | 개선 전 | woff2 전환 |
|---|---|---|
| 폰트 전송량 | 972kB (2개) | 572kB (2개) |
| 폰트 다운로드 완료 | 9.68s | 7.37s |

폰트는 약 40% 가벼워졌지만, 화면 지표는 거의 바뀌지 않았습니다. 형식이 바뀌어도 한글 폰트 한 벌을 통째로 받는 구조는 그대로였기 때문입니다.

### 세 번째 시도. 글자 범위별로 나누자 처음으로 화면이 빨라졌습니다

한글 폰트는 글자 수가 많아 파일이 큽니다. 하지만 한 화면에 쓰이는 글자는 그중 일부입니다. 그래서 폰트를 글자 범위별 조각으로 나누고, `unicode-range`로 화면에 필요한 조각만 받게 했습니다.

조각을 나누는 기준은 Google Fonts의 Noto Sans KR이 쓰는 124개 범위를 참고했습니다. 자주 쓰이는 글자끼리 묶여 있어, 한 화면에 필요한 조각 수가 적게 나옵니다. 분할 작업은 fontTools(`pyftsubset`) 기반 스크립트로 만들어 저장소에 함께 남겼고, 폰트 버전이 바뀌어도 다시 만들 수 있게 했습니다.

```css
@font-face {
  font-family: "Kakao Small Sans";
  src: url("/fonts/KakaoSmallSans-Regular-v2.002.94.woff2") format("woff2");
  font-weight: 400;
  font-style: normal;
  font-display: swap;
  unicode-range: U+ac00-ac0b, U+ac0d-ac19 /* 일부 */;
}
```

폰트는 SIL OFL 1.1 라이선스라 분할·변환이 허용되지만, 저작권·라이선스 정보를 지우면 안 됩니다. 조각마다 이름 테이블을 유지했고, 조각의 글자를 모두 합치면 원본과 같은지 스크립트에서 검증했습니다.

| 항목 | 개선 전 | woff2 전환 | 글자 범위 분할 |
|---|---|---|---|
| 폰트 요청 | 2개 | 2개 | 화면에 필요한 조각만 (12~17개) |
| 폰트 전송량 | 972kB | 572kB | **약 100~140kB** |
| ② 안내 문구 | 5.72s | 약 6.0s | **4.37s** |
| ③ 상품 사진 | 7.20s | 7.22s | **6.13s** |
| Lighthouse 점수 | 74 | 78 | 79 |

### 네 번째 시도. 폰트 CSS를 분리했더니 안내 문구가 다시 늦어졌습니다

조각이 많아지면서 `@font-face` 정의만 모아도 CSS가 커졌습니다. 이 정의가 앱 전체 CSS 안에 있으면, 화면을 그리기 전에 반드시 받아야 하는 렌더링 차단 CSS가 그만큼 무거워집니다.

그래서 폰트 정의를 별도 CSS 파일로 분리하고, 화면 표시를 막지 않는 방식으로 불러왔습니다. 인쇄용(`media="print"`)으로 먼저 받은 뒤, 다운로드가 끝나면 화면용으로 바꾸는 방식입니다.

```js
(function () {
  var link = document.createElement("link");
  link.rel = "stylesheet";
  link.href = "/fonts/kakao-small-sans-v2.002.css";
  link.media = "print";
  link.onload = function () {
    link.media = "all";
  };
  document.head.appendChild(link);
})();
```

그런데 결과가 이상했습니다. 헤더(①)는 1.37초로 빨라졌지만, 안내 문구(②)는 오히려 4.81초로 늦어졌습니다.

### 다섯 번째 시도. 인라인 스크립트 위치를 옮겨 대기열을 없앴습니다

HAR을 다시 보니, 초기 JS 요청들이 출발하지 못하고 **약 0.7초 동안 대기열에 묶여** 있었습니다. 원인은 로더 스크립트의 **위치**였습니다.

브라우저는 `<head>` 안에서 스타일시트 뒤에 있는 일반 인라인 스크립트를 만나면, 그 스크립트가 스타일을 읽을 수도 있기 때문에 **앞선 CSS가 다 받아질 때까지 실행을 미룹니다**. 그동안 HTML 해석도 멈추고, Chrome은 해석이 `<head>`에 머무는 동안 낮은 우선순위 요청을 보류합니다. 폰트 로더 한 줄 때문에 초기 JS 전체가 늦게 출발한 것입니다.

로더를 `<body>` 끝으로 옮겨 HTML 해석을 막지 않게 했습니다.

| 항목 | 폰트 CSS 분리 (네 번째) | 로더 위치 이동 (다섯 번째) |
|---|---|---|
| 초기 JS 요청 대기 시간 | 약 708ms | 약 7ms |
| 가장 큰 JS 다운로드 완료 | 4.05s | 3.66s |
| ① 헤더 | 1.37s | 1.76–1.81s |
| ② 안내 문구 | 4.81s | 4.33–4.48s |
| ③ 상품 사진 | 6.50s | 6.09–6.16s |

![네 번째와 다섯 번째 시도의 가장 큰 초기 JS 요청 타이밍. 대기열 시간이 707ms에서 7ms로 줄어듦](/images/2026-10-25-main-page-performance-1-web-font/s3-s4-queue.png "가장 큰 초기 JS 요청의 타이밍 비교. 대기열 707.42ms에서 7.18ms로 줄었습니다")

## 972kB에서 140kB로, 그리고 남은 과제

| 단계 | ① 헤더 | ② 안내 문구 | ③ 상품 사진 | Lighthouse 점수 / LCP |
|---|---|---|---|---|
| 개선 전 | 1.86s | 5.72s | 7.20s | 74 / 9.49s |
| 두 번째 시도: woff2 전환 | – | 약 6.0s | 7.22s | 78 / 6.14s |
| 세 번째 시도: 글자 범위 분할 | 2.38s | 4.37s | 6.13s | 79 / 5.52s |
| 네 번째 시도: 폰트 CSS 분리 | 1.37s | 4.81s | 6.50s | – |
| 다섯 번째 시도: 로더 위치 이동 | 1.76–1.81s | 4.33–4.48s | 6.09–6.16s | 80 / 5.21s |

웹폰트만으로 안내 문구는 약 1.3초, 상품 사진은 약 1.1초 빨라졌고, Lighthouse LCP는 9.49초에서 5.21초로 줄었습니다. 받는 폰트는 972kB에서 약 140kB로 줄었습니다.

하지만 안내 문구가 4초 넘게 걸리는 문제는 여전했습니다. 남은 병목은 폰트가 아니라 "JS가 끝나야 데이터 요청이 시작되는 구조"였습니다. 이 이야기는 2편에서 이어가겠습니다.
