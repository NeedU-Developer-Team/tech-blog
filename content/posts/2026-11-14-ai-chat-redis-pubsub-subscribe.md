2편 후반부에서 말씀드린 것처럼, 이 포스트에서의 작업은 이상한 현상 하나에서 시작했습니다.

Redis는 분명 순서대로 보내 주는데.. 가끔 AI 답변 조각이 섞여서 도착할 수 있었습니다.

![](/images/2026-11-14-ai-chat-redis-pubsub-subscribe/send-vs-receive-order.svg "")

알아보기 쉽게 글자로 나눴지만, 1편에서 말했듯 실제 `delta` 하나는 대략 문장 하나입니다.

**문장의 순서가 이렇게 뒤바뀐다**고 생각하시면 됩니다.

최종 답까지 틀어지지는 않습니다. 1편에서 정한 약속대로 `completed`에는 완성된 답변 전체가 들어 있어, 마지막에 덮어쓰면 화면은 바른 답으로 돌아옵니다.

하지만 그때까지 사용자는 앞뒤가 뒤바뀐 답변을 읽다가, 마지막에 문장들이 완성되게 바뀐 화면을 보게 됩니다. 조각 단위로 **자연스럽게 보여 주겠다**는 1편의 목표가 **정작 그 조각에서 무너지는 것**입니다.

## 다시 살펴본 발행 구조

답변 조각 하나가 브라우저로 가기까지는 다음의 절차를 거칩니다.

- 서버 A의 답변 스레드가 Redis에 발행하고..
- Redis가 모든 서버에 전달하고..
- 서버 B가 받은 메시지를 리스너 코드에 넘기고..
- 리스너가 SSE 연결에 `send()`하고..
- 마지막으로 브라우저가 이를 받습니다.

이 중 앞의 두 단계는 2편에서 이미 확인했습니다.

보내는 쪽은 `AiChatTurnEvents`가 한 스레드에서 차례대로 발행하고, Redis는 공식 문서에서 다음과 같이 순서를 보장합니다.

> Subscribers receive the messages in the order that the messages are published.

즉, **서버 B의 구독 연결까지는 순서가 지켜집니다.**

따라서 문제는 그다음, 서버 B 안에서 받은 메시지를 리스너에 넘기고 브라우저로 쓰는 구간에 있었습니다.

## 순서를 섞은 건 메시지마다 새로 뜨는 스레드

Spring에서 Redis 채널을 구독할 때는 `RedisMessageListenerContainer`를 사용합니다.

이 컨테이너는 메시지를 받으면 직접 처리하지 않고, 실행기(executor)에 넘겨 리스너 코드를 실행합니다. 메시지를 받는 일과 처리하는 일을 나눠 둔 구조입니다.

저희는 알림 기능과 함께 쓰기 위해 처음 만든 공통 설정에서 이 실행기를 따로 지정하지 않았었습니다. 때문에 자연스럽게 컨테이너는 기본값인 `SimpleAsyncTaskExecutor`를 사용하는 구조였습니다.

`SimpleAsyncTaskExecutor`는 이름 그대로 작업마다 새 스레드를 띄우는 실행기입니다. 스레드를 재사용하지 않고, 동시에 띄울 수 있는 스레드 수에도 제한이 없습니다.

![](/images/2026-11-14-ai-chat-redis-pubsub-subscribe/shuffle.svg "")

조각 다섯 개가 연달아 오면 스레드 다섯 개가 거의 동시에 만들어집니다.

문제는 여기서 발생합니다. **스레드가 만들어진 순서와 실제로 실행되는 순서는 다를 수 있습니다.**

다섯 스레드는 모두 같은 SSE 연결에 `send()`를 호출합니다. `SseEmitter`는 쓰기를 잠금으로 보호하기 때문에 동시에 쓰지는 않지만, 잠금을 먼저 잡은 스레드가 먼저 쓰게 됩니다.

같은 설정을 쓰던 알림에서는 이 문제가 크게 드러나지 않았습니다.

알림은 하나하나가 독립된 이벤트라, 순서가 바뀌어도 목록에 각자 들어가면 그만이기 때문입니다.

반면 AI 답변 조각은 **순서가 곧 내용**이라 이 기본값이 맞지 않았습니다.

### 답변 내용 순서보다 중요한 문제

원인을 찾고 나니 더 위험한 시나리오도 보였습니다.

**브라우저가 데이터를 읽지 않아 `send()`가 멈춘다면 어떻게 될까요?**

그 연결로 가는 조각마다 스레드가 새로 생기고, 이 스레드들은 끝나지 못한 채 계속 쌓입니다.

`SimpleAsyncTaskExecutor`의 스레드는 가상 스레드가 아니기에 하나하나가 메모리를 차지합니다. 

이렇게 쌓이다 스레드 한도에 닿으면 JVM은 `OutOfMemoryError: unable to create native thread`를 던지고, 그때부터는 AI 대화뿐 아니라 서버 전체가 새 스레드를 만들 수 없게 됩니다.

그렇다고 실행기 설정을 바꾸는 것만으로는 문제가 해결되지 않았습니다. 스레드 수에 상한을 걸면, 메시지를 넘겨주던 쪽이 막히게 되고, 넘친 작업을 버리게 하면 답변 조각이 사라지게 됩니다.

## 그럼 스레드 하나로 하면 되지 않나?

원인이 "스레드가 여러 개"라면, 가장 먼저 떠오르는 방법은 스레드를 하나로 줄이는 것입니다.

실제로 처음엔 그렇게 수정했습니다. 실행기를 스레드 1개짜리로 바꾸고, 그 스레드가 메시지를 받아 대화방의 연결들에 차례로 `send()`하게 했습니다.

```java
executor.setCorePoolSize(1);
executor.setMaxPoolSize(1);

// 수신 스레드가 그대로 실행
emitters.forEach(emitter -> emitter.send(event)); // 소켓 쓰기까지 이 스레드가 직접 한다
```

스레드가 하나이니 받은 순서대로 쓰고, 순서 문제는 깔끔하게 사라집니다.

> 스레드 하나로 처리

순서만 보면 올바른 방향이었습니다. 하지만 위 코드의 주석을 다시 보면 꺼름직한 부분이 하나 있습니다.

**소켓 쓰기까지 이 하나의 스레드가 직접 수행한다**는 점입니다.

---

## 하나가 안 읽으면 전체가 멈춘다

`send()`는 생각보다 쉽게 멈춥니다.

서버가 쓴 데이터는 OS의 소켓 송신 버퍼에 들어갔다가 네트워크로 나갑니다. 그런데 망이 끊긴 휴대폰이나 덮어 둔 노트북처럼 브라우저가 데이터를 읽지 않으면 버퍼가 비워지지 않습니다.

버퍼가 가득 차면, 다음에 쓰려는 스레드는 자리가 날 때까지 기다려야 합니다.

스레드 하나 구조에서는 이 기다림이 **하나뿐인 수신 스레드**에서 일어납니다.

![수신 스레드 하나가 읽지 않는 브라우저 B에 쓰다가 멈추고, 그 뒤로 브라우저 A와 C의 이벤트, 다른 대화방 이벤트가 수신 대기열에 계속 쌓이는 모습](/images/2026-11-14-ai-chat-redis-pubsub-subscribe/single-thread-blocking.svg "브라우저 B가 읽지 않아 send()가 멈추면, 수신 스레드가 하나뿐이라 A와 C, 다른 대화방의 이벤트까지 전부 뒤에서 기다립니다.")

브라우저 B 하나 때문에 이 서버로 들어오는 모든 AI 대화 이벤트가 줄을 서서 기다리게 됩니다. 즉 이렇게 맨 앞 하나가 막혀 뒤가 전부 움직이지 못하는 **head-of-line blocking** 문제가 발생한 것입니다.

그렇다고 다른 서버가 대신 보내 주는 것도 불가능했습니다.

브라우저의 SSE 연결은 처음 붙은 서버 한 대에만 있기 때문입니다. 게다가 연결이 끊긴 것은 아니라서 브라우저가 다른 서버로 다시 연결하지도 않습니다. 사용자 화면은 아무 오류 없이 멈춰 있게 됩니다.

물론 자주 생기는 일은 아닙니다. 이벤트 하나가 수백 바이트 정도라 버퍼가 차려면 꽤 많이 쌓여야 합니다. 하지만 한 번 생기면 그 서버에 붙은 모든 사용자의 AI 답변이 멈춥니다. 또한 AI 서버가 조각을 잘게 나눠 보낼수록 버퍼는 더 빨리 차는 **외부 시스템에 의존한 장애 발생 지점**이 생긴 것입니다.

그렇다고 멈춘 스레드 대신 다른 스레드가 다음 메시지를 처리하게 하면, 스레드가 다시 여러 개가 되면서 순서 문제가 또 발생하게 됩니다.

결국 저희는 다음 두 가지를 동시에 보장하여야, 올바른 시스템 동작이 이루어짐을 인지할 수 있었습니다.

- **같은 연결 안에서는 앞 이벤트가 끝날 때까지 기다린다.**
- **다른 연결은 그와 상관없이 계속 보낸다.**

## 받는 일과 쓰는 일의 역할 분리

결과적으로 단일 스레드 구조의 문제는 스레드가 하나라는 사실이 아니었습니다.

**오래 걸릴 수 있는 소켓 쓰기를 수신 스레드가 직접 한다는 것**이 문제였습니다.

그래서 답변 조각을 받는 일과 이를 클라이언트에 보내주는 일을 분리하였고, 지금의 구조가 완성되었습니다.

![](/images/2026-11-14-ai-chat-redis-pubsub-subscribe/per-connection-queue.svg "")

먼저 AI 대화 전용 리스너 컨테이너를 따로 만들고, 수신 스레드를 1개로 고정했습니다. (공통 컨테이너는 원래대로 돌려놓아 알림 기능에는 영향이 없도록 했습니다.)

수신 스레드는 받은 이벤트를 연결마다 있는 대기열에 넣기만 하고, 바로 다음 메시지로 넘어갑니다.

쓰기 작업은 연결마다 동시에 딱 하나만 돌며, 가상 스레드에서 실행됩니다. 이 작업이 대기열 앞에서부터 이벤트를 꺼내 `send()`합니다.

한 연결의 대기열에 이벤트가 1,000개 넘게 쌓이면 그 연결만 닫습니다. 끊긴 화면은 `EventSource`가 다시 연결하고, 2편에서 말한 대로 메시지 목록 API로 DB에 저장된 답을 가져옵니다.

정리하면 다음과 같습니다.

- 수신 스레드는 대기열에 넣기만 하니 금방 끝나고, 하나뿐이니 받은 순서가 그대로 보장
- 한 연결 안에서는 쓰기 작업이 하나뿐이라 순서가 섞이지 않음
- 느린 연결은 자기 대기열에서만 기다리고, 다른 연결에는 영향을 주지 않음

```java
void enqueue(SseEmitter.SseEventBuilder event) {
    if (!pendingEvents.offer(event)) {                 // 상한 초과면 이 연결만 닫는다
        close();
        sendExecutor.execute(emitter::complete);
        return;
    }
    if (sending.compareAndSet(false, true)) {          // 쓰는 작업이 없을 때만 새로 시작
        sendExecutor.execute(this::sendPendingEvents);
    }
}
```


플로우를 설계한 뒤 적용하였으나, 사실 위와 같은 구조는 찾아보니 이미 널리 쓰이는 방식이었습니다.

Java `Executor` 공식 문서의 `SerialExecutor` 예제가 거의 같은 모양이고, Spring WebSocket(STOMP)도 문서에서 느린 클라이언트를 같은 방식으로 다룬다고 설명합니다.

- **연결 안에서는 순서대로, 연결끼리는 독립적으로, 버퍼에는 상한을 두는 것**

## 수신 구조의 변화

지금까지의 과정을 정리하면, 구독자 쪽 구조는 다음 세 단계를 거쳐 지금의 모습이 되었습니다.

![](/images/2026-11-14-ai-chat-redis-pubsub-subscribe/before-after.svg "")

**1. 메시지마다 새 스레드를 띄우던 구조**

처음에는 조각마다 스레드가 새로 떠서, 먼저 잠금을 잡은 스레드가 먼저 썼습니다.

때문에 A의 화면에는 "녕하요안세"처럼 순서가 섞인 답변이 그려졌고,

B에게 보내려던 스레드는 끝나지 못한 채 계속 쌓였습니다.

**2. 스레드 하나로 처리하던 구조**

스레드를 하나로 줄이자 순서 문제는 사라졌습니다.

하지만 그 스레드가 B에게 쓰다가 멈추자, 뒤에 있던 A의 이벤트까지 전부 멈춰 버렸습니다.

A는 아무 문제가 없는데도 "안" 한 글자에서 답변이 멈춘 것입니다.

**3. 받는 일과 쓰는 일을 나눈 지금 구조**

수신 스레드가 이벤트를 연결별 대기열에 넣기만 하고, 쓰기는 연결마다 따로 진행합니다.

A는 "안녕하세요"를 보낸 순서 그대로 받습니다.

B의 이벤트는 B의 대기열에서만 기다리고, 1,000개를 넘기면 그 연결만 닫힙니다.

B 역시 다시 들어오면 메시지 목록 API로 완성된 답변을 받아 볼 수 있습니다.

| | 메시지마다 새 스레드 | 스레드 하나 | 받기 · 쓰기 분리 |
| --- | --- | --- | --- |
| 답변 순서 | 섞임 | 지켜짐 | 지켜짐 |
| 느린 연결이 생기면 | 스레드가 끝없이 쌓임 | 수신 스레드가 멈춤 | 그 연결만 기다림 |
| 다른 사용자에게 주는 영향 | 서버 전체 스레드 고갈 위험 | 같은 서버의 모든 답변이 멈춤 | 없음 |

결과적으로 같은 서버에 느린 사용자가 있든 없든,

사용자는 AI 답변을 **보낸 순서 그대로, 끊김 없이** 받을 수 있게 되었습니다.

---

다시 앞선 생각으로 돌아가 보겠습니다.

> "그냥 스레드 하나로 처리하면 되지 않나?"

순서만 놓고 보면 지금의 구조와 단일 스레드, 두 방식은 같습니다.

차이는 **느린 연결 하나가 서버 한 대의 전달 전체를 멈출 수 있느냐**에 있습니다.

저희 SSE는 서블릿의 블로킹 쓰기를 사용하기 때문에 이런 일이 실제로 생길 수 있었고, 이를 막는 데 든 비용은 오직 클래스 하나와 테스트 몇 개였습니다.
