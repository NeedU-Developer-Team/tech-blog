안녕하세요, NeedU 프론트엔드 개발자 김주희입니다.

긴 목록을 한참 내려가다 보면 스크롤이 조금씩 무거워지는 느낌, 받아 보신 적 있으신가요? 처음에는 부드럽던 화면이 어느 순간 뚝뚝 끊기기 시작하는 그런 느낌이요.

[3편](https://needu-developer-team.github.io/tech-blog/posts/product-list-performance-3-back-restore/)에서는 상품을 보고 돌아와도 보던 위치로 이어 볼 수 있게 만들었는데요. 그 과정에서 목록 높이가 10,000px을 넘어가는 것을 보며 걱정이 하나 생겼습니다. 이번 4편에서는 그 걱정, **상품이 계속 쌓이는 목록**을 다뤄 보려고 해요.

## 상품은 계속 쌓이는데, 카드는 지워지지 않았습니다

NeedU에서는 취향 분석을 확정할 때마다 새로운 추천 상품이 기존 목록에 **더해집니다.** 분석을 여러 번 하면 목록은 그만큼 길어지고, 정해진 상한도 없습니다.

목록은 무한 스크롤로 20개씩 불러옵니다. 문제는 불러온 카드를 **한 번도 지우지 않고** 모두 화면에 남겨 두고 있었다는 점입니다. 100번째 줄을 보고 있어도 1번째 줄부터 99번째 줄까지의 카드가 그대로 남아 있었습니다.

![카드가 쌓이는 구조. 무한 스크롤로 20개씩 불러온 카드가 지워지지 않고 계속 쌓여, 200장일 때보다 5,000장일 때 화면에 남아 있는 카드와 DOM 노드가 훨씬 많다. 실제로 화면에 보이는 카드는 한 화면 분량뿐이다](/images/2026-11-26-product-list-performance-4-virtual-scroll/card-accumulation.svg "불러온 카드가 모두 남아 있어, 보이는 것보다 훨씬 많은 카드를 들고 있었습니다.")

브라우저는 화면에 있는 요소를 **DOM 노드**라는 단위로 관리합니다. 카드 하나에도 이미지, 이름, 가격 같은 요소가 여러 개 들어 있어서, 카드가 쌓일수록 DOM 노드도 함께 늘어납니다. DOM 노드가 많으면 메모리를 많이 쓰고, 화면을 다시 계산하고 그리는 데에도 시간이 더 걸립니다.

## 얼마나 무거운지부터 쟀습니다

이번에도 바로 고치지 않고 먼저 쟀습니다. 상한 없이 쌓이는 상황을 재현하려고 측정용 목업 상품을 5,000개로 늘렸고, 카드를 200장, 1,000장, 5,000장까지 불러온 지점에서 각각 값을 기록했습니다.

측정은 로컬 프로덕션 빌드에서 390×844 화면, CPU 4배 감속, 느린 4G 조건으로 진행했습니다. 목업 상품 수가 바뀌면서 목록 구성도 달라져, 1~3편의 수치와는 직접 비교하지 않고 이번 기준값을 새로 쟀습니다.

| 카드 수 | DOM 노드 | 메모리 (힙 스냅샷) | 상세에서 돌아오는 시간 |
| --- | --- | --- | --- |
| 200장 | 2,274개 | 22.1MB | 263ms |
| 1,000장 | 10,274개 | 51.1MB | 938ms |
| 5,000장 | **50,271개** | **193MB** | **5,038ms** |

숫자가 보여 주는 것은 분명했습니다. **카드 수가 늘어나는 만큼 모든 비용이 함께 늘어났습니다.** 5,000장에서는 DOM 노드가 5만 개를 넘었고, 상세에서 돌아와 목록이 다시 그려지기까지 5초가 걸렸습니다. 사용자 입장에서는 뒤로가기를 눌렀는데 화면이 5초 동안 멈춰 있는 셈입니다.

2편에서 썼던 `memo`처럼 "다시 그리지 않아도 되는 카드를 건너뛰는" 방법으로는 이 문제를 풀 수 없었습니다. 건너뛰더라도 카드 자체는 여전히 화면에 남아 있기 때문입니다. 필요한 것은 **보이지 않는 카드를 아예 화면에서 빼는 것**이었습니다.

## 보이는 곳만 그리는 가상 스크롤

이럴 때 쓰는 방법이 **가상 스크롤(virtual scroll)**입니다. 목록 전체의 높이는 그대로 유지하되, 실제로는 **화면에 보이는 부분과 그 근처만** 그리는 방식입니다.

![가상 스크롤 개념. 목록 전체 높이는 5,000장 기준으로 유지하지만, 실제로 그리는 것은 지금 보이는 화면과 위아래 몇 줄뿐이다. 나머지는 빈 공간으로 높이만 차지하고, 스크롤하면 그리는 줄이 바뀐다](/images/2026-11-26-product-list-performance-4-virtual-scroll/virtual-window.svg "전체 높이는 그대로 두고, 보이는 화면 근처의 줄만 그립니다.")

스크롤바와 전체 길이는 5,000장 그대로라서 사용자는 차이를 느끼지 못합니다. 하지만 브라우저가 실제로 들고 있는 카드는 화면 근처의 몇 줄뿐이라, 카드가 아무리 쌓여도 그리는 양은 거의 일정하게 유지됩니다.

### 바로 라이브러리를 고르지는 않았습니다

가상 스크롤을 만드는 방법은 여러 가지였습니다. 고르는 기준은 두 가지로 정했습니다.

> 지금의 카드 디자인과 3열 그리드를 그대로 쓸 수 있는가, 그리고 3편에서 만든 스크롤 복원과 맞물릴 수 있는가

**react-window, react-virtuoso: 많이 쓰이지만, 우리 구조와는 맞지 않았습니다.** 사용 사례가 많고 목록 컴포넌트까지 제공해 주지만, 목록이 **자기만의 스크롤 영역**을 갖는 것을 전제로 합니다. 3편에서 말씀드린 것처럼 NeedU는 레이아웃의 가운데 영역이 스크롤되는 구조라, 이 구조와 3열 그리드에 맞추려면 손볼 곳이 많았습니다.

**직접 구현: 의존성은 없지만, 직접 챙길 것이 많았습니다.** 보이는 줄 계산, 스크롤 위치 보정, 화면 밖 여유분 처리를 모두 직접 만들어야 합니다. 경계 상황이 많은 만큼 놓치는 부분이 생기기 쉬웠습니다.

**CSS `content-visibility`: 코드는 거의 안 바뀌지만, 메모리는 그대로입니다.** 화면 밖 요소의 그리기를 브라우저가 건너뛰게 하는 CSS 속성입니다. 그리기 비용은 줄지만 DOM 노드 자체는 그대로 남아 있어서, 메모리 문제는 풀지 못합니다.

**TanStack Virtual: 계산만 맡고, 그리는 방식은 그대로 둡니다.** 화면을 직접 그리지 않고 "몇 번째 줄을 어디에 놓을지"만 계산해 주는 라이브러리입니다. 그래서 기존 카드와 그리드를 그대로 쓸 수 있고, 목록 바깥의 스크롤 영역을 지정하는 옵션(`getScrollElement`, `scrollMargin`)도 있었습니다. 1편에서 도입한 TanStack Query와 같은 곳에서 만든 라이브러리라 사용 방식도 익숙했습니다.

| 방법 | 기존 카드·그리드 | 가운데 영역 스크롤 | 메모리 개선 |
| --- | --- | --- | --- |
| react-window, react-virtuoso | 맞추기 어려움 | 맞추기 어려움 | 됨 |
| 직접 구현 | 그대로 | 직접 처리 | 됨 |
| `content-visibility` | 그대로 | 상관없음 | 한계 있음 |
| **TanStack Virtual** | **그대로** | **옵션으로 지원** | **됨** |

그래서 **TanStack Virtual**을 골랐습니다.

## 세 장씩 한 줄로 묶었습니다

가상 스크롤 라이브러리는 기본적으로 **한 줄에 항목 하나**인 목록을 다룹니다. 그런데 NeedU의 상품 목록은 한 줄에 카드가 세 장씩 들어가는 3열 그리드입니다.

그래서 카드를 세 장씩 묶어 **한 줄을 항목 하나**로 다루도록 했습니다. 카드 5,000장이면 약 1,667줄이 되고, 라이브러리는 이 줄들 중 화면 근처의 줄만 그리도록 알려 줍니다.

![줄 단위 가상화. 카드 세 장을 한 줄로 묶어 줄 하나를 가상 항목으로 다룬다. 화면에 보이는 줄과 위아래 4줄씩만 그리고, 나머지 줄은 높이만 차지한다](/images/2026-11-26-product-list-performance-4-virtual-scroll/row-grouping.svg "카드 세 장을 한 줄로 묶고, 화면 근처의 줄만 그립니다.")

빠르게 스크롤할 때 빈 화면이 보이지 않도록, 화면 위아래로 4줄씩 더 그려 두었습니다(`overscan`).

```tsx
const virtualizer = useVirtualizer({
  count: rowCount,                                  // 카드 수가 아니라 줄 수
  getScrollElement: () => gridRef.current?.closest(SCROLL_AREA_SELECTOR) ?? null,
  estimateSize: () => rowHeight ?? ESTIMATED_ROW_HEIGHT_PX,
  gap: ROW_GAP_PX,                                  // 줄 사이 간격 20px
  overscan: ROW_OVERSCAN,                           // 화면 위아래로 4줄씩 더 그림
  scrollMargin,                                     // 목록 위 영역의 높이
});
```

### 목록 위의 영역만큼 위치를 보정했습니다

여기서 한 가지 더 맞춰야 할 것이 있었습니다. 스크롤되는 가운데 영역에는 목록만 있는 게 아니라, 그 위에 탭, 추천 대상, 예산, 카테고리 영역이 먼저 있습니다.

라이브러리는 스크롤 영역의 맨 위를 0으로 계산하는데, 실제 목록은 그보다 아래에서 시작합니다. 이 차이를 알려 주지 않으면 보이는 줄을 잘못 계산하게 됩니다. 그래서 목록 위 영역의 높이를 `scrollMargin`으로 넘겨 주었습니다.

![목록 위 영역 보정. 가운데 스크롤 영역 안에서 탭, 추천 대상, 카테고리 영역 아래부터 목록이 시작한다. 이 높이를 scrollMargin으로 알려 주어 라이브러리가 목록 시작 위치를 기준으로 보이는 줄을 계산하게 한다](/images/2026-11-26-product-list-performance-4-virtual-scroll/scroll-margin.svg "목록 위 영역의 높이(scrollMargin)만큼 계산 기준을 옮겨 줍니다.")

예산 슬라이더가 나타나는 등 위 영역의 높이는 바뀔 수 있어서, `ResizeObserver`로 크기 변화를 지켜보다가 다시 계산하도록 했습니다.

## 모든 줄의 높이를 같게 만들었습니다

가상 스크롤에서 가장 까다로운 부분은 **줄의 높이**입니다. 그리지 않은 줄도 높이는 알아야 전체 길이와 각 줄의 위치를 계산할 수 있기 때문입니다.

그런데 상품 카드는 줄마다 높이가 달랐습니다. 상품명이 한 줄인 카드와 두 줄인 카드가 섞여 있어서, 같은 줄의 카드 중 가장 긴 상품명에 따라 줄 높이가 달라졌습니다.

![줄 높이 통일. 상품명이 한 줄인 카드와 두 줄인 카드가 섞이면 줄마다 높이가 달라진다. 상품명 영역을 항상 두 줄 높이로 확보하면 모든 줄의 높이가 같아진다](/images/2026-11-26-product-list-performance-4-virtual-scroll/fixed-row-height.svg "상품명 영역을 항상 두 줄 높이로 확보해, 모든 줄의 높이를 같게 맞췄습니다.")

줄마다 높이를 재는 방법도 있지만, 그리지 않은 줄은 잴 수 없으니 추정과 보정이 계속 필요합니다. 그래서 반대로 **줄 높이가 달라지지 않게** 만들기로 했습니다. 상품명 영역을 항상 두 줄 높이로 확보해 두면, 상품명이 한 줄이어도 카드 높이가 같아집니다.

```tsx
{/* 가상 목록의 줄 높이가 상품명 길이에 따라 달라지지 않도록 최대 2줄 높이를 항상 확보함 */}
<h2 className="mt-0.5 line-clamp-2 min-h-[2lh] text-body-sm font-medium text-muted">
```

이제 모든 줄의 높이가 같으니, 렌더링된 **한 줄만 재서** 전체에 적용하면 됩니다. 390px 화면에서 한 줄은 약 203px이었습니다.

## 3편의 복원과 맞물리게 했습니다

가상 스크롤을 붙이고 나니 3편에서 만든 뒤로가기 복원에 문제가 생겼습니다. 돌아왔을 때 위치가 원래보다 **위쪽에서 멈추는** 경우가 있었습니다.

원인은 돌아온 직후의 줄 높이였습니다. 목록이 새로 만들어지면 아직 한 줄도 재지 않은 상태라, 처음에는 미리 정해 둔 추정값으로 전체 길이를 계산합니다. 이 추정값이 실제보다 작으면 전체 길이도 짧게 계산되고, 저장해 둔 위치까지 내려갈 수 없어 중간에서 잘립니다.

![복원 위치가 잘리는 이유. 돌아온 직후 추정 줄 높이로 계산한 전체 길이가 실제보다 짧으면, 저장한 위치까지 내려갈 수 없어 중간에서 멈춘다. 마지막으로 잰 줄 높이를 보관해 두면 돌아온 첫 순간부터 실제 길이로 계산해 저장한 위치까지 이동한다](/images/2026-11-26-product-list-performance-4-virtual-scroll/restore-clip.svg "마지막으로 잰 줄 높이를 보관해, 돌아온 첫 순간부터 실제 길이로 계산합니다.")

그래서 **마지막으로 잰 줄 높이를 보관**해 두고, 목록이 새로 만들어질 때 추정값 대신 그 값을 쓰도록 했습니다. 돌아온 첫 순간부터 실제 길이로 계산하니, 3편의 복원 훅이 저장된 위치까지 정확히 이동할 수 있게 되었습니다.

```ts
// 돌아온 첫 렌더링부터 실제 높이를 쓰도록 측정값을 보관함
let lastMeasuredRowHeight: number | null = null;

const [rowHeight, setRowHeight] = useState(() => lastMeasuredRowHeight);
```

스크롤 위치 자체는 3편에서 만든 저장소와 `useLayoutEffect` 복원을 그대로 씁니다. 3편에서 위치를 카드 기준이 아니라 `scrollTop` 숫자로 저장하기로 한 덕분에, 가상 스크롤을 붙여도 복원 방식을 바꿀 필요가 없었습니다.

## 첫 화면은 서버에서 그렸습니다

하나 더 지켜야 할 것이 있었습니다. 상품 목록의 첫 화면은 서버에서 미리 그려서 보내고 있었는데, 가상 스크롤은 **스크롤 영역의 크기와 카드 폭**을 알아야 줄을 배치할 수 있습니다. 서버는 사용자의 화면 크기를 모르니 이 값을 알 수 없습니다.

그래서 처음에는 두 단계로 나눠 그리도록 했습니다.

![서버 렌더링에서 가상 스크롤로 전환하는 흐름. 서버에서는 첫 20장을 일반 그리드 흐름으로 그려 보낸다. 브라우저에서 화면이 준비되면 한 줄의 높이를 재고, 그리기 전에 보이는 줄만 그리는 가상 스크롤 방식으로 바꾼다. 줄의 key가 같아 카드는 새로 만들지 않고 그대로 쓴다](/images/2026-11-26-product-list-performance-4-virtual-scroll/ssr-to-virtual.svg "서버는 일반 그리드로 첫 화면을 그리고, 브라우저에서 보이는 줄만 그리는 방식으로 바꿉니다.")

1. **서버에서는** 첫 페이지 20장을 담는 7줄을 일반 그리드로 그립니다. 사용자는 서버에서 온 화면을 바로 봅니다.
2. **브라우저에서** 화면이 준비되면 렌더링된 한 줄의 높이를 잽니다.
3. **그리기 전에** 보이는 줄만 그리는 가상 스크롤 방식으로 바꿉니다. 줄의 key가 같아서 카드를 새로 만들지 않고 위치만 바뀝니다.

이렇게 해서 가상 스크롤을 붙이면서도, 첫 화면을 서버에서 미리 그리는 장점은 그대로 지켰습니다.

## 예상하지 못했던 두 가지 문제

구현하면서 예상하지 못한 문제가 두 번 있었습니다.

### 깊이 내려가면 목록 높이가 13px씩 흔들렸습니다

5,000장 근처까지 내려가면 목록 전체 높이가 13px 정도 위아래로 계속 바뀌었습니다. 높이가 바뀔 때마다 다시 계산하고 다시 그리니, 화면이 미세하게 떨렸습니다.

원인은 위치를 읽는 방법이었습니다. 줄은 `translateY`로 아래로 옮겨 배치하는데, 수십만 픽셀 아래에 있는 요소의 크기를 `getBoundingClientRect`로 읽으면 소수점 오차가 생겼습니다. 이 작은 오차가 줄 높이와 전체 높이 계산에 섞여 들어가 값이 계속 흔들린 것입니다.

그래서 줄 높이는 화면상의 위치가 아닌 **레이아웃 값**(`getComputedStyle(row).height`)으로 읽고, 목록 위 영역의 높이는 정수로 반올림하도록 바꿔 해결했습니다.

### 메모리가 새는 줄 알았는데, 개발자 도구 때문이었습니다

가상 스크롤을 붙인 뒤에도 메모리를 재 보니, 화면에서 빠졌어야 할 카드들이 여전히 남아 있었습니다. 처음에는 코드 어딘가에서 메모리가 새는 줄 알았습니다.

힙 스냅샷에서 이 카드들을 붙잡고 있는 곳을 따라가 보니, 원인은 두 가지였습니다.

- **React DevTools 확장 프로그램**이 화면에서 빠진 컴포넌트 정보를 보관하고 있었습니다.
- 화면에서 빠진 카드의 **이미지가 아직 내려받는 중**이라 잠시 남아 있었습니다.

확장 프로그램을 끄고, 이미지 요청이 끝난 뒤 다시 재 보니 DOM 노드는 655개로 정상이었습니다. 이후 측정은 모두 확장 프로그램을 끄고, 이미지 요청이 끝난 뒤 기록하는 것으로 규칙을 정했습니다.

## 5,000장에서도 640개

같은 조건으로 다시 쟀습니다.

| 지표 | 200장 | 1,000장 | 5,000장 |
| --- | --- | --- | --- |
| DOM 노드 | 2,274 → **649** | 10,274 → **644** | 50,271 → **643** |
| 메모리 (힙 스냅샷) | 22.1 → **16.7MB** | 51.1 → **18.0MB** | 193 → **21.0MB** |
| 상세에서 돌아오는 시간 | 263 → **105ms** | 938 → **81ms** | 5,038 → **132ms** |

가장 눈에 띄는 것은 **카드 수가 늘어나도 DOM 노드가 거의 그대로**라는 점입니다. 200장이든 5,000장이든 640개 남짓을 유지했습니다. 5,000장 기준으로 DOM 노드는 98.7%, 메모리는 89.1% 줄었고, 상세에서 돌아오는 시간은 5초에서 0.13초가 되었습니다. 돌아온 위치도 떠날 때와 0px 차이로 정확했습니다.

스크롤하는 동안 브라우저가 하는 일도 크게 줄었습니다. 5,000장까지 스크롤하며 Chrome DevTools의 Performance 패널로 기록한 결과입니다.

| 작업 | 개선 전 | 개선 후 |
| --- | --- | --- |
| 50ms 넘게 화면을 멈춘 작업(Long Task) | 17회 | **0회** |
| 화면 변경 반영(Commit) | 3,048ms | **130ms** |
| 화면 그리기(Paint) | 925ms | **85ms** |
| 요소가 화면에 들어오는지 확인(IntersectionObserver) | 2,904ms | **46ms** |

## 얻은 만큼 내준 것도 있었습니다

좋아진 것만 있지는 않았습니다.

**받아야 하는 JS가 11.5KB 늘었습니다.** TanStack Virtual 라이브러리의 크기입니다. 상품 목록 화면에서만 쓰이고, 얻은 효과에 비해 크지 않다고 판단해 그대로 두었습니다.

**LCP 수치가 늘어났습니다.** 화면에서 가장 큰 요소가 그려지는 시간(LCP)이 2,096ms에서 2,392ms로 늘었습니다. 다만 실제로 첫 이미지가 보이는 시간은 2,096ms와 2,100ms로 같았습니다. 줄 단위로 배치하면서 크기 계산이 미세하게 달라져, LCP 측정 대상이 조금 늦게 뜨는 다른 카드로 바뀌었기 때문입니다. 사용자가 보는 화면은 같아서 그대로 두었습니다.

**짧은 목록에서는 조금 더 일합니다.** 200장에서는 페이지를 추가할 때 렌더링 시간이 7ms에서 9.9ms로 약 3ms 늘었습니다. 보이는 줄을 다시 계산하는 작업이 더해졌기 때문입니다. 카드 수와 상관없이 드는 고정 비용이라, 5,000장에서는 오히려 53ms에서 15ms로 줄었습니다.

**모든 카드의 높이가 같아야 합니다.** 상품명을 항상 두 줄 높이로 확보하면서, 상품명이 짧은 카드에는 빈 공간이 생겼습니다. 앞으로 카드에 정보를 추가할 때도 줄 높이가 달라지지 않도록 함께 신경 써야 합니다.

## 아직 남아 있는 것들

가상 스크롤로 화면에 남는 카드는 줄었지만, 아직 풀지 못한 문제도 있습니다.

**지나간 카드의 이미지도 모두 내려받습니다.** 화면을 빠르게 지나간 카드의 이미지도 요청이 나가서, 5,000장까지 스크롤하면 이미지 요청이 5,135건, 약 23.9MB에 달했습니다. 화면에서 빠진 카드의 이미지 요청을 멈추는 방법을 다음 과제로 남겨 두었습니다.

**다른 화면에서 이동해 올 때 첫 카드가 조금 늦게 보입니다.** 같은 날 비교에서 45~97ms 늦어졌습니다. 늘어난 JS를 받고 실행하는 시간과, 첫 카드 직전에 줄 높이를 재는 과정 때문으로 추정하지만 아직 정확히 확인하지는 못했습니다.
