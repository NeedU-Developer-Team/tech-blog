안녕하세요, 주라 팀 NeedU 프론트엔드 Juno 입니다!

메인페이지 성능 개선 시리즈에 이어, 이번에는 상품 목록 화면을 다뤄 보려고 합니다. 1편에서는 상품 목록을 측정할 환경을 만든 과정과, 조건을 바꿀 때마다 목록이 사라지던 문제를 고친 과정을 이야기합니다.

## 조건을 바꿀 때마다 목록이 사라졌습니다

NeedU의 상품 목록 화면에서는 카테고리 배지와 예산 슬라이더로 추천 상품을 거를 수 있습니다. 그런데 직접 써 보니 조금 거슬리는 부분이 있었습니다. 카테고리를 하나 누르면 보고 있던 목록이 통째로 사라지고, "추천 상품을 불러오는 중이에요"라는 문구가 잠깐 나온 뒤에야 새 목록이 나타났습니다.

![개선 전 조건 변경 모습. 리빙, 뷰티 카테고리를 누르고 예산을 줄일 때마다 목록과 예산 슬라이더 영역이 초록색으로 깜빡이며 카드가 빈 상자로 바뀌었다가 다시 채워짐](/images/2026-11-10-product-list-performance-1-keep-previous-list/before-filter-change.gif "개선 전 조건 변경 모습 (리빙 → 뷰티 → 예산 1번, 페인트 플래시 켬, Slow 4G·CPU 4배 감속)")

위 영상에서 초록색으로 깜빡이는 부분이 브라우저가 화면을 다시 그린 영역입니다. 조건을 바꿀 때마다 목록 전체가 다시 그려지는 것을 볼 수 있습니다.

불편한 점은 이것만이 아니었습니다. 방금 본 카테고리로 다시 돌아가도 똑같이 목록이 사라졌다가 나타났습니다. 예산 슬라이더를 키보드 방향키로 움직이면, 한 칸 움직일 때마다 포커스가 풀려서 다시 클릭해야 했습니다.

### 측정할 환경부터 만들었습니다

메인페이지를 개선하면서 배운 것이 하나 있다면, **감으로 고치지 말고 먼저 재 보자**는 것이었습니다. 그런데 상품 목록은 메인페이지와 조금 달랐습니다. 페이지가 처음 열리는 속도보다, **사용자가 조건을 바꾸는 순간**에 무슨 일이 일어나는지를 재야 했기 때문입니다.

그래서 본격적으로 고치기 전에 세 가지를 먼저 준비했습니다.

1. **목업 데이터 늘리기:** 무한 스크롤이나 예산 조건을 재현하려면 상품이 충분히 많아야 해서, 측정용 가짜 데이터(목업)를 늘렸습니다.
2. **로컬 프로덕션 환경 만들기:** 개발 서버는 실제 배포 환경과 동작이 달라서 측정값을 믿기 어렵습니다. 그래서 내 컴퓨터에서 프로덕션 빌드를 띄우고, 앞에 Caddy라는 웹 서버를 두어 배포 환경처럼 HTTPS로 접속하게 만들었습니다.
3. **계측 코드 넣기:** 목록이 실제로 화면에 반영된 순간을 코드에서 직접 기록하도록 `window.__perf`라는 작은 도구를 만들었습니다. 브라우저 콘솔에서 `__perf.summary()`를 입력하면 기록된 값을 표로 볼 수 있습니다.

측정 조건은 메인페이지 때와 비슷하게 맞췄습니다. Chrome 시크릿 창에서 화면 크기를 390×844로 두고, CPU는 `4배 감속`, 네트워크는 `Slow 4G`로 제한했습니다. 같은 시나리오를 3~5번씩 반복해서 중앙값으로 비교했습니다.

측정 도중 로그인 토큰이 만료되는 일도 꽤 자주 있었습니다. 토큰이 만료되면 재발급 요청이 끼어들어 기다리는 시간이 달라지기 때문에, 그런 회차는 버리고 다시 로그인한 뒤 처음부터 다시 쟀습니다.

### 무엇을 재야 할지 고민했습니다

처음에는 "조건을 바꾸고 새 목록이 뜰 때까지 걸리는 시간"만 재면 된다고 생각했습니다. 그런데 화면을 다시 보니, 문제는 느리다는 것보다 **기다리는 동안 화면이 비어 있다**는 것에 더 가까웠습니다.

그래서 사용자가 실제로 보는 화면을 숫자로 남길 방법을 찾았습니다. 가장 먼저 잰 것은 **목록 공백 시간**, 즉 상품 카드가 하나도 없는 상태가 이어진 시간입니다. 이걸 재 주는 도구는 따로 없어서, 콘솔에서 카드 개수를 지켜보는 짧은 스크립트를 만들어 썼습니다.

```js
// 카드가 0개가 된 순간부터 다시 생길 때까지의 시간을 기록
new MutationObserver(() => {
  const isBlank = document.querySelector("div.grid-cols-3")?.children.length === 0;
  // isBlank가 true가 된 시각과 false로 돌아온 시각의 차이를 저장
}).observe(document.body, { childList: true, subtree: true });
```

여기에 이미 본 조건으로 돌아갈 때의 대기 시간, React가 목록과 카드를 **새로 만들었는지(mount) 다시 그리기만 했는지(update)**를 보여 주는 React Profiler, 화면에서 다시 그려지는 영역을 보여 주는 개발자 도구의 페인트 플래시를 함께 사용했습니다. 마지막으로 개선 후에 다른 부분이 나빠지지 않았는지 보려고 첫 진입 시간과 Lighthouse 점수도 챙겼습니다.

## 목록을 비우고 처음부터 다시 그리고 있었습니다

먼저 개선 전 상태를 재 봤습니다.

| 시나리오 | 대기 시간 | 목록 공백 시간 |
|---|---|---|
| 카테고리 변경 | 160ms | **156ms** |
| 예산 변경 | 157.5ms | **154ms** |
| 이미 본 카테고리로 다시 방문 | 158ms | – |

숫자로 보니 생각보다 심각했습니다. 새 목록을 기다리는 약 160ms 가운데 155ms 동안 화면에 상품이 하나도 없었습니다. 이미 본 카테고리로 돌아가도 처음 볼 때와 똑같이 기다렸습니다.

사실 기다리는 시간 자체는 어쩔 수 없는 부분이었습니다. 측정용 목업 응답에 일부러 150ms 지연을 넣어 두었기 때문입니다. 그래서 고민의 방향을 바꿨습니다. 기다리는 시간을 줄이기보다, **기다리는 동안 무엇을 보여 줄지**를 바꿔 보기로 했습니다.

![조건을 바꾼 뒤 기다리는 동안의 화면 비교. 개선 전에는 목록을 비우고 로딩 문구를 보여 준 채 약 155ms 동안 빈 화면이 이어진 뒤 카드 20개를 새로 만든다. 개선 후에는 이전 목록을 흐리게 유지한 채 응답을 기다리고, 바뀐 카드만 새로 만들어 교체한다](/images/2026-11-10-product-list-performance-1-keep-previous-list/waiting-screen-flow.png "조건을 바꾼 뒤 기다리는 동안의 화면")

코드를 열어 보니 원인은 생각보다 단순했습니다. 목록을 컴포넌트 안의 `useState`로 직접 관리하고 있었는데, 조건이 바뀌면 목록부터 비운 뒤 첫 페이지를 다시 요청하고 있었습니다. 조건별 결과를 어디에도 저장하지 않으니, 방금 본 조건으로 돌아가도 처음부터 다시 받아야 했습니다.

목록 영역의 `key`에 조건 값이 들어 있던 것도 문제였습니다. React는 `key`가 바뀌면 그 컴포넌트를 버리고 새로 만듭니다. 그래서 조건을 바꿀 때마다 목록과 그 안의 카드 20개가 전부 새로 만들어지고 있었습니다. React Profiler로 확인해 보니, 예산을 한 칸만 줄여서 실제로 새로 들어온 상품이 5개뿐일 때도 카드 20개를 모두 새로 만들고 있었습니다.

## 바로 TanStack Query를 고르지는 않았습니다

원인을 알고 나서도 바로 코드를 고치지는 않았습니다. 같은 문제를 푸는 방법이 여러 가지였고, 고르는 기준에 따라 답이 달라졌기 때문입니다. 크게 세 번의 고민을 거쳤습니다.

### 첫 번째 고민. 기다리는 동안 무엇을 보여 줄까

가장 먼저 떠올린 것은 **스켈레톤**이었습니다. 로딩 문구 대신 카드 모양의 회색 상자를 보여 주는 방식으로, 구현이 간단하고 지금 구조를 거의 바꾸지 않아도 됩니다.

그런데 화면 흐름을 그려 보니 문제가 있었습니다. 스켈레톤도 결국 **보던 목록을 지우고** 회색 상자로 바꿉니다. 로딩 문구가 회색 상자로 바뀌었을 뿐, 상품이 사라진다는 점은 그대로였습니다. 게다가 응답이 약 0.16초로 짧아서, 회색 상자가 잠깐 보였다 사라지면 오히려 화면이 번쩍이는 것처럼 느껴질 것 같았습니다.

스켈레톤은 **아직 보여 줄 내용이 없을 때** 어울리는 방법입니다. 페이지에 처음 들어왔을 때가 그렇습니다. 하지만 조건을 바꾸는 순간에는 이미 보여 줄 목록이 있습니다. 그래서 그 목록을 그대로 둔 채, 반투명하게 만들어 "바뀌는 중"이라는 것만 알려 주기로 했습니다.

### 두 번째 고민. 직접 만들까, 라이브러리를 쓸까

이전 목록을 붙잡아 두는 방법도 여러 가지였습니다.

| 방법 | 장점 | 단점 |
|---|---|---|
| 직접 구현 (`key`를 없애고 응답이 오면 교체) | 의존성 추가 없음, 변경 범위가 작음 | 커서, 요청 순서, 캐시를 모두 직접 관리해야 함 |
| React `useTransition` | React 내장 기능만 사용 | 요청이 겹칠 때의 순서 처리와 캐시는 여전히 직접 해야 함 |
| 서버 상태 라이브러리 (TanStack Query) | 이전 목록 유지, 요청 순서, 캐시를 라이브러리가 처리 | 의존성이 추가되고 목록 코드를 거의 새로 써야 함 |

처음에는 직접 구현하는 쪽에 마음이 기울었습니다. 의존성을 늘리지 않고, 변경 범위도 가장 작아 보였기 때문입니다.

그런데 직접 구현할 때 처리해야 할 일을 하나씩 적어 보니 생각보다 많았습니다.

- 조건이 바뀌는 동안 이전 목록과 다음 페이지 커서를 따로 들고 있다가, 새 응답이 오면 한꺼번에 바꿔야 합니다.
- 카테고리를 빠르게 연달아 바꾸면 요청이 겹칩니다. 늦게 도착한 이전 조건의 응답이 최신 목록을 덮어쓰지 않도록, 요청을 취소하거나 순서를 확인해야 합니다.
- 무한 스크롤로 다음 페이지를 불러오는 도중에 조건이 바뀌면, 이전 조건의 페이지가 새 목록에 섞이지 않게 막아야 합니다.
- 이미 본 조건으로 돌아갈 때 다시 기다리지 않게 하려면, 조건별로 페이지와 커서를 저장하고 언제 다시 요청할지도 정해야 합니다.

이 목록을 다 만들고 나면, 서버 상태 라이브러리가 하는 일을 작게 다시 만드는 셈이었습니다. 경계 상황이 많은 만큼 직접 만든 코드에서 놓치는 부분이 생기기도 쉬웠습니다.

`useTransition`도 살펴봤습니다. 상태 변경을 급하지 않은 업데이트로 표시해, 새 화면이 준비될 때까지 이전 화면을 유지해 주는 기능입니다. 하지만 이 효과는 `Suspense`로 데이터를 기다릴 때 나타납니다. 지금처럼 effect 안에서 목록을 요청하는 구조에서는 상태 변경이 바로 끝나 버려서, 이전 화면 유지도 결국 직접 처리해야 했습니다. 요청 순서와 저장 문제도 그대로 남았습니다.

그래서 **TanStack Query를 도입**하기로 했습니다. 조건을 쿼리 키로 삼으면 결과가 조건별로 나뉘어 저장되고, 늦게 도착한 이전 조건의 응답은 그 조건의 자리에만 들어가 최신 목록을 덮어쓰지 않습니다. 이전 목록 유지는 옵션 하나로 해결됩니다.

다만 이전 목록 유지와 캐시가 한 번에 들어오면, 어느 쪽 덕분에 빨라졌는지 구분하기 어렵습니다. 그래서 측정 시나리오를 나눴습니다. 처음 보는 조건으로 바꾸는 시나리오로는 "이전 목록 유지" 효과를, 이미 본 조건으로 돌아가는 시나리오로는 "캐시" 효과를 따로 확인했습니다.

### 세 번째 고민. 로딩 상태를 어디서 처리할까

TanStack Query 안에서도 선택지가 두 가지 남았습니다.

하나는 `useSuspenseInfiniteQuery`와 `useTransition`을 함께 쓰는 방법입니다. 두 훅의 특징부터 정리하면 이렇습니다.

**`useSuspenseInfiniteQuery`** 는 로딩과 에러를 컴포넌트 바깥으로 넘기는 무한 스크롤용 훅입니다.

- 데이터가 아직 없으면 렌더링을 멈추고, 가장 가까운 `Suspense`의 대체 화면(fallback)을 보여 줍니다.
- 에러가 나면 가장 가까운 에러 경계(Error Boundary)가 처리합니다.
- 그래서 컴포넌트 안에서는 `data`가 항상 있다고 보고 그리기만 하면 됩니다. `isLoading`으로 분기하는 코드가 사라집니다.
- 대신 쿼리 키가 처음 보는 조건으로 바뀌면 다시 렌더링을 멈추고 대체 화면을 띄웁니다. 그대로 쓰면 조건을 바꿀 때마다 목록이 다시 사라집니다.

**`useTransition`** 은 상태 변경을 "급하지 않은 업데이트"로 표시하는 React 훅입니다.

- `startTransition`으로 감싼 상태 변경 중에 렌더링이 멈추면, React는 대체 화면을 띄우지 않고 이미 보이던 화면을 그대로 둡니다.
- 새 화면이 준비되는 동안에는 `isPending`이 `true`가 되어, 진행 중 표시를 붙일 수 있습니다.
- 대신 효과를 보려면 화면을 바꾸는 상태 변경, 여기서는 카테고리와 예산을 바꾸는 코드를 빠짐없이 `startTransition`으로 감싸야 합니다.

두 훅을 함께 쓰면 목록 컴포넌트는 데이터가 있다고 가정하고 그리기만 하고, 첫 진입 로딩은 바깥의 `Suspense`가, 조건 변경 중 이전 목록 유지는 `useTransition`이 맡습니다. 역할이 깔끔하게 나뉘지만, 지금 페이지에는 맞지 않았습니다. 로딩 경계를 새로 만들어야 했고, 카테고리·예산을 바꾸는 쪽 코드까지 모두 고쳐야 했습니다. 한 곳이라도 감싸는 것을 빠뜨리면 그 조작에서만 목록이 다시 사라집니다. 첫 진입 로딩 화면도 `Suspense` 경계를 기준으로 바뀌어서, 조건 변경 문제 하나를 풀려다 페이지 전체의 로딩 구조를 바꾸는 일이 됐습니다.

다른 하나는 `useInfiniteQuery`에 `keepPreviousData` 옵션을 쓰는 방법입니다. 지금처럼 목록 컴포넌트가 로딩 상태를 직접 받아서 처리하고, 조건을 바꾸는 쪽은 손대지 않아도 됩니다. 변경 범위가 목록 컴포넌트 두 개로 좁아서, 이번에는 이 방법을 골랐습니다.

## TanStack Query로 이전 목록을 붙잡아 두었습니다

하고 싶은 일은 두 가지였습니다. 새 목록이 올 때까지는 이전 목록을 보여 주는 것, 그리고 이미 본 조건은 바로 보여 주는 것입니다.

### 조건을 캐시의 이름표로 삼았습니다

TanStack Query는 요청 결과를 **쿼리 키**라는 이름표를 붙여 저장합니다. 그래서 카테고리와 예산을 쿼리 키에 넣었습니다. 조건이 같으면 같은 이름표의 결과를 꺼내 쓰고, 조건이 다르면 새로 요청합니다.

```ts
useInfiniteQuery({
  queryKey: ["personal-recommendations", { category, minPrice, maxPrice }],
  // ...목록 요청과 다음 페이지 커서 처리
  placeholderData: keepPreviousData,
});
```

여기서 핵심은 마지막 줄의 `keepPreviousData`입니다. 조건이 바뀌어 새 응답을 기다리는 동안, 이전 조건의 목록을 그대로 돌려줍니다. 이때는 `isPlaceholderData` 값이 `true`가 되어서, 이 값으로 이전 목록을 반투명하게 보여 주었습니다.

```tsx
<div aria-busy={isPlaceholderData} className={isPlaceholderData ? "opacity-50" : ""}>
```

`aria-busy`도 함께 붙여서, 화면 낭독기를 쓰는 사용자에게도 목록이 갱신 중이라는 것을 알려 주었습니다. 목록 영역의 `key`도 없앴습니다. 이제 조건이 바뀌어도 목록을 새로 만들지 않고, 바뀐 카드만 다시 그립니다.

캐시는 바로 보여 주되, 오래된 목록을 계속 보여 주면 안 되니 `staleTime`은 0으로 두었습니다. 캐시에 있는 목록을 먼저 보여 주고, 뒤에서 다시 요청해 최신 목록으로 맞추는 방식입니다. 그 밖에 기존 동작이 바뀌지 않도록, 실패한 요청을 자동으로 다시 보내는 기능과 탭으로 돌아올 때마다 다시 요청하는 기능은 껐습니다.

![조건별 캐시 흐름. 처음 보는 조건은 쿼리 키를 확인한 뒤 서버에 요청해 약 160ms를 기다리고, 응답을 쿼리 키별로 캐시에 저장한다. 다시 보는 조건은 캐시에서 약 5ms 만에 바로 표시한 뒤, 뒤에서 다시 요청해 최신 목록으로 맞춘다](/images/2026-11-10-product-list-performance-1-keep-previous-list/query-cache-flow.png "조건별 캐시와 다시 방문 흐름")

### 그런데 슬라이더 포커스가 계속 풀렸습니다

목록이 유지되니, 그동안 묻혀 있던 문제가 더 잘 보이기 시작했습니다. 예산 슬라이더를 방향키로 한 칸 움직이면 포커스가 풀리는 문제였습니다.

원인은 이번에도 `key`였습니다. 슬라이더의 `key`에 **사용자가 선택한 가격**이 들어 있었습니다. 그래서 예산을 바꾸면 `key`가 바뀌고, React가 슬라이더를 새로 만들어 버렸습니다. 새로 만들어진 슬라이더에는 당연히 포커스가 없습니다.

그래서 `key`에는 전체 가격 범위만 남겼습니다. 대신 바깥에서 선택 가격이 바뀌면, 슬라이더를 새로 만들지 않고 안쪽 값만 맞추도록 바꿨습니다. React 공식 문서에서 소개하는 "props가 바뀔 때 state 조정하기" 방법입니다.

```tsx
// 선택 가격이 바뀌면 슬라이더를 새로 만들지 않고 안쪽 값만 맞춤
if (syncedRange.maxPrice !== initialMaxPrice) {
  setSyncedRange({ minPrice: initialMinPrice, maxPrice: initialMaxPrice });
  setDraftMaxPrice(initialMaxPrice);
}
```

정말 슬라이더가 새로 만들어지지 않는지는 React DevTools의 Profiler로 확인했습니다. Profiler 설정에서 "Record why each component rendered"를 켜면, 컴포넌트가 왜 다시 그려졌는지를 알려 줍니다.

![React DevTools Profiler에서 예산을 바꾼 직후 커밋의 PriceRangeSlider. key는 10000:200000 그대로이고, Why did this render?에 Hooks changed 3·4 State와 Props changed initialMaxPrice, onPriceRangeCommit이 표시됨](/images/2026-11-10-product-list-performance-1-keep-previous-list/slider-why-rendered.png "예산을 바꾼 직후 PriceRangeSlider가 다시 렌더링된 이유")

예산을 바꾼 직후에도 `key`는 `10000:200000` 그대로였습니다. 다시 그려진 이유도 "처음 그려짐"이 아니라 "선택 가격(`initialMaxPrice`)이 바뀌어서"로 나왔습니다. 슬라이더를 새로 만들지 않고 값만 바꿨다는 뜻입니다.

## 공백은 0ms가, 다시 방문은 5ms가 됐습니다

같은 조건으로 다시 재 봤습니다.

![개선 후 조건 변경 모습. 카테고리와 예산을 바꾸면 이전 목록이 흐려진 채로 남아 있다가 새 목록으로 바뀌고, 로딩 문구나 빈 목록이 나타나지 않음](/images/2026-11-10-product-list-performance-1-keep-previous-list/after-filter-change.gif "개선 후 조건 변경 모습 (리빙 → 뷰티 → 예산 1번, 페인트 플래시 켬, Slow 4G·CPU 4배 감속)")

이제 조건을 바꾸면 이전 목록이 흐려진 채로 남아 있다가 새 목록으로 바뀝니다. 로딩 문구도 더 이상 나오지 않습니다.

| 지표 | 개선 전 | 개선 후 |
|---|---|---|
| 목록 공백 시간 (카테고리 / 예산) | 156ms / 154ms | **0ms / 0ms** |
| 다시 방문 대기 시간 | 158ms | **5ms** |
| 예산 변경 시 새로 만든 카드 | 100개 | **5개** |
| 예산 변경 시 슬라이더 | 새로 만들어짐 | **유지** |

목록 공백 시간은 두 시나리오 모두 0ms가 됐습니다. 이미 본 카테고리로 돌아가면 캐시에서 바로 꺼내 5ms 만에 보여 줍니다. 예산을 바꿀 때 새로 만든 카드 5개는 실제로 새로 들어온 상품 수와 정확히 같았습니다. 나머지 카드는 새로 만들지 않고 그대로 다시 썼습니다.

재미있는 점은 **조건을 바꾸고 새 목록이 뜰 때까지의 시간은 거의 그대로**였다는 것입니다. 카테고리 변경은 160ms에서 163ms, 예산 변경은 157.5ms에서 158.7ms로 거의 차이가 없었습니다. 응답을 기다리는 시간은 건드리지 않았으니 당연한 결과입니다.

만약 처음에 대기 시간 하나만 재기로 했다면, "고쳤는데 효과가 없네"라고 결론을 냈을지도 모릅니다. 공백 시간과 렌더링 횟수를 함께 잰 덕분에, 이번 개선의 효과를 숫자로 설명할 수 있었습니다.

### 공짜는 아니었습니다

좋아진 것만 있지는 않았습니다. 대가로 생긴 부분도 그대로 적어 두려고 합니다.

먼저 첫 진입이 조금 느려졌습니다. 상품 목록이 처음 뜨기까지의 시간이 4,806ms에서 4,870ms로 약 64ms(1.3%) 늘었습니다. 개선 후 가장 빠른 회차가 개선 전 가장 느린 회차보다 느렸기 때문에, 우연이 아니라 실제로 늘어난 것으로 봤습니다. TanStack Query가 추가되면서 받아야 하는 JS가 14kB 늘어난 영향으로 추정합니다. 다행히 Lighthouse 점수는 개선 전후 모두 99점으로 같았습니다.

조건을 바꿀 때의 렌더링 작업도 조금 늘었습니다. 이전 목록을 흐리게 보여 주는 동안, 화면에 남아 있는 카드들이 매번 다시 그려졌기 때문입니다. 조건을 다섯 번 바꾸는 동안 카드가 약 200번 다시 그려졌고, 조건 변경 한 번에 0.7~2.8ms가 더 걸렸습니다. 응답을 기다리는 160ms에 비하면 작은 값이지만, 하지 않아도 되는 일입니다.

마지막으로, 목록을 흐리게 했다가 되돌릴 때마다 스크롤 영역 전체가 다시 그려졌습니다. 위의 개선 후 영상에서 예산 슬라이더 영역까지 함께 깜빡이는 이유입니다.
