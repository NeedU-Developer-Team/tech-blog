안녕하세요, 주라 팀 NeedU 프론트엔드 Juno 입니다!

이 글은 메인페이지 성능 개선 시리즈의 2편입니다. [1편: 원인 분석과 웹폰트 최적화](https://needu-developer-team.github.io/tech-blog/posts/main-page-performance-1-web-font/)에서는 측정 기준을 세우고 웹폰트를 줄인 과정을 다뤘습니다. 이번 글에서는 웹폰트 개선 후에도 남아 있던 원인을 하나씩 해결해, Lighthouse LCP를 **2초 안**으로 줄인 과정을 다룹니다.

## 웹폰트를 줄여도 LCP는 5초를 넘었습니다

1편에서 웹폰트를 972kB에서 약 140kB로 줄였습니다. 그 결과 Lighthouse 성능 점수는 74점에서 80점으로 올랐고, LCP는 9.49초에서 5.21초로 줄었습니다. 하지만 상품 사진이 그려지기까지 여전히 5초가 넘게 걸렸습니다.

### 측정 기준은 1편과 같습니다

| 항목 | 설정 |
|---|---|
| 대상 | dev 서버의 메인페이지 (취향 분석을 마친 계정으로 로그인) |
| Lighthouse | 모바일, 시뮬레이션된 제한, 단계마다 3~5회 측정 후 중앙값 |
| HAR·성능 탭 | Chrome DevTools `느린 4G`, CPU `4배 감속`, `캐시 사용 중지` |

결과는 Lighthouse로, 원인은 HAR과 성능(Performance) 탭으로 확인했습니다. 성능 탭은 페이지를 불러오는 동안 네트워크 요청, 스크립트 실행, 화면 그리기를 한 타임라인에 기록해, 화면이 무엇을 기다리느라 늦게 그려졌는지 보여 줍니다.

| 지표 | 의미 | 메인페이지에서 |
|---|---|---|
| 성능 점수 | 여러 지표를 합친 0~100점 | – |
| FCP | 화면에 무언가 처음 그려지는 시점 | 헤더가 처음 보이는 시점 |
| LCP | 화면에서 가장 큰 콘텐츠가 그려지는 시점 | 추천 상품 사진이 보이는 시점 |

### 남은 원인 네 가지와 새로 찾은 하나

1편에서 정리한 다섯 가지 원인 중 웹폰트를 제외한 네 가지가 남아 있었습니다.

| 원인 | 내용 | 이 글에서 다룬 작업 |
|---|---|---|
| 분석 스크립트 | GA 스크립트가 초기 JS와 대역폭을 나눠 씀 | GA 로딩 시점 조정 |
| 클라이언트 데이터 요청 | JS 실행이 끝난 뒤에야 API를 요청함 | 데이터 서버 조회 전환 |
| 순차 요청 | 안내 문구 응답 이후에야 추천 상품을 요청함 | 데이터 서버 조회 전환 |
| 상품 이미지 | CSS 배경 이미지라 브라우저가 늦게 발견함 | 이미지 요소 전환과 썸네일 축소 |

여기에 작업 중 새로 찾은 원인 하나를 더 해결했습니다. 헤더 표시를 막고 있던 **렌더링 차단 CSS**입니다.

## LCP를 2초 안으로 줄이기까지의 다섯 번의 시도

남은 원인을 하나씩 없애며 다섯 번 시도했습니다. 한 곳을 고치자 다른 곳이 늦어진 경우도 있어, 순서대로 모두 정리했습니다.

### 첫 번째 시도. GA 스크립트를 페이지 로드 이후로 미뤘습니다

NeedU는 Google Analytics(GA4)로 방문 데이터를 수집합니다. 특히 메인페이지에 들어왔다가 금방 떠나는 짧은 방문이 얼마나 되는지 확인하는 데 쓰고 있어서, GA를 빼는 선택지는 없었습니다.

그런데 폰트를 줄이고 나니, 초기 JS와 대역폭을 가장 많이 나눠 쓰는 리소스는 GA 스크립트(gtag, 약 180kB)가 됐습니다. 가장 큰 JS가 받아지는 구간(0.6~3.66초)의 전송량을 나눠 보면 다음과 같았습니다.

| 리소스 | 받은 양 | 비율 |
|---|---|---|
| 앱 JS | 238kB | 50% |
| **GA 스크립트** | **165kB** | **34%** |
| CSS | 33kB | 7% |
| 폰트 | 32kB | 7% |
| 이미지 | 11kB | 2% |

GA가 페이지를 여는 데 필요한 JS와 같은 시간대에 받아지고 있었고, 원인은 GA를 붙이는 방식이었습니다. 기존에 쓰던 `@next/third-parties`의 `GoogleAnalytics` 컴포넌트는 `<head>`에 gtag preload를 넣습니다. 그래서 gtag가 HTML 도착 직후(0.63초) **높은 우선순위**로 받아졌고, 불러오는 시점을 바꾸는 옵션은 없었습니다.

GA 수집은 유지하면서 gtag 본체만 나중에 받도록, GA 초기화와 gtag 본체 로딩을 나눠 직접 구현했습니다.

```tsx
export default function GoogleAnalytics({ gaId }: GoogleAnalyticsProps) {
  // gtag 본체가 도착하기 전의 페이지뷰를 dataLayer에 쌓아 두도록 초기화는 즉시 실행
  const initGoogleAnalytics = `window.dataLayer = window.dataLayer || [];
function gtag() {
  window.dataLayer.push(arguments);
}
gtag("js", new Date());
gtag("config", ${JSON.stringify(gaId)});`;

  return (
    <>
      <script dangerouslySetInnerHTML={{ __html: initGoogleAnalytics }} />
      <Script src={`https://www.googletagmanager.com/gtag/js?id=${gaId}`} strategy="lazyOnload" />
    </>
  );
}
```

- **초기화 스크립트:** `<body>` 끝에서 바로 실행해 `dataLayer`를 만듭니다. gtag가 늦게 도착해도 그 전의 페이지뷰가 쌓여 있다가 전송됩니다. 1편에서 폰트 로더 위치를 옮기며 배운 대로 `<head>`가 아니라 `<body>` 끝에 두어 HTML 해석을 막지 않게 했습니다.
- **gtag 본체:** `next/script`의 `lazyOnload`로 페이지 로드 이후, 브라우저가 한가할 때 받습니다.

적용한 뒤 gtag 요청은 페이지 로드 이후로 밀려났습니다.

| 항목 | 적용 전 | GA 로딩 시점 조정 |
|---|---|---|
| gtag 요청 | 0.63s 시작, 높음 | **3.41s 시작, 낮음** |
| 가장 큰 JS 다운로드 완료 | 3.66s | **2.82s** |
| Lighthouse 점수 | 80 | **87** |
| Lighthouse FCP | 0.80s | 0.86s |
| Lighthouse LCP | 5.21s | **4.07s** |

gtag가 빠진 만큼 앱 JS가 0.84초 일찍 끝났고, 그 뒤의 API 요청도 약 0.8초씩 앞당겨졌습니다. Lighthouse LCP는 5.21초에서 4.07초로 줄었고, GA 수집 요청도 정상으로 전송됐습니다.

**더 늦추지 않은 이유:** gtag를 상품 사진이 보인 뒤로 더 늦추면 상품 사진을 조금 더 빨리 보여 줄 수 있었습니다. 하지만 GA는 gtag가 도착하기 전에 떠난 방문을 기록하지 못합니다. 이 변경만으로도 느린 4G에서 gtag 완료 시점이 약 4.1초에서 약 6초로 늦어졌습니다. GA를 쓰는 이유가 바로 짧은 방문을 확인하는 것이었기 때문에, 수집 손실을 더 늘리지 않기로 했습니다.

### 두 번째 시도. 데이터 요청을 서버로 옮겼습니다

GA 로딩 시점을 조정한 뒤의 요청 흐름을 HAR로 보면, 안내 문구가 늦은 이유가 분명했습니다.

| 순서 | 일어나는 일 | 시점 |
|---|---|---|
| 1 | 빈 `<main>`이 담긴 HTML 도착 | 0.59s |
| 2 | 가장 큰 JS 다운로드 완료, 하이드레이션 | 2.82s |
| 3 | 브라우저에서 안내 문구 API 요청 | 2.98s |
| 4 | 안내 문구 응답 후 추천 상품 API 요청 | 3.56s → 4.20s |
| 5 | 상품 이미지 요청 | 4.21s → 5.43s |

메인페이지는 클라이언트 컴포넌트에서 `useEffect`로 데이터를 요청하고 있었습니다. 그래서 JS가 모두 받아지고 실행될 때까지 데이터 요청이 시작되지 않았고, 추천 상품은 안내 문구 응답을 기다린 뒤에야 요청됐습니다.

메인페이지를 서버 컴포넌트로 바꿔, HTML을 만들 때 서버에서 데이터를 조회하도록 했습니다.

```tsx
async function getHomeDataOrRedirect() {
  // proxy가 검증한 세션 정보를 사용해 백엔드 세션 재조회 생략
  const loginUser = await getServerLoginUser();

  if (!loginUser) {
    redirect("/login");
  }

  try {
    const guidance = await getHomeGuidance();
    // 취향 분석을 마친 사용자만 추천 상품 조회
    const products = guidance.tasteAnalysisCompleted ? await getHomeRecommendations() : [];

    return { loginUser, guidance, products };
  } catch (error) {
    if (error instanceof ServerApiError && error.status === 401) {
      redirect("/login");
    }

    redirect("/error");
  }
}
```

구현하면서 신경 쓴 부분은 세 가지입니다.

- **세션을 다시 조회하지 않기:** 인증을 확인하는 proxy(Next.js 미들웨어)가 이미 세션을 검증하고 있었습니다. 그 결과로 얻은 사용자 정보를 요청 헤더에 담아 페이지로 넘겨, 서버 컴포넌트에서 백엔드에 세션을 한 번 더 묻지 않게 했습니다.
- **로딩 화면 범위 좁히기:** 서버 조회 동안 보여 줄 `loading.tsx`를 라우트 그룹 `(home)` 안에 두었습니다. 같은 레이아웃을 쓰는 다른 페이지에는 로딩 화면이 적용되지 않습니다.
- **오류 처리 나누기:** 세션이 만료된 401 응답은 로그인 화면으로, 그 밖의 오류는 오류 화면으로 보냅니다.

**정적 페이지를 포기한 비용:** 서버 컴포넌트에서 요청마다 데이터를 조회하면, 메인페이지는 정적 페이지에서 동적 페이지로 바뀝니다. 미리 만들어 둔 HTML을 바로 보내던 방식보다 첫 바이트(TTFB)가 늦어질 수 있습니다. 측정해 보니 TTFB는 **0.569~0.576초**로, 이전 HTML 응답 시간과 거의 같았습니다. 서버에서 조회하는 시간이 느린 4G의 요청 지연 안에 가려진 것으로 보입니다.

| 항목 | GA 로딩 시점 조정 | 서버 조회 전환 |
|---|---|---|
| HTML | 0.59s 완료 (빈 화면) | 0.62s 완료 (내용 포함) |
| 브라우저의 API 요청 | 안내 문구 → 추천 상품 순차 요청 | 없음 (서버에서 처리) |
| 상품 이미지 요청 시작 | 4.21s | **1.70s** |
| Lighthouse 점수 | 87 | **90** |
| Lighthouse FCP | 0.86s | 0.92s |
| Lighthouse LCP | 4.07s | **3.62s** |

요청 흐름으로 보면 이번 개선에서 가장 큰 변화였습니다. 안내 문구와 추천 상품이 HTML에 담겨 오면서, 브라우저가 JS를 받아 실행한 뒤 API를 두 번 순서대로 요청하던 과정이 통째로 사라졌습니다. 상품 이미지 요청도 4.21초에서 1.70초로 2.5초 앞당겨졌고, Lighthouse LCP는 3.62초로 줄었습니다.

### 세 번째·네 번째 시도. 상품 이미지를 더 빨리, 더 가볍게 받았습니다

데이터를 서버에서 조회한 뒤에도 상품 이미지 요청은 HTML 도착 직후가 아니라 **1.67초**에 시작했습니다. Lighthouse가 LCP로 잡는 요소가 바로 이 상품 이미지라, 이미지 요청이 늦을수록 LCP도 늦어졌습니다.

**세 번째 시도. CSS 배경 이미지를 이미지 요소로:** 상품 이미지는 `div`의 CSS `background-image`로 그리고 있었습니다. 브라우저의 프리로드 스캐너는 HTML 속 `<img>`는 바로 찾지만, CSS 배경 이미지는 CSS를 받고 스타일을 계산한 뒤에야 발견합니다. 그래서 렌더링 차단 CSS가 다 받아진 뒤에야 이미지 요청이 나갔습니다. 이미지를 `next/image` 요소로 바꾸고 세 가지 속성을 지정했습니다.

```tsx
<Image
  src={toHomeThumbnailUrl(product.productImageUrl)}
  alt={`${product.name} 상품 이미지`}
  fill
  unoptimized
  loading="eager"
  fetchPriority="high"
  className="object-cover"
/>
```

| 속성 | 이유 |
|---|---|
| `loading="eager"` | `next/image`의 기본값은 지연 로딩이라, 첫 화면 이미지에는 해제해야 함 |
| `fetchPriority="high"` | 레이아웃 이후가 아니라 처음부터 높은 우선순위로 요청 |
| `unoptimized` | 이미 카카오 CDN 썸네일이라, 우리 서버의 이미지 변환을 거치지 않고 CDN에서 바로 받음 |

이미지 preload는 넣지 않았습니다. 1편에서 폰트 preload가 다른 요청의 우선순위를 밀어냈던 것처럼, 렌더링 차단 CSS와 대역폭을 나눠 쓸 위험이 있었기 때문입니다.

**네 번째 시도. 필요한 크기만큼만 받기:** 이미지 주소는 백엔드가 카카오 썸네일 주소로 내려 줍니다. 주소의 `C175x175@2x`는 175×175를 2배 해상도로, 즉 **350px**로 받는다는 뜻입니다. 그런데 메인 카드의 이미지는 약 101~108px로 표시되어, 2배 화면에도 약 216px이면 충분했습니다.

| 썸네일 크기 | 실제 픽셀 | 추천 3장 합계 |
|---|---|---|
| `C175x175@2x` (기존) | 350px | 50.9kB |
| `C150x150@2x` | 300px | 40.8kB |
| `C120x120@2x` (적용) | 240px | 29.1kB |

카드 컴포넌트에서 카카오 썸네일 주소의 크기 부분만 `C120x120@2x`로 바꾸고, 형식이 다른 주소는 그대로 쓰게 했습니다.

```tsx
const HOME_THUMBNAIL_SIZE = "C120x120@2x";
const KAKAO_THUMBNAIL_SIZE_PATTERN =
  /^(https?:\/\/[^/]+\.kakaocdn\.net\/thumb\/)C\d+x\d+(?:@\d+x)?(?=[./])/;

const toHomeThumbnailUrl = (imageUrl: string) =>
  imageUrl.replace(KAKAO_THUMBNAIL_SIZE_PATTERN, `$1${HOME_THUMBNAIL_SIZE}`);
```

이 방식은 카카오 CDN의 공개 문서에 없는 주소 규칙에 기대고 있습니다. 주소 형식이 바뀌면 원래 주소를 그대로 쓰게 되어 화면이 깨지지는 않지만, 장기적으로는 백엔드에서 크기를 정해 내려 주는 편이 안정적입니다.

| 항목 | 서버 조회 전환 | 이미지 요소 전환 | 썸네일 축소 |
|---|---|---|---|
| 상품 이미지 요청 시작 | 1.67s | **0.61s** | 0.64s |
| Lighthouse 점수 | 90 | **95** | 94 |
| Lighthouse FCP | 0.92s | 0.94s | 0.92s |
| Lighthouse LCP | 3.62s | **2.79s** | 2.95s |

이미지 요청이 약 1초 앞당겨지면서 LCP는 3.62초에서 2.79초로 줄었습니다. 그런데 이미지 용량까지 줄인 뒤에는 LCP가 2.95초로 오히려 조금 늘었습니다.

HAR을 보니 다른 문제가 함께 생겨 있었습니다. 이미지가 렌더링 차단 CSS와 같은 시간대에 받아지면서 CSS 다운로드 시간이 0.47초에서 0.61초로 늘어난 것입니다. 렌더링 차단 CSS가 늦어지면 헤더를 포함한 화면 전체가 늦게 그려집니다. 이미지 용량을 줄인 뒤에도 이 지연은 회복되지 않아, 따로 분석하기로 했습니다.

### 다섯 번째 시도. 헤더를 막고 있던 CSS 8kB를 HTML에 넣었습니다

렌더링 차단 CSS가 실제로 화면을 얼마나 막고 있는지 보기 위해, 성능 기록(Performance 탭)으로 헤더가 그려지기까지의 과정을 살펴봤습니다. 세 번 기록했는데 결과가 거의 같았습니다.

| 항목 | 값 |
|---|---|
| HTML 완료 | 0.62s |
| 렌더링 차단 CSS 수신 | 1.16s → **1.70s** |
| 첫 페인트 (헤더) | **1.76s** |
| 첫 페인트 전 메인 스레드 작업 합계 | 약 60ms |

헤더는 **CSS가 도착하고 약 60ms 뒤에** 매번 그려졌고, 그 전까지 메인 스레드는 거의 쉬고 있었습니다. 즉 헤더가 그려지는 시점은 CPU가 아니라 CSS가 언제 도착하느냐로 정해졌습니다.

그런데 이 CSS는 8.2kB밖에 되지 않았습니다. 측정 회선 속도라면 0.05초면 받을 크기인데 0.54초가 걸렸습니다. 같은 시간대에 다른 요청 17개가 회선을 나눠 쓰고 있었기 때문입니다.

| CSS와 같은 시간대에 받은 요청 | 개수 | 크기 |
|---|---|---|
| JS 파일 | 13개 | 약 235kB |
| 상품 이미지 | 3개 | 약 29.6kB |
| 헤더 로고 | 1개 | 6.8kB |
| 작은 CSS | 1개 | 1.0kB |

JS는 우선순위가 낮지만, 프리로드 스캐너가 `<script async>`를 HTML에서 바로 찾기 때문에 CSS와 같은 시점에 요청이 나갑니다. 한 가지 짚어 둘 점은, DevTools의 `느린 4G`는 동시에 진행 중인 요청에 대역폭을 거의 고르게 나눠 준다는 것입니다. 그래서 실제 네트워크보다 경쟁 영향이 크게 측정됐을 수 있습니다.

경쟁 자체를 없애는 방법을 골랐습니다. Next.js의 `experimental.inlineCss`를 켜면 CSS를 별도 파일로 받지 않고 HTML `<head>` 안에 넣어 보냅니다.

```tsx
experimental: {
  inlineCss: true,
},
```

트레이드오프도 분명했습니다.

- **HTML이 커집니다.** 압축 기준 약 8.5kB에서 33.6kB로 늘었습니다.
- **CSS를 캐시할 수 없습니다.** 페이지마다 HTML에 CSS가 다시 담겨 옵니다.
- **실험 기능입니다.** Next.js를 업그레이드할 때 동작이 바뀌는지 확인해야 합니다.

HTML이 커지는 만큼 손해가 클 수도 있어서, 배포한 뒤 측정으로 판단하기로 했습니다.

| 항목 | 썸네일 축소 | CSS 인라인 |
|---|---|---|
| HTML 전송량 / 완료 | 약 8.5kB / 0.62s | 33.6kB / 0.76s |
| 렌더링 차단 CSS 파일 | 1개 | **없음** |
| Lighthouse 점수 | 94 | **98** |
| Lighthouse FCP | 0.92s | 0.92s |
| Lighthouse LCP | 2.95s | **1.98s** |

LCP는 2.95초에서 1.98초로 약 1초 줄었고, 성능 점수는 98점이 됐습니다. HTML이 커졌지만 서버가 HTML을 나눠 보내기(스트리밍) 때문에, CSS와 헤더가 담긴 첫 부분이 도착하자마자 화면을 그릴 수 있게 됐습니다. Lighthouse의 FCP는 두 단계 모두 0.92초로 같게 계산됐습니다.

부작용도 하나 있었습니다. HTML이 커지면서 이미지 주소를 발견하는 시점이 0.64초에서 0.76초로 늦어졌습니다. 그래도 LCP가 약 1초 줄어든 만큼 받아들이기로 했습니다.

## LCP 9.49초에서 1.98초로, 그리고 남은 과제

| 단계 | 성능 점수 | FCP | LCP |
|---|---|---|---|
| 개선 전 | 74 | 1.55s | 9.49s |
| 1편 완료 (웹폰트 개선) | 80 | 0.80s | 5.21s |
| 첫 번째 시도: GA 로딩 시점 조정 | 87 | 0.86s | 4.07s |
| 두 번째 시도: 서버 조회 전환 | 90 | 0.92s | 3.62s |
| 세 번째 시도: 이미지 요소 전환 | 95 | 0.94s | 2.79s |
| 네 번째 시도: 썸네일 축소 | 94 | 0.92s | 2.95s |
| **다섯 번째 시도: CSS 인라인** | **98** | **0.92s** | **1.98s** |

Lighthouse 모바일, 단계마다 3~5회 측정한 중앙값입니다.

![개선 후 메인페이지 로딩 모습. 새로고침 직후 헤더와 안내 문구, 카드 틀이 함께 보이고 상품 사진이 이어서 채워짐](/images/2026-10-28-main-page-performance-2-server-rendering/after-loading.gif "개선 후 메인페이지 로딩 모습 (느린 4G, CPU 4배 감속). 닉네임과 상품 정보는 가렸습니다")

처음과 비교하면 Lighthouse 성능 점수는 **74점 → 98점**, LCP는 **9.49초 → 1.98초**가 됐습니다. 상품 사진이 그려지기까지의 시간이 약 5분의 1로 줄었고, 레이아웃 이동(CLS)은 모든 단계에서 0이었습니다. Core Web Vitals의 "좋음" 기준(LCP 2.5초 이하, CLS 0.1 이하)에 들어오는 값입니다. 다만 이 값은 실험실 측정이고, Core Web Vitals는 실제 사용자 데이터의 75번째 백분위로 판단하기 때문에 실제 사용자 지표는 따로 확인이 필요합니다.

여기서 끝은 아니었습니다. CSS를 인라인한 뒤에는 폰트가 초기 JS와 다시 대역폭을 나눠 쓰는 문제가 보였습니다. 이를 고친 최적화는 DevTools 측정에서는 빨라졌지만 Lighthouse 점수는 오히려 떨어졌고, 결국 되돌렸습니다. 이 이야기는 3편에서 이어가겠습니다.
