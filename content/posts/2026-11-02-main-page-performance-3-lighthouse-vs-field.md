안녕하세요, 주라 팀 NeedU 프론트엔드 Juno 입니다!

이 글은 메인페이지 성능 개선 시리즈의 마지막 편입니다. [2편: 서버 조회 전환, 이미지, 렌더링 차단 CSS](https://needu-developer-team.github.io/tech-blog/posts/main-page-performance-2-server-rendering/)까지의 작업으로 Lighthouse(구글이 만든 웹 페이지 성능 측정 도구) 점수는 74점에서 98점으로 올랐습니다. 화면에서 가장 큰 콘텐츠인 상품 사진이 보이기까지 걸리는 시간(LCP)도 9.49초에서 1.98초로 줄었습니다.

3편에서는 그 뒤에 시도했다가 **되돌린 최적화**와, 그 과정에서 찾은 Lighthouse의 이상한 측정 결과를 다룹니다.

## 화면은 빨라졌는데, 버튼은 늦어졌습니다

웹 페이지가 열리는 과정은 크게 두 단계로 나눌 수 있습니다.

1. **화면이 보이는 단계:** 서버가 보낸 HTML과 디자인 파일(CSS)로 글자와 그림을 그립니다.
2. **화면이 동작하는 단계:** 버튼과 링크를 움직이는 JavaScript(JS) 파일을 받아 실행합니다. 이렇게 이미 그려진 화면에 동작을 붙이는 과정을 **하이드레이션**이라고 부릅니다. 하이드레이션이 끝나기 전에는 화면이 보여도 버튼을 눌러도 반응하지 않습니다.

2편의 마지막 작업은 화면을 그리기 전에 꼭 받아야 하는 디자인 파일(렌더링 차단 CSS)을 따로 받지 않고, HTML 안에 직접 담아 보내는 것이었습니다(CSS 인라인). 덕분에 1단계는 빨라져 LCP가 약 1초 줄었습니다. 그런데 브라우저가 주고받은 요청 기록(HAR)을 다시 보니, 2단계가 오히려 늦어져 있었습니다.

이 글에서 **실측**은 1편과 같은 조건(Chrome 개발자 도구의 `느린 4G` 회선, CPU `4배 감속`, 캐시 사용 안 함)에서 실제로 페이지를 열어 기록한 값을 말합니다. 요청 기록(HAR)과 성능(Performance) 탭 기록이 여기에 해당합니다. 뒤에서 설명할 Lighthouse는 시간을 계산으로 구하기 때문에, 둘을 구분해서 부르겠습니다.

| 항목 | CSS 인라인 전 | CSS 인라인 후 | 변화 |
|---|---|---|---|
| 글꼴 설정 파일 요청 | 1.83s | **0.65s** | 약 1.2초 앞당겨짐 |
| 글꼴 파일 17개 (143kB) 받는 구간 | 2.71 → 4.18s | **2.28 → 3.77s** | JS를 받는 구간과 겹침 |
| JS 받기 완료 (하이드레이션 시작) | 2.98s | **3.72s** | **0.74초 늦어짐** |

원인은 1편에서 만든 **글꼴 로더**였습니다. 글꼴 로더는 페이지 맨 끝에 넣어 둔 작은 스크립트로, 글꼴 설정 파일을 불러오는 역할을 합니다. CSS를 인라인하기 전에는 디자인 파일을 다 받을 때까지 이 스크립트가 기다렸다가 실행됐습니다. 그런데 디자인 파일이 HTML 안으로 들어가면서 기다릴 대상이 사라졌고, 스크립트가 HTML을 받자마자 바로 실행됐습니다.

그 결과 글꼴 파일과 JS 파일을 같은 시간대에 받게 됐습니다. 브라우저는 여러 파일을 받을 때 **우선순위**를 정하는데, 글꼴은 가장 높은 순위를, Next.js의 JS는 낮은 순위를 받습니다. 좁은 회선을 글꼴이 먼저 차지하면서 JS가 밀려난 것입니다. 화면은 먼저 보이지만, 버튼이 실제로 반응하기 시작하는 시점은 약 3.7초로 늦어졌습니다.

이미지나 스크립트는 우선순위를 직접 지정할 수 있지만(`fetchpriority`), CSS의 `@font-face`로 불러오는 글꼴은 그럴 수 없습니다. 그래서 순위 대신 글꼴을 **받기 시작하는 시점**을 바꾸기로 했습니다.

## 첫 방문에만 폰트를 늦게 받아 봤습니다

가장 단순한 방법은 글꼴을 항상 페이지가 다 열린 뒤(`load` 이후)에 받는 것입니다. 하지만 그러면 이미 글꼴을 받아 둔 재방문 사용자도 매번 기본 글꼴을 잠깐 보다가 NeedU 글꼴로 바뀌는 화면을 보게 됩니다.

그래서 **처음 방문한 사용자만** 글꼴을 늦게 받게 했습니다. 글꼴을 다 받은 뒤에는 브라우저에 작은 메모(localStorage)를 남기고, 다음 방문에서 이 메모가 있으면 지금처럼 바로 글꼴을 받습니다.

![첫 방문과 재방문의 글꼴 로딩 흐름. 첫 방문은 메모가 없어 화면과 버튼을 먼저 준비하고 페이지가 다 열린 뒤 글꼴을 받는다. 재방문은 메모가 있어 브라우저에 저장된 글꼴을 바로 쓴다](/images/2026-11-02-main-page-performance-3-lighthouse-vs-field/font-first-visit.png "첫 방문에만 글꼴을 늦게 받는 흐름")

실제 코드는 다음과 같습니다. 1편에서 만든 글꼴 로더에 메모를 확인하고 남기는 부분을 더했습니다.

```js
(function () {
  var href = "/fonts/kakao-small-sans-v2.002.css";
  var storageKey = "needu-font-stylesheet";
  function load() {
    var link = document.createElement("link");
    link.rel = "stylesheet";
    link.href = href;
    link.media = "print";
    link.onload = function () {
      link.media = "all";
      document.fonts.ready.then(function () {
        try {
          localStorage.setItem(storageKey, href);
        } catch (error) {}
      });
    };
    document.head.appendChild(link);
  }
  var isCached = false;
  try {
    isCached = localStorage.getItem(storageKey) === href;
  } catch (error) {}
  if (isCached || document.readyState === "complete") {
    load();
  } else {
    window.addEventListener("load", load, { once: true });
  }
})();
```

- **메모 내용:** 글꼴 버전이 담긴 파일 경로를 메모로 남깁니다. 글꼴 버전이 바뀌면 메모와 경로가 달라지므로, 자동으로 첫 방문처럼 동작합니다.
- **메모를 남기는 시점:** 글꼴 파일을 끝까지 받은 뒤(`document.fonts.ready`)에만 남깁니다. 받는 도중에 떠난 사용자는 다음에도 첫 방문으로 처리됩니다.
- **메모를 쓸 수 없는 경우:** 브라우저 설정 등으로 localStorage를 쓸 수 없으면 항상 첫 방문 방식으로 동작합니다.

실측 조건에서 첫 방문 상황으로 5회 측정했습니다.

| 항목 | CSS 인라인 | 폰트 지연 | 변화 |
|---|---|---|---|
| 글꼴 설정 파일 요청 | 0.65s | 2.91s (페이지가 다 열린 시점) | 의도대로 늦어짐 |
| **JS 받기 완료 (하이드레이션 시작)** | **3.72s** | **2.80s** | **0.92초 빨라짐** |
| 페이지가 다 열린 시점 (load) | 3.84s | 2.91s | 0.93초 빨라짐 |
| 첫 방문에 NeedU 글꼴이 적용된 시점 | 약 3.8s | 약 5.3s | 1.5초 늦어짐 |
| 화면이 밀리는 정도 (CLS) | 0 | 사실상 0 (0.0003) | 같음 |

실측에서는 버튼이 반응하기 시작하는 시점이 0.92초 빨라졌습니다. 대신 첫 방문 사용자가 기본 글꼴을 보는 시간은 약 1.5초 길어졌습니다. 글꼴이 바뀌어도 화면이 밀리지는 않았습니다.

그런데 Lighthouse 결과는 정반대였습니다.

| 항목 (5회 중앙값) | CSS 인라인 | 폰트 지연 |
|---|---|---|
| 성능 점수 | 98 | **91** |
| LCP | 1.98s | **3.17s** |
| TBT | 99ms | 145ms |
| FCP / CLS | 0.92s / 0 | 0.92s / 0 |

TBT는 페이지가 열리는 동안 화면이 다른 작업에 막혀 입력에 반응하지 못한 시간의 합이고, FCP는 화면에 무언가 처음 그려진 시점입니다.

회차별로 보니 5회 중 2회는 LCP가 4.60초로 크게 튀었고, 나머지 3회도 LCP가 2.79~3.17초로 CSS 인라인 단계의 중앙값(1.98초)보다 0.8~1.2초 높았습니다.

## 실측과 Lighthouse가 반대로 말한 이유

같은 코드인데 결과가 반대로 나온 이유는 두 가지였습니다.

**원인 1. Lighthouse는 실제로 느리게 열어 보지 않고, 계산합니다.**

두 방식은 측정 방법부터 다릅니다.

| | 실측 | Lighthouse 기본 측정 |
|---|---|---|
| 측정 방법 | 회선과 CPU를 실제로 느리게 만든 뒤 페이지를 엽니다 | 제한 없이 **빠르게 한 번 연 뒤**, 그 기록으로 느린 회선이었다면 얼마나 걸렸을지 **계산**합니다 |
| LCP를 구하는 방식 | 상품 사진이 실제로 그려진 시점을 잽니다 | 빠른 기록에서 LCP보다 **먼저 시작된 요청은 모두** 사진을 그리는 데 필요했다고 보고 시간을 더합니다 |

빠른 환경에서는 페이지가 약 0.2초 만에 다 열립니다. 그래서 "페이지가 다 열린 뒤" 받게 한 글꼴 파일(143kB)과 GA 스크립트(181kB)가 상품 사진이 그려진 시점과 거의 같은 시점에 요청됩니다. 이 요청들이 사진보다 조금이라도 먼저 시작된 회차에서는, Lighthouse가 이 파일들까지 사진을 그리는 데 필요했다고 보고 느린 회선 기준의 시간을 더했습니다.

실측에서는 사정이 달랐습니다. 상품 사진은 1.82초에 그려졌고, 글꼴 요청은 그보다 1초 넘게 늦은 2.88초에 시작했습니다. 글꼴이 사진에 아무 영향을 주지 않은 것입니다. 이처럼 같은 코드를 두 방식으로 재면, 결과가 반대로 나올 수 있는 구조였습니다.

**원인 2. 이미지가 두 번 요청된 회차가 있었습니다.**

LCP가 4.60초로 크게 튄 2회는 다른 현상이었습니다. 페이지가 다 열린 직후 **상품 이미지 3장이 한 번 더 요청**됐고, Lighthouse가 두 번째로 그려진 이미지를 기준으로 LCP를 잡았습니다. 이 현상은 실측 10회에서는 한 번도 나오지 않았습니다. 처음에는 폰트 지연 때문이라고 생각했지만, 원인을 확인하기 전에 유지할지 되돌릴지부터 정해야 했습니다.

## 결국 폰트 지연을 되돌렸습니다

| 관점 | 폰트 지연 유지 | 되돌리기 |
|---|---|---|
| 실측: 버튼이 반응하기 시작하는 시점 | 2.80s | 3.72s (0.92초 늦어짐) |
| 첫 방문에 NeedU 글꼴이 적용된 시점 | 약 5.3s | 약 3.8s |
| Lighthouse 점수 / LCP | 91 / 3.17s | 약 98 / 약 2.0s |

처음에는 실측 결과를 근거로 폰트 지연을 유지하기로 했습니다. 하지만 다시 검토한 끝에 되돌렸습니다. 팀이 성능을 보고하고 비교할 때 쓰는 지표가 Lighthouse였고, 처음 방문한 사용자가 기본 글꼴을 1.5초 더 보는 것도 서비스의 첫인상에 영향을 준다고 판단했습니다.

이 변경은 이미 개발 브랜치(`dev`)에 합쳐진 상태였습니다. 그래서 기록을 지우지 않고, 합친 변경을 거꾸로 적용하는 새 변경(`git revert -m 1`)을 만들어 되돌렸습니다. 사용자 브라우저에 남은 글꼴 메모는 되돌린 코드가 더 이상 읽지 않으므로 아무 영향이 없습니다.

그런데 되돌린 뒤에도 이미지가 두 번 요청되는 현상이 나왔습니다. 되돌린 코드는 CSS 인라인 단계와 완전히 같은데도, Lighthouse 5회 중 2회에서 같은 현상이 생겼고 LCP가 4.31초, 5.73초로 튀었습니다.

| 조건 | 이미지 중복 요청 | 중복이 없는 회차의 LCP |
|---|---|---|
| CSS 인라인 (당시) | 0 / 5회 | 1.83–2.87s |
| 폰트 지연 | 2 / 5회 | 2.79–3.17s |
| 되돌린 후 | 2 / 5회 | 1.83–2.51s |

**이미지 중복 요청은 폰트 지연과 무관한 현상**이었습니다. 폰트 지연 단계의 점수 하락(98 → 91) 중 상당 부분은 폰트 지연 때문이 아니라 이 현상이 섞인 결과였습니다. 다만 중복이 없는 회차끼리 비교해도 폰트 지연 단계의 LCP가 높았기 때문에, 원인 1의 영향은 실제로 있었습니다.

### 이미지가 두 번 요청된 이유를 따라가 봤습니다

**단서 1. 넣지 않은 "미리 받기"가 있었습니다.**

브라우저에는 곧 필요할 파일을 먼저 받아 두라고 알려 주는 기능(preload)이 있습니다. 중복이 생긴 Lighthouse 결과를 보니, 첫 번째 이미지 요청이 이 preload로 기록돼 있었습니다. 2편에서 이미지 preload는 일부러 넣지 않았는데도 말입니다.

원인은 화면을 만드는 라이브러리인 React(19 버전)였습니다. React 19는 서버에서 화면을 만들 때 "높은 우선순위로, 바로 받아야 하는 이미지"를 찾으면 preload를 **자동으로** 추가합니다. 2편에서 상품 이미지에 `loading="eager"`(바로 받기)와 `fetchPriority="high"`(높은 우선순위)를 지정했기 때문에 여기에 해당했습니다.

보통은 이미지가 미리 받아 둔 파일을 그대로 다시 씁니다. 그래서 먼저 preload와 실제 이미지의 주소와 요청 설정(`crossorigin`, `referrerpolicy`, `srcset`)이 같은지 확인했는데, 모두 같았습니다. 설정이 달라서 생긴 문제는 아니었습니다.

**단서 2. 로딩 화면이 먼저 보인 회차에서만 생겼습니다.**

Lighthouse의 `추적 보기`로 정상 회차와 중복 회차의 기록을 저장해 비교했습니다.

| 항목 | 정상 회차 (100점) | 중복 회차 (84점) |
|---|---|---|
| 처음 보인 화면 | 본문 | **로딩 문구** |
| 본문이 처음 보인 시점 | 120ms | 291ms |
| 이미지 1번째 요청 | 미리 받기, HTML을 읽다가 요청 | 미리 받기, HTML을 읽다가 요청 |
| 이미지 2번째 요청 | 없음 | **272.8ms, 스크립트가 요청** |
| 2번째 요청 직전 | – | 269.8ms, React 코드 실행 |

중복은 **서버 응답이 조금 늦어 로딩 화면이 먼저 보인 회차**에서만 생겼습니다. 두 번째 요청은 React 코드가 실행된 직후, 스크립트가 이미지를 새로 만들면서 나갔습니다. 기록을 바탕으로 추정한 흐름은 다음과 같습니다.

![정상 회차와 중복 회차의 비교. 정상 회차는 HTML에 본문까지 담겨 와 이미지를 한 번만 받는다. 중복 회차는 로딩 화면이 먼저 오고, 본문으로 바꾸기 전 대기하는 사이 JS가 먼저 실행돼 본문을 새로 그리면서 이미지를 다시 요청한다](/images/2026-11-02-main-page-performance-3-lighthouse-vs-field/image-double-request.png "Lighthouse에서 이미지가 두 번 요청되는 과정 (추정)")

1. 서버는 데이터를 조회하는 동안 헤더와 로딩 화면을 먼저 보내고, 본문은 조회가 끝나면 이어서 보냅니다(스트리밍).
2. React 19는 로딩 화면을 본문으로 바꾸는 작업을 **약 300ms씩 묶어서** 처리합니다.
3. Lighthouse의 빠른 환경에서는 JS가 매우 빨리 실행돼, 이 교체가 일어나기 전에 하이드레이션이 먼저 시작됩니다.
4. 이때 React가 서버에서 온 본문을 그대로 쓰지 못하고 새로 그리면서, 이미지도 다시 요청합니다.
5. Lighthouse는 다시 그려진 이미지를 기준으로 LCP를 잡고, 계산 과정에서 4초 이상으로 커집니다.

**재현 시도:** 원인을 확정하려고, 로컬 환경에서 서버의 데이터 조회에 0.5초 지연을 넣어 로딩 화면이 먼저 보이게 만들었습니다.

| 조건 | 로딩 화면 → 본문 교체 | 이미지 중복 | 화면 어긋남 경고 |
|---|---|---|---|
| 로컬 개발 모드 | 있음 | 없음 (같은 이미지가 그대로 옮겨짐) | 없음 |
| 로컬 운영 빌드 | 있음 | 없음 | – |
| dev 서버 실측 (느린 4G, 13회) | – | 없음 | – |
| dev 서버 Lighthouse | 일부 회차 | 약 40% | 콘솔 오류 없음 |

로딩 화면이 본문으로 바뀌는 과정은 재현됐지만, 이미지 중복은 Lighthouse 환경에서만 나타났습니다. 서버가 만든 화면과 브라우저가 만든 화면이 어긋날 때 나오는 경고(하이드레이션 불일치)처럼, 코드에 버그가 있다는 증거도 없었습니다.

느린 모바일 회선에서는 JS가 2.8~3.7초에 도착하고, 본문 교체는 그보다 훨씬 이른 약 1초에 끝나므로 이 현상이 생기지 않습니다. 빠른 회선에서 서버 응답만 느린 경우에는 생길 수 있지만, 그 영향은 이미지 약 30kB를 한 번 더 받는 정도로 봤습니다.

그래서 여기서 조사를 마무리하고 **알려진 한계로 기록**했습니다. 이후 Lighthouse 결과를 볼 때는 이미지 중복이 생긴 회차(점수가 크게 떨어지고 LCP가 4초 이상)를 따로 구분해서 해석하기로 했습니다.

## 74점에서 98점으로, 그리고 남은 과제

| 항목 | 개선 전 | 최종 |
|---|---|---|
| Lighthouse 성능 점수 | 74 | **98** |
| Lighthouse FCP | 1.55s | **0.92s** |
| Lighthouse LCP | 9.49s | **1.98s** |
| 화면이 밀리는 정도 (CLS) | 0 | 0 |
| 받는 웹폰트 | 972kB | **약 140kB** |

Lighthouse 모바일, 5회 측정한 중앙값입니다. 폰트 지연을 되돌린 최종 코드는 2편의 CSS 인라인 단계와 같아서, 그 단계의 측정값을 최종 결과로 적었습니다. 되돌린 뒤 다시 측정했을 때도 이미지 중복 요청 회차를 빼면 LCP는 1.83~2.51초였습니다.

폰트 지연은 되돌렸지만, 그 과정에서 Lighthouse 점수가 회차마다 크게 흔들리던 원인을 찾았습니다. 덕분에 이후 측정 결과를 더 정확하게 해석할 수 있게 됐습니다.

버튼이 반응하기 시작하는 시점(하이드레이션, 실측 약 3.7초)이 늦은 문제는 남은 과제로 두었습니다. 다음에는 글꼴을 늦추는 대신, 처음에 받아야 하는 JS 자체를 줄이는 방향으로 접근할 계획입니다. 예를 들어 오류를 수집하는 도구는 나중에 불러오고, 첫 화면에 필요 없는 공통 설정 코드(Provider)는 따로 떼어 내려고 합니다.

세 편에 걸쳐 측정 기준을 세우고, 원인을 하나씩 고치고, 되돌리기까지 한 과정을 정리했습니다. 비슷한 문제를 겪고 계신 분께 도움이 되면 좋겠습니다. 읽어 주셔서 감사합니다!
